# 第三十四课：首次发送与单轮任务状态闭环

创建日期：2026-09-26。状态：基础实现和首次发送桌面回归已完成，完整生命周期矩阵待完成。

前一课：[第三十三课：任务状态收敛与生命周期闭环验收](43-第三十三课-任务状态收敛与生命周期闭环验收.md)。阶段复盘：[第二十二至三十三课小结](44-第二十二至三十三课小结.md)。

本课是后续 Codex 类交互收口的起点。先把“空白工作台直接发送一条消息”做成一条状态清楚、可取消、可失败恢复的完整流程，再在后续课程分别处理会话管理、输入框、消息操作、任务详情和响应式布局。

本课不接入 MCP、Skills、SSH、并发 Agent、自动批准、任意命令或新的模型工具。本课也不做整页视觉重设计，不把工作区、任务历史和所有工具面板一次性重写。

## 1. 本课目标与前置条件

完成后应达到以下结果：

1. 空白工作台可以直接输入并发送；首次发送时自动创建会话，不要求用户先点击“新建会话”。
2. 同一轮请求的 `conversationId`、用户消息 ID、助手消息 ID、`taskId` 和 `requestId` 归属明确，迟到事件不能写入其他会话或其他轮次。
3. 页面能区分空闲、创建、运行、停止中、完成、失败和已停止等用户可理解的状态；等待批准仍然不能伪装成进程运行。
4. 重复点击发送不会创建第二个运行时任务；停止后底层收尾完成，页面恢复发送能力。
5. 第一轮失败后可以在同一会话继续输入第二轮；失败或停止的助手内容不进入下一轮有效上下文。
6. 重新生成只在来源仍可安全确认时显示；不能因为刷新、切换模式或附件变化就使用当前环境猜测旧请求来源。

第 33 课的桌面生命周期矩阵是本课前置基线。若刷新、取消、超时、工作区撤销或窗口销毁仍未在可用 Electron 环境观察，应先记录为前置待验收，不在本课用新 UI 掩盖问题。

## 2. 用 Vue 经验理解本课

| Vue 经验 | React / Electron 对应 | 本课用途 |
|---|---|---|
| 路由进入页面时创建默认会话 | 首次发送事件中创建会话并继续请求 | 避免空白页面必须先点击一次“新建” |
| Pinia 中的 `loading` | renderer 的 `Operation` | 控制按钮和输入框的瞬时互斥 |
| 后端任务状态 | 主进程发布的 `TaskRecord` | 作为任务生命周期的唯一权威 |
| `watch` 请求结果 | IPC 事件订阅与请求 ID 判断 | 过滤迟到事件 |
| 失败后保留表单 | 失败消息保留、草稿和发送能力恢复 | 让用户可以继续输入或重新请求 |

不要把 `operation === 'generating'` 当成完整任务状态。它只说明页面当前是否有生成操作；`TaskRecord.status` 才说明主进程任务已经走到哪个生命周期阶段。两者可以互相影响界面，但不能各自推进同一条任务的终态。

## 4. 先画出单轮调用链

实现前先画出下面这条链，并在每个箭头标出 ID：

```text
用户输入
  → 首次发送事件
  → 创建或确认 conversationId
  → 创建 userMessageId、assistantMessageId、taskId、requestId
  → preload IPC
  → 主进程创建 TaskRecord 和运行时句柄
  → task:state / model:delta 事件
  → renderer 按 conversationId、taskId、requestId 更新
  → 成功、失败或取消后保存展示记录
```

必须分清：

- `conversationId` 表示消息归属的会话。
- `userMessageId` 和 `assistantMessageId` 标识这一轮展示消息。
- `requestId` 标识一次请求和事件流。
- `taskId` 标识主进程任务生命周期。
- `operation` 是页面操作互斥状态，不是持久化任务状态。

## 5. 按依赖顺序实现

### 第一步：定义首次发送策略

选择一种明确策略并写下理由：

```text
空白工作台
  → 先在 renderer 创建本地会话
  → 得到 conversationId
  → 再启动请求
```

或者：

```text
首次发送一次性创建会话和请求
  → 主进程与 renderer 使用同一个 conversationId
```

无论选择哪种策略，都不能先启动一个没有会话归属的请求，再靠默认的 `time` 会话或当前选中项补救。若请求在被接受前就被参数、容量、会话创建或 IPC 调用拒绝，应保留 composer 草稿并显示错误，不能清空用户输入。若请求已经被接受，随后模型或网络才失败，则应保留本轮用户消息和失败任务记录，恢复发送能力，让用户继续输入第二轮；这时不要求把已经进入消息记录的内容再写回 composer。

预期效果：用户打开应用后直接输入第一句话即可发送；重复点击不会产生两个会话或两个请求。

### 第二步：统一一轮请求的身份

检查 `useChatRequest` 的 `ActiveRequest` 和主进程任务注册入口，保证发送时一次性捕获本轮所有身份。回调到达时只更新仍然匹配的会话和请求。

验收：快速连续点击、停止后立即再次发送、切换会话后收到迟到事件，都不会把助手文字或任务状态写到错误的消息上。

### 第三步：让页面状态和任务状态各司其职

页面可以用 `Operation` 禁用发送和选择，但完成、失败、取消和超时必须由主进程终态事件驱动。不要在停止按钮点击时直接把消息改成完成，也不要在请求刚发出时把任务历史提前写成成功。

至少明确以下映射：

| 主进程任务状态 | 页面可见行为 |
|---|---|
| `created` | 已提交，等待任务开始；不能重复发送 |
| `running` | 显示生成中，可点击停止 |
| `waiting_approval` | 显示等待批准，不显示正在运行的进程 |
| `completed` | 助手消息完成，可继续输入 |
| `failed` | 显示错误和失败记录，可继续输入 |
| `cancelled` | 显示已停止，可继续输入或重新生成 |
| `timed_out` | 显示超时，可继续输入；不能继续使用旧句柄 |
| `interrupted` | 显示页面重载或窗口结束导致的中断 |

### 第四步：处理失败后的第二轮

失败或停止的用户/助手消息保留在当前会话，但下一轮模型上下文只使用成功的用户/助手问答。失败的空助手消息不能被当作有效回答发送给模型。

第二轮必须使用新的 `taskId` 和 `requestId`。它可以继续留在同一个 `conversationId`，但不能复用上一轮的取消控制器、运行时句柄或一次性授权。

### 第五步：收紧重新生成入口

本课只处理状态和来源边界，不重做第 37 课的全部消息操作。先核对当前“重新生成”入口：

- 来源用户消息必须仍然能由稳定 ID 找到。
- 重试使用原请求的模式、范围和会话来源；不能直接读取当前页面的模式或附件来猜测。
- 刷新后如果没有持久化足够的来源信息，应隐藏聊天任务的重新生成入口，而不是冒险重发。
- 重试必须创建新任务，旧失败记录保留。

## 6. 常见错误

### 先发请求再补会话

请求先以默认会话启动，随后页面才创建真实会话，会造成任务记录、消息和保存记录归属不一致。

### 只判断按钮是否 disabled

按钮禁用不能阻止键盘提交、重复事件或并发回调。函数入口仍要检查操作锁、活动请求和会话归属。

### 把失败消息删除

删除失败轮次会让用户无法理解发生了什么，也会破坏任务历史。失败消息可以展示，但不能进入成功问答上下文。

### 用当前附件重试旧请求

用户切换附件或模式后，当前页面状态已经不等于旧请求状态。没有来源快照时应禁用重试，不能猜测。

### 把主进程任务状态复制到多个 renderer 状态

任务历史、消息状态和操作锁可以有不同用途，但终态只能有一个权威来源。重复状态源会导致页面显示完成而主进程仍在取消。

## 7. 桌面验收矩阵

至少在可用 Electron 环境记录观察结果：

| 场景 | 必须观察 |
|---|---|
| 空白工作台首次发送 | 自动创建会话，草稿只在请求被接受后清空 |
| 快速重复发送 | 只创建一条用户消息、一个请求和一个运行时任务 |
| 正常完成 | 助手消息完成，任务结果可见，之后可以继续输入 |
| 用户停止 | 停止后不再追加流片段，最终显示 `cancelled` |
| 模型或网络失败 | 显示错误，失败记录保留，输入恢复可用 |
| 失败后第二轮 | 同一会话、新任务；失败助手内容不进入上下文 |
| 切换会话 | 旧事件不污染新会话；不能在生成中无意切换 |
| 刷新窗口 | 活动任务按第 33 课规则对账，旧许可不恢复 |
| 重新生成 | 仅在来源安全时出现，使用新 ID，不覆盖旧记录 |
| 请求接受前失败 | composer 草稿保留，页面给出可理解错误，之后可重试 |
| 请求接受后异步失败 | 用户消息和失败任务记录保留，助手标记失败，发送能力恢复，可继续第二轮 |

离线类型检查和协议脚本只能验证部分边界，不能代替首次发送、停止、失败后继续输入和刷新后的真实桌面观察。
