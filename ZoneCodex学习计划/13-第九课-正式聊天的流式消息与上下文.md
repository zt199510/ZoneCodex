# 第九课：正式聊天的流式消息与上下文

## 1. 目标与代码起点

正式聊天发送问题后，立即出现用户消息和一条空的助手消息。真实片段持续追加到同一条助手消息；完成时这一问一答进入后续上下文，停止或失败时保留部分文字并明确标记。

本次核对：App 仍调用 askModel(history) 获取整段回复，真实流在独立 ModelStreamPractice 中。你已经将该练习区的停止入口修正为 cancelModelStream；本次没有独立操作窗口验证停止效果。

本课复用第八课 SSE 解析、网络取消和 60 秒总超时，不新建另一套网络实现，不安装依赖，也不修改密钥配置。核心代码由你亲手实现。

仍然是第六课定义的简化文本上下文：最多最近 4 轮成功问答，加当前问题，总长度不超过 24000，单个用户问题不超过 4000。本课不宣称完整保留模型推理状态，不实现工具循环、多会话切换、自动重试和持久化。

## 2. 先确定状态如何变化

```text
发送：user(pending) + assistant(pending，空文字)
片段：只修改这条 assistant 的 content
成功：user(complete) + assistant(complete)
停止：user(cancelled) + assistant(cancelled，保留部分文字)
失败：user(failed) + assistant(failed，保留部分文字)
```

这里的 status 是应用对本轮问答结果的记录，不是模型“正在思考/调用工具”的内部状态。用户消息标 pending 的含义是“这个问题正在等待完整回答”。

| 标识或状态 | 作用 |
|---|---|
| requestId | 匹配本轮网络任务，忽略旧片段和旧结果 |
| userId / assistantId | 找到消息列表里的两个固定对象 |
| React key={message.id} | 保持列表项身份，追加片段时不换 key |
| isSending | 更新按钮和界面显示 |
| sendingRef / activeRequest | 同步检查是否已有请求，并保存当前请求的目标消息 |

对应 Vue 的响应式列表更新：React 用 map 返回新数组，用 {...message, content: ...} 返回新消息对象；不会给每个片段创建一条新的助手消息。

## 6. App：保存本轮目标并订阅

将 React 导入改为：

```tsx
import { useEffect, useRef, useState } from 'react'
```

在 App 函数外定义类型：

```ts
type ActiveRequest = {
  requestId: string
  userId: string
  assistantId: string
}
```

在 App 已有的 sendingRef 等状态旁增加：

```tsx
const activeRequest = useRef<ActiveRequest | null>(null)
const subscribed = useRef(false)
const [streamReady, setStreamReady] = useState(false)
```

在 App 内添加 Effect：

```tsx
useEffect(() => {
  const unsubscribe = window.api.onModelDelta((event) => {
    const active = activeRequest.current
    if (!active || event.requestId !== active.requestId) return
    setMessages((previous) => previous.map((message): Message =>
      message.id === active.assistantId && message.status === 'pending'
        ? { ...message, content: message.content + event.delta }
        : message
    ))
  })
  subscribed.current = true
  setStreamReady(true)

  return () => {
    subscribed.current = false
    unsubscribe()
    const active = activeRequest.current
    activeRequest.current = null
    sendingRef.current = false
    if (active) {
      void window.api.cancelModelStream(active.requestId).catch(() => {
        // App 已卸载，不再更新 UI；窗口生命周期仍有主进程清理。
      })
    }
  }
}, [])
```

这里的回调不直接读取闭包里的 messages，用函数式更新获得更新队列中的最新前值。activeRequest 是 ref，所以不需要每次换 requestId 都重新订阅。

只更新对应的 pending 助手消息。旧 requestId 不匹配就忽略，已完成消息也不再追加。清理先移除监听，再使当前请求失效，最后请求取消；只取消订阅不会停止后台 fetch。

开发时修改 App 可能触发热更新重建或 Effect 清理；这不等同于正常完成。遇到热更新后的临时状态，完整重启后再验收，不要用热更新来验证正在进行的真实请求。

## 7. App：替换正式发送函数

在 App 内添加更新本轮结果的函数：

```tsx
function finishTurn(
  active: ActiveRequest,
  status: 'complete' | 'failed' | 'cancelled'
): void {
  setMessages((previous) => previous.map((message): Message =>
    message.id === active.userId || message.id === active.assistantId
      ? { ...message, status }
      : message
  ))
}
```

用下面函数替换整个原 handleSend，包括旧 askModel 调用和成功时“新建助手消息”的逻辑：

```tsx
async function handleSend(rawContent: string): Promise<void> {
  const content = rawContent.trim()
  if (!subscribed.current || sendingRef.current || !content) return
  if (content.length > 4000) {
    setChatError('请输入不超过 4000 个字符的消息。')
    return
  }

  const history = buildContext(messages, content)
  const active: ActiveRequest = {
    requestId: crypto.randomUUID(),
    userId: crypto.randomUUID(),
    assistantId: crypto.randomUUID()
  }
  const userMessage: Message = {
    id: active.userId, role: 'user', content, status: 'pending'
  }
  const assistantMessage: Message = {
    id: active.assistantId, role: 'assistant', content: '', status: 'pending'
  }

  activeRequest.current = active
  sendingRef.current = true
  setIsSending(true)
  setChatError(null)
  setMessages((previous) => [...previous, userMessage, assistantMessage])

  try {
    const result = await window.api.startModelStream(active.requestId, history)
    if (activeRequest.current?.requestId !== active.requestId) return
    if (result.status === 'done') {
      finishTurn(active, 'complete')
    } else if (result.status === 'cancelled') {
      finishTurn(active, 'cancelled')
    } else if (result.status === 'error') {
      finishTurn(active, 'failed')
      setChatError(result.error)
    }
  } catch {
    if (activeRequest.current?.requestId === active.requestId) {
      finishTurn(active, 'failed')
      setChatError('流式通信失败，请重试。')
    }
  } finally {
    if (activeRequest.current?.requestId === active.requestId) {
      activeRequest.current = null
      sendingRef.current = false
      setIsSending(false)
    }
  }
}
```

history 在添加占位消息之前构造，当前问题只加入一次；空助手消息不能发送给模型。setMessages 不会立即替换当前函数中的 messages。

成功终态只改状态，不再追加一份完整助手文字。文字已经由 delta 拼好，再添加一次会得到两条回复或重复文本。

这一层 finally 恢复 React 状态；主进程 finally 释放网络任务；readResponseStream 的 finally 清理 reader。三个位置各有自己的资源。

## 8. 停止按钮与正式界面

在 App 内新增：

```tsx
async function handleStop(): Promise<void> {
  const active = activeRequest.current
  if (!active) return
  try {
    await window.api.cancelModelStream(active.requestId)
  } catch {
    if (activeRequest.current?.requestId === active.requestId) {
      setChatError('停止请求失败，请等待完成或超时。')
    }
  }
}
```

在 MessageList 附近添加：

```tsx
<button type="button" disabled={!isSending} onClick={() => { void handleStop() }}>
  停止生成
</button>
```

正式 ChatInput 的 disabled 改为：

```tsx
disabled={!streamReady || isSending}
```

保留 key={inputVersion} 和 onSend 回调。确认 ChatInput 内的 input 也使用 disabled 属性。

等待提示可改为“正在接收回复…”。保留错误提示、清空按钮和 handleClearConversation 的 sendingRef 检查。请求进行时仍不允许清空；停止的最终结果回来后才恢复清空和发送。

停止按钮不直接调用 finishTurn，也不立刻设 isSending=false。否则旧任务尚未清理，就可能启动新请求。自然完成恰好先于取消时，最终显示完成是正常的。

把 App 的 ModelStreamPractice 导入、showModelStream 状态以及挂载/卸载练习区的 JSX 移除。文件保留作为练习记录，但当前主界面只使用正式聊天入口，避免两个入口争抢同一窗口的真实流任务。若你的 App 仍挂载模拟区，也可以同样移除其挂载及未使用的导入/状态。

不要删除主进程旧处理器、旧练习文件或 askModel 实现；本课先完成行为整合，后面再做明确的清理重构。

## 9. 上下文与本地验证

context.ts 保持原样：pending、failed 和新增的 cancelled 都不会通过 complete 检查。即使屏幕上有三轮记录，本次请求也可能只有一轮成功历史。

示例：

```text
第一轮：user complete + assistant complete
第二轮：user cancelled + assistant cancelled（保留半句）
第三轮：当前问题

第三次实际 history：第一轮的两条消息 + 当前问题，共 3 条
```

原有 9 条/24000 总长度裁剪仍有效。若最近一轮助手回复太长，可能整轮被裁掉，只发送当前问题；页面记录仍保留，不能据此误判历史丢失。

先运行 npm run typecheck，再停止 Debug All 并 F5 完整重启。重点检查新签名的所有调用点：App、preload、main 和保留的 ModelStreamPractice。

| 本地或界面实验 | 预期 |
|---|---|
| 连续三个 delta | 只更新同一条助手消息，ID 不变、列表长度不变 |
| 旧 requestId 的 delta | 不修改当前或历史消息 |
| done | 两条消息变 complete，不再追加助手消息 |
| cancelled / error | 两条消息变对应状态，部分文字保留 |
| 下一次 buildContext | 排除停止/失败轮次，当前问题只出现一次 |
| 清空 | 空闲时清除消息、错误和草稿，目录保留 |

本地测试可使用虚构 ID 和片段“你”“好”，不需要真实密钥。真正请求的最小验收：

1. 第一轮告知测试代号“蓝鲸27”，能看到同一条助手消息逐渐变长，最终完成。
2. 第二轮问代号；主进程 history 为 user/assistant/user，确认上下文真的发送了。
3. 请求较长回答，中途停止；最终两条消息标为已停止，文字不再增加。
4. 再发送问题；主进程 history 不含停止轮次。

故障实验可临时在 model-stream.ts 的 onDelta 回调中使用一个请求内计数器，在第二个片段到达时抛出 Error，验证“已经显示一部分文字后失败”的路径。计数器放在该次 IPC 请求的作用域，不能是跨请求全局变量。错误后应释放任务并恢复按钮；删除实验代码、完整重启后再验证正常请求。优先离线模拟事件，不用反复付费制造故障。

如果只有按钮恢复、消息仍 pending，优先检查 finishTurn 是否在三种最终结果和 catch 中执行。如果停止后新请求提示忙，先检查停止是否仍误调用 cancelMockStream，及主进程 finally 是否执行。

当前 history 仍是显示文字重建的简化对话，不保存完整 output、推理项和 phase。它适用于当前纯文本练习，不是完整推理续接或工具循环的通用实现。后续进入这些能力前需要设计协议历史与显示消息的对应关系。

自测题：

1. 为什么发请求前要创建空的助手消息？为什么不能每来一段就 push 一条？
2. requestId、assistantId 和 React key 分别负责什么？
3. history 为什么要在追加 pending 消息之前创建？
4. 为什么 done 后只修改状态，不再追加完整回复？
5. 停止的半截文字为什么可以显示，却不进入本课下一次上下文？
6. 主进程和 React 的 finally 分别清理什么？
7. 清空按钮为什么仍要等待请求结束？
8. 现在实现了多轮流式文字，是否等于完整保存了模型推理状态和聊天记录？



1. **基本正确。**先创建一条带固定 `assistantId` 的空助手消息，后续片段都追加到它身上。不能每来一个片段就新增一条，否则一句回答会被拆成很多条消息。

2. 需要把“对话”和“请求”分开：

   | 标识 | 标识什么 |
   |---|---|
   | `requestId` | 一次生成请求；再次发送就换一个 |
   | `assistantId` | 本次生成对应的那条助手消息 |
   | React `key` | 列表项或组件的身份；这里使用 `message.id` |

   一段多轮对话包含多个请求，不共用一个 `requestId`。

3. `history` 是消息集合，但题目问的是**为什么先构造它**。因为本次请求需要“成功历史＋当前问题”，不能把刚创建的空助手消息发过去，也不能重复加入当前问题。另外，`setMessages` 不会立即改变当前函数里的 `messages`。

4. **`done` 表示成功完成，不是要求停止。**

   ```text
   done      → 成功完成
   cancelled → 已取消
   error     → 失败
   ```

   完成时文字已经通过 delta 拼好了，所以只改消息状态；再次追加全文会重复。

5. **正确。**停止的半截回复可以留给用户阅读，但本课只把完整成功的一问一答放进后续上下文。

6. 不只是刷新状态，还要区分两层：

   - **主进程 `finally`**：清理网络任务、计时器和窗口监听器。
   - **React `finally`**：清空当前请求标记，恢复发送按钮。

   它们都不会自动删除聊天消息。

7. 主要是**防止旧请求回写已经清空的对话**。如果后台还在生成，你已经清空了消息，后续片段和最终结果就可能找不到目标，或污染新对话。本课采用“请求结束后才能清空”的简单规则。

8. **不是。这里有三个不同层次：**

   - 多轮上下文：每次把选中的历史文字发给模型，已经实现。
   - 聊天持久化：保存到磁盘，重启后恢复，尚未实现。
   - 完整模型推理状态：保留完整协议输出、推理项和 `phase` 等，当前文本历史没有做到。
