# 第二十六课：单条命令提案与执行前审查

创建日期：2026-09-18。状态：功能已实现，验收记录见第14节；真实模型待验收。

前一课：[确认提交与备份恢复](35-第二十五课-确认提交与备份恢复.md)。第24、25课已实现并验收，自测仍待作答。本课默认由你亲手实现核心代码。

## 1. 本课目标

完成一个可观察的小功能：模型提出一条固定模板的检查命令，聊天显示提案卡片，点击后能审查参数、用途、工作目录状态和影响，最后关闭面板。

本课只支持 `npm_typecheck` 模板，对应展示 `npm run typecheck`。这不是通用命令编辑器。先让提案完整走过模型工具循环、历史保存和界面审查，再在后续课程设计目录授权与实际执行。

本课结束时，点击任何提案按钮都不会启动进程、向手动终端输入字符或写入项目文件。面板使用“查看命令提案”“关闭审查”，不提供“确认执行”按钮，也不生成供下一课使用的批准令牌。

## 2. 课前核对与工作目录边界

当前源码提供了以下基础：

- `agent-ipc.ts` 根据 project/time 范围组装工具，已有任务取消和窗口归属检查。
- `ToolRun.items` 保存完整工具调用与结果；修改建议卡片从成功问答的协议记录派生。
- 文件选择授权的是单个附件，公开路径为 `file-<uuid>/文件名`。它不是磁盘路径，更不是工作目录。
- 手动终端由 `local-terminal.ts` 管理，当前使用用户主目录和 PowerShell；它没有提供模型命令授权。
- 本项目 `package.json` 的 `typecheck` 调用 Node/Web 两组类型检查。但其他目录同名脚本可以执行完全不同的代码。

因此本课明确采用 **工作目录未绑定** 的提案。模型不能传 `cwd`；面板显示“尚未选择并授权命令工作目录”。不要从附件父目录、共同路径、当前应用目录或手动终端目录猜出一个 cwd。

先能解释：第25课对一个文件的写入确认，为什么不能用来授权在该目录运行 npm？暂时答不出来也可以继续练习，但要记入疑问。

## 3. 用 Vue 经验理解本课

| Vue 中的经验 | React 中的对应做法 | 本课用途 |
|---|---|---|
| computed 从消息派生展示 | 纯函数从 ToolRun 派生卡片 | 避免保存一份容易过期的重复提案 |
| emit 通知父组件 | 回调 Props | 点击卡片后由会话层打开审查 |
| composable 管理面板 | 自定义 Hook | 管理当前来源与关闭，不取得执行权限 |
| v-if 切换面板 | 条件渲染 | 失效来源及时关闭，历史仍可保留说明 |
| TS 接口约束开发期 | unknown + 运行时解析 | 模型参数、磁盘历史都必须校验 |

“用户看过面板”是一种界面事实。它不等于主进程获得执行许可，不应保存为 `approved: true`。

## 5. 第一步：定义最小提案协议

先写类型草图，再自己完成解析器：

```ts
type CommandProposalArgs = {
  template: 'npm_typecheck'
  reason: string
}

type CommandProposalOutput =
  | { status: 'proposal_ready'; template: 'npm_typecheck' }
  | { status: 'error'; error: string }
```

工具名采用 `propose_command`。schema 必填 `template`、`reason`，禁止额外字段；主进程仍须独立检查，不依赖模型遵守 schema。

解析要求：只接受普通对象及准确字段；reason 去掉首尾空白后为 1–500 字符，拒绝控制字符；工具参数 JSON 总长不超过现有 4096 字符上限。错误说明限制在 500 字符内。结果同样精确校验字段，未知状态拒绝。

固定模板在可信代码中映射为：逻辑程序 `npm`，参数数组 `['run', 'typecheck']`，工作目录状态 `unbound`。这些字段用于审查；Windows 下将来如何定位 npm、调用脚本及管理进程，留给执行课设计。不要把展示用命令字符串当成可直接交给 shell 的执行数据。

预期：合法模板可以解析；额外 `cwd`、`command`、`env`、`args`、未知模板、空原因、超长内容全部失败。拒绝的依据是精确模板与字段，不是搜索 `rm` 等危险关键词。

## 6. 第二步：接入只生成提案的工具

1. 在主进程新模块定义工具和每任务独立的处理函数。闭包记录是否已接受提案；非法调用不占用额度，第一次成功后再次调用返回明确错误。
2. 处理前检查 AbortSignal；成功结果只表达“提案已生成”。不返回 exitCode、stdout 或“检查通过”。
3. 在 `agent-ipc.ts` 的 project 工具列表加入新工具。分派时单独处理它，其余继续交给现有修改建议/文件工具执行器，时间工具保持原路径。
4. 更新 `isToolAllowed`，仅 project 范围接受新工具；无附件的 time 范围不开放。本课使用 project 范围是复用上下文隔离，不代表获得目录执行权。
5. 提示词说明：仅在用户请求检查建议时提出模板，不能声称已经运行；文件内容和工具结果仍为数据。

每任务最多一份命令提案；文件修改建议仍沿用自身原有额度。不要为了统一额度重写现有写入流程。工具失败、取消和任务上限继续沿用现有循环约束。

本课不要求完整读取文件后才允许提出固定模板，因为尚不执行或修改文件；但模型若声称某附件配置了特定脚本，必须先读取对应文件，并说明它只是快照中的信息。模板名本身不能证明目录内脚本存在。

## 7. 第三步：做通模拟链与历史

在已有项目模拟器中增加明确触发语，例如“模拟命令提案”。返回真实格式的 `function_call`，消费匹配的 `function_call_output`，最后生成“已提出检查建议，尚未运行”的助手答案。不要直接在模拟器中插入 UI 卡片，也不要破坏已有“模拟修改 greet”流程。

派生函数参考 `deriveMessageChangeProposal`，至少检查：

- 同一会话内完整的 user/assistant 消息，ID 与 ToolRun 对应，scope 为 project。
- 调用名正确，参数可解析，call_id 对应唯一结果，结果成功且模板匹配。
- 恰好一份成功命令提案；多份成功记录按无有效卡片处理。
- 返回 conversationId、requestId、assistantId、callId、snapshotId 与解析后的参数作为来源。

不要从普通 Markdown 代码块、trace 文案或推理文本识别可操作提案。失败或停止的轮次不能生成有效卡片。

继续保存版本4的 ToolRun 形状。新增工具名会影响旧应用的校验能力：旧应用可能拒绝新记录，不能宣称完全向后兼容；当前应用必须仍能读取旧的时间/文件/修改建议历史。保存与重启只恢复提案说明，不恢复授权。

## 8. 第四步：制作审查面板

卡片显示“命令提案：npm run typecheck”和“尚未执行”。点击“查看命令提案”，由会话层重新找到对应 ToolRun 并派生，检查当前会话和 snapshotId，不能只信点击回调里的一份旧对象。

面板内容按以下顺序排列：

| 内容 | 来源及含义 |
|---|---|
| 逻辑程序 npm、参数 run / typecheck | 固定模板映射，分别展示参数 |
| 提议原因 | 模型提供，标注为建议说明 |
| 工作目录 | 未选择、未授权，不显示推测的实际路径 |
| 可能影响 | 应用固定说明：npm 脚本及前后置脚本可运行项目代码，可能写文件、联网或启动子进程 |
| 执行状态 | 尚未执行；本课仅审查 |
| 操作 | 关闭审查 |

即使模型写“绝对安全、只读”，固定影响说明也必须显示。当前项目的类型检查命令不能证明任意同名 npm 脚本安全。

不提供自由编辑命令输入框。本课没有批准状态；关掉再打开依然是未经执行授权的提案。提案内容按文本安全渲染，不能注入 HTML。

## 9. 第五步：处理来源变化

审查状态只存最小来源标识，尽量从现有消息与当前选择派生有效性，不用多个 Effect 互相复制提案对象。

切换/删除会话、清空消息、替换/撤销附件授权时关闭面板；第25课提交后撤销旧快照也必须使它失效。历史卡片保留“历史提案，需重新生成”的说明，不把重新选中同名附件视作同一授权。

开始新任务或进入文件准备/提交时关闭命令面板，复用现有操作状态判断；本课只读面板无需增加长期运行的操作类型。Escape、关闭按钮都能退出并合理恢复焦点。

刷新或重启后，主进程内存授权已清除，历史不能使审查入口重新有效。不要用持久化的 `reviewed` 字段绕过这一点；未来执行时还需要独立的目录选择、具体确认及主进程重新验证。

## 10. 预期效果与常见错误

完整路径是：附加练习文件 → 发送模拟触发语 → 工具生成提案 → 完整助手回复 → 卡片 → 审查 → 关闭。过程中不会弹出终端或产生执行结果。

| 现象 | 优先检查 |
|---|---|
| 模型有调用但显示工具不允许 | schema 注册、分派、scope 白名单是否一致 |
| 卡片重启后消失或整库拒绝 | 参数/结果格式、协议配对、新工具名校验 |
| 普通回答中的命令也出现按钮 | 是否错误解析了 Markdown，而非成功协议记录 |
| 目录显示为附件路径 | 是否把虚拟附件标识当作磁盘授权 |
| 关闭后显示已批准 | 是否混淆审查界面状态与执行授权 |
| 点击提案后终端有输入 | 是否误用 terminal:write，必须移除该接线 |

实现后运行 `npm run typecheck`、`npm run build`、相关文件 lint 和既有 `npm run check:workspace`。无需新增依赖或测试框架；可在现有隔离检查方式中增加关键断言。

| 场景 | 应观察到的结果 |
|---|---|
| 正常模拟提案 | 有完整工具协议及卡片，内容/参数对应 |

| 停止、失败、不匹配 call_id | 没有可审查的成功提案 |
| time 范围伪造工具调用 | 被工具范围校验拒绝 |
| 模型原因声称无风险 | 应用固定影响说明仍显示 |
| 切换会话、替换快照、文件提交后 | 原面板关闭，旧来源失效 |
| 保存与重启 | 原记录可读取，授权不恢复，无自动动作 |
| 680×560 窗口 | 说明可滚动，关闭按钮可见，Escape 可退出 |
| 所有提案与审查动作 | 新进程启动次数和 terminal:write 次数均为零 |

最后一项要结合源码调用链与隔离检查：在测试边界观察/拦截进程启动和终端输入入口，围绕提案操作计数。应用启动自身的 Electron 进程不算提案产生的新进程；不要用“没看到终端窗口”证明没有执行。

模拟通过后，可沿用现有配置和附件上传许可做一次真实模型提案检查；不为本课启动实际命令。若没有做真实调用，就记录“模拟与界面通过，真实模型待验收”，不要混写。

## 15. 八题参考答案

以下为参考讲解，不代表学习者已经独立作答或掌握。

1. 固定模板把可表达的操作收窄到已知集合，程序和参数由可信代码生成；任意 shell 字符串会引入引用、转义、拼接和额外命令语义。
2. 参数数组保留每个参数的明确边界；展示字符串帮助人阅读。展示文本不能直接当 shell 执行数据，未来还须确定 Windows 下 npm 的启动方式。
3. 附件仅授权特定文件快照，虚拟路径不代表磁盘目录；父目录、共同路径、终端目录都没有经过独立目录选择和执行确认。第25课单文件写入确认不授权运行目录内程序。
4. typecheck 只是脚本名。package.json 可将它定义为任意程序，npm 还可能运行前后置脚本，造成文件修改、网络请求和子进程启动。
5. Markdown 是普通模型文本，不能证明工具被允许、参数被校验或主进程接受了提案。卡片需要完整成功轮次、唯一调用/结果配对及相符模板。
6. schema 向模型声明工具格式；运行时解析检查实际收到的不可信参数及磁盘记录；isToolAllowed 检查当前上下文是否允许这个工具。三者互不替代。
7. 重启可恢复消息、ToolRun 和提案说明，不能恢复附件内存授权、当前审查面板或命令执行许可；重新选中同名文件会生成新快照。
