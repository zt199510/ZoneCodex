## 1. 目标与前置检查

做出下面的效果：

1. 工具回答下的执行记录，保存重启后仍然能看到。
2. 同一会话、同一种工具模式连续提问时，下一轮收到上一轮完整的协议项。
3. 普通聊天继续使用原来的纯文本上下文。
4. 版本 1、版本 2 的旧记录先备份，再迁移为版本 3。
5. 失败、取消或中断的任务不会被恢复成正在运行，也不会在启动时重新执行工具。

## 2. 先分清“保存”和“续聊”

| 数据                            | 第十九课           | 第二十课           |
| ------------------------------- | ------------------ | ------------------ |
| 用户问题、最终回答、消息状态    | 保存               | 继续保存           |
| 工具执行记录 trace              | 页面内临时显示     | 终态时随会话保存   |
| 完整工具协议 items              | 只在本次循环内存在 | 成功终态时按轮保存 |
| 正在请求的连接、AbortController | 不保存             | 仍不保存           |
| 未完成任务自动执行              | 不支持             | 仍不支持           |

“恢复”有两种含义：恢复页面上的历史，和恢复一个仍在运行的进程。本课只实现前者；下一次由用户主动发送新问题，才会使用已保存的成功历史发起新请求。

工具执行记录是给人看的说明。协议历史则包含原始 `function_call`、`function_call_output`、助手消息、reasoning 项及原有 `phase` 等字段。不能根据 trace 或最终文字反向编造这些协议项。

从 Vue 经验理解：会话库相当于统一的响应式数据源；`toolActivity` 是请求期间的临时状态；消息区的数据由两者派生。不要再建一个与会话库重复、靠 watch/Effect 互相同步的“已保存历史 state”。

## 3. 本课采用的上下文规则

先选一个容易验证的明确规则：**只延续消息尾部连续、成功、模式一致的工具问答**。

例如下面的消息顺序：

```text
普通聊天 → 真实工具 A → 真实工具 B → 新的真实工具问题
                         ↑ 下一次携带 A、B 的完整协议
真实工具 A → 模拟工具 B → 新的真实工具问题
                         ↑ 不携带 A、B，从新问题开始
真实工具 A → 失败的真实工具 B → 新的真实工具问题
                              ↑ 失败中断连续链，从新问题开始
```

只是切换下拉框、没有发送消息，不产生问答，也不切断历史。切换会话后回来，历史由该会话自己的消息和工具轮次重新派生。重启默认仍是普通模式，必须重新选择对应工具模式才能续聊。

本课不混合模拟与真实协议，不把普通聊天消息转换成工具协议，不自动裁剪链中的某一项。超出上下文上限时提示新建会话、明确重新提问，保留原记录。更复杂的历史压缩留待以后。

## 5. 第一步：定义一轮工具历史

新增 `src/shared/agent-history.ts`，先写类型：

```ts
import type { AgentMode } from './agent'
import type { ChatMessage } from './conversation'

export type JsonValue =
  null | boolean | number | string | JsonValue[] | { [key: string]: JsonValue }

export type ProtocolItem = { [key: string]: JsonValue }

export type ToolRun = {
  requestId: string
  userId: string
  assistantId: string
  mode: AgentMode
  trace: string[]
  items: ProtocolItem[]
}
```

为什么没有再保存 status、prompt 和 answer？它们已经在对应的两条 ChatMessage 中，重复保存会出现“一边 complete，另一边 failed”的冲突。成功与否通过关联消息判断。

`items` 只保存这一轮新增的内容，从本轮 user 项开始，到本轮最后的助手回答结束。第二轮不能把第一轮再次存入自己的 items，否则第三次拼接时历史会重复。

约定：pending、failed、cancelled 的轮次，`items` 必须为空；trace 可以保留已收到的执行说明。只有两条关联消息都是 complete，才允许非空 items。

### 5.1 unknown 不能直接断言成 ProtocolItem[]

继续在新文件中实现以下函数。函数名也是后文接线约定：

```ts
// 实现练习：这里列出函数签名，不是可直接粘贴的函数实现。
// parseProtocolTurn(value: unknown): ProtocolItem[] | null
// parseToolRuns(value: unknown, messages: readonly ChatMessage[]): ToolRun[] | null
```

`parseProtocolTurn` 校验“一轮已成功完成的协议”，必须满足：

1. 是普通 JSON 对象数组；最多 160 项，序列化长度最多 128000 字符。递归 JSON 检查最大深度 30，拒绝 undefined、非有限数字、函数及非普通对象；序列化异常返回 null。
2. 第一项只允许本应用创建的 `{ role: 'user', content: string }`；问题非空且不超过 2000 字。后续不允许混入 user/system/developer 消息。
3. 支持的后续项为 `reasoning`、`function_call`、`function_call_output` 和 assistant `message`。其他类型本课拒绝，而不是悄悄删除。
4. function_call 的 name、arguments、call_id 按现有 tool-loop 的长度规则校验。本课只接受 `get_current_time`，arguments 必须是字符串；实际执行时仍重新检查参数。
5. 用 Set/Map 记录 call_id：调用不能重复；结果必须对应前面尚未返回结果的调用，不能孤立或重复；轮末不能留下未配对调用。
6. assistant message 的 content 必须为数组；本课支持 output_text，text 必须是字符串。refusal 不作为成功历史接受；未知内容类型拒绝。phase 缺失或为 commentary/final_answer；其他值拒绝。
7. 对齐本课串行循环：同一时刻最多一个未配对调用；有未配对调用时不能接受最终答案；最后一项必须是带有效最终文字的 assistant message，phase 缺失或为 final_answer。
8. reasoning 的 summary 必须是数组（其中每项为 summary_text 和字符串 text）；encrypted_content 如果存在必须是字符串。保留完整对象，不解释其加密内容。
9. 原始对象中的 id、status、annotations、phase、encrypted_content 以及其他 JSON 字段均原样保留，不用 `{ type, content }` 重新拼一个简化版本。校验通过后返回 JSON 深拷贝，避免共享可变引用。

本解析器是当前时间工具协议子集的校验，不声称覆盖 Responses 全部输出类型。服务返回新增类型时明确失败，之后再升级解析器与课程。

`parseToolRuns` 进一步检查业务关联：

- 是数组，单会话不超过 100 轮；requestId/assistantId/userId 都合法；requestId 不重复，同一条消息不能被多个工具轮次占用。
- 每轮 userId、assistantId 必须指向本会话内相邻的 user/assistant 消息，状态一致；轮次按消息顺序排列。
- mode 只能是 mock/live；trace 最多 30 条，每条最多 500 字符。
- complete 时调用 parseProtocolTurn；第一项 content 必须等于用户问题。将本轮所有最终 phase（缺失或 final_answer）的 output_text 按 tool-loop 相同规则拼成答案，与助手正文一致。本课循环遇到最终回答即结束，因此成功轮只会有最后一次模型响应提供最终正文。
- 非 complete 时 items 必须是空数组。不能把半轮调用链当成可续聊历史。

先完成这两个纯函数，再改存储；解析不通过必须报错，不能返回空历史覆盖原始文件。

## 6. 第二步：选择下一次发送的历史

在同一个文件追加下面的完整函数。它接收已经通过版本 3 校验的消息和轮次。

```ts
export function selectToolHistory(
  messages: readonly ChatMessage[],
  runs: readonly ToolRun[],
  mode: AgentMode
): ProtocolItem[] {
  const selected: ToolRun[] = []
  for (let index = messages.length - 1; index >= 1; index -= 2) {
    const assistant = messages[index]
    const user = messages[index - 1]
    const run = runs.find((item) => item.assistantId === assistant.id)
    if (
      assistant.role !== 'assistant' ||
      user.role !== 'user' ||
      assistant.status !== 'complete' ||
      user.status !== 'complete' ||
      !run ||
      run.userId !== user.id ||
      run.mode !== mode
    )
      break
    selected.unshift(run)
  }
  const items = selected.flatMap((run) => run.items)
  if (items.length > 300 || JSON.stringify(items).length > 64000) {
    throw new Error('工具上下文已达到本课上限，请新建会话并重新说明问题。')
  }
  return structuredClone(items)
}
```

这是“遇到断点就停”的规则，不是筛选出整个会话里所有成功工具轮次。不要改成 `runs.filter(status === complete)`，否则会绕过失败或普通聊天边界。

发送前调用，异常时显示提示并返回 false，保留草稿；这一步必须在 begin('generating') 和追加 pending 消息之前。

## 7. 第三步：会话库升级版本 3

在 `conversation-library.ts` 导入 ToolRun 与 parseToolRuns，把正式类型改为：

```ts
export type Conversation = {
  id: string
  title: string
  messages: ChatMessage[]
  toolRuns: ToolRun[]
}

export type ConversationLibrary = {
  version: 3
  activeConversationId: string | null
  conversations: Conversation[]
}
```

不要把原来的版本 2 校验直接改到无法读取旧数据。按以下顺序重构：

1. 将原 Conversation/ConversationLibrary 的版本 2 形状保留为内部 `ConversationV2`、`LibraryV2` 类型。
2. 原 parseLibrary 改名为 `parseLibraryV2`，只验证版本 2、返回 LibraryV2。原消息/ID/标题/全库数量限制保持不变。
3. 新 parseLibrary 只接受版本 3。先借用 parseLibraryV2 验证公共字段，再逐会话执行 parseToolRuns，重建带 toolRuns 的版本 3 返回值。
4. 版本 3 缺失 toolRuns 时判为损坏；只有迁移版本 1/2 时才填 `[]`。
5. 新增 migrateV2：旧库合法才为每个会话添加空 toolRuns，最后再交给新版 parseLibrary。
6. 原 migrateV1 先 parseSnapshot，保留旧消息、会话标题和提供的 conversationId，再通过 migrateV2 得到版本 3。保留原函数名，但更新返回类型。
7. readLibrary 按版本明确分支：3 → parseLibrary；2 → migrateV2；1 → migrateV1；未知版本 → null。

旧工具回答只有文字，迁移时不能为它伪造 call_id 或执行记录。界面可以继续显示旧回答，但它不参与本课协议续聊。

保留原来的 100 个会话、1000 条消息、正文合计 1000000 字符限制。新增全库协议 items 序列化合计不超过 2000000 字符，以及整个快照序列化 UTF-8 字节数不超过 8000000 的检查。共享层用 TextEncoder，主进程仍可用 Buffer.byteLength；两边比较相同的序列化结果。

注意存储使用 `JSON.stringify(library, null, 2)`：全库字节校验也用相同缩进，不能只计算紧凑 JSON。超限不截断密文、工具参数或工具结果。

## 8. 第四步：先备份，再迁移磁盘文件

修改 `conversation-store.ts`，仍使用同一个 conversation.json、串行队列和临时文件 rename，不另建第二套“工具历史数据库”。

当前 Existing 的 legacy 只有布尔值，需要改成源版本：

```ts
type Existing = {
  bytes: Buffer
  library: ConversationLibrary
  sourceVersion: 1 | 2 | 3
}
```

readExisting 中先识别合法版本 1/2/3，再调用 readLibrary。仅版本 1 需要生成迁移用 conversationId；其他版本传空字符串即可。非法版本与损坏内容仍抛错。

load 流程：

```text
读取原始字节 → 校验/纯数据迁移 → 恢复 pending 状态
  ├─ 原版本 1/2：wx 写原始字节备份 → 成功后写版本 3
  └─ 原版本 3：只有恢复结果发生变化才写回
最后返回实际保存成功的 snapshot
```

备份名使用 `conversation-v${saved.sourceVersion}-${randomUUID()}.bak`。保存的是 saved.bytes，不是重新序列化后的迁移对象。备份失败立即返回加载失败，原文件不得被迁移覆盖。

save 中将 `existing?.legacy` 检查改为“existing 存在且 sourceVersion 不是 3 时拒绝”，确保不能绕过 load 的备份步骤。

没有文件时返回 `{ version: 3, activeConversationId: null, conversations: [] }`。useConversation 的初始库也改为版本 3，新建会话必须加 toolRuns: []。不要遗漏这三处构造入口。

恢复 pending 时：原先 pending 消息变 failed 的逻辑保留；关联工具轮的 items 本来就必须为空，保持为空，trace 只保留已经保存的记录。两条关联消息一起变 failed；恢复后再次 parseLibrary 校验再写回。界面显示“本轮未完成，未自动续跑”。

本课仍在 generating 时暂停自动保存，所以突然刷新可能丢失本轮所有未保存内容；恢复 pending 的规则是处理磁盘上确实存在的 pending 数据，不代表新增了实时崩溃检查点。不要为了展示恢复效果取消生成期间的保存互斥。

## 9. 第五步：工具循环接收历史，返回本轮协议

### 9.1 成功结果增加 items

在 shared/agent.ts 用 type import 导入 ProtocolItem，成功分支改为：

```ts
| { status: 'done'; answer: string; trace: string[]; items: ProtocolItem[] }
```

失败和取消分支保持只有 trace（失败另有 error）。parseAgentResult 的 done 分支额外调用 parseProtocolTurn 校验 items，并要求 answer.trim() 非空且与协议中的最终文字一致。不能只改 TypeScript 类型、不改运行时解析。

agent-history.ts 引用 AgentMode 必须使用 `import type`，agent.ts 才能在运行时引用历史解析器而不形成运行时循环依赖。

### 9.2 修改 runToolLoop

保留原来前五个参数，末尾增加 `history: ProtocolItem[] = []`；返回类型改为 `Promise<{ answer: string; items: ProtocolItem[] }>`。

将初始化 input 替换为：

```ts
const input: unknown[] = [...structuredClone(history), { role: 'user', content: prompt }]
const turnStart = history.length
```

seenCalls 初始填入历史中全部 function_call 的 call_id，防止新响应重复旧调用 ID。只有本次 send 返回的 response.output 能触发 executeTimeTool，绝不能遍历整个 input 去执行历史调用。

循环内原样追加 response.output、function_call_output 的逻辑保留。最终成功处改为：

```ts
const items = parseProtocolTurn(input.slice(turnStart))
if (!items) throw new AgentError('本轮协议历史不完整或超过保存上限')
record('获得最终回答')
return { answer, items }
```

删除原位置重复的 record，保证完成记录只出现一次。128000 字符的运行输入上限仍保留，且在追加 output 和工具结果后、包括最终返回前也检查整个 input；不能只在下一轮开始时检查，否则最后一轮可能绕过上限。

历史是用于理解上下文的数据，工具调用上限仍是本次最多 3 次模型请求、2 次实际工具执行；旧历史不消耗本次计数，但旧 call_id 不能被新调用复用。

### 9.3 IPC 与 preload 一起改

AppAPI 的 startAgentPractice 追加可选参数，保留历史练习组件的三参数调用：

```ts
startAgentPractice: (
  requestId: string,
  prompt: string,
  mode: AgentMode,
  history?: ProtocolItem[]
) => Promise<AgentResult>
```

preload 参数默认 `history = []`，invoke 时作为第 4 个业务参数传入。主进程 handler 对应 `(event, id, prompt, mode, history: unknown = [])`。

主进程必须重新校验历史：空数组合法；非空数组按 user 项划分完整轮次，逐轮 parseProtocolTurn，并检查跨轮 call_id 不重复；总计最多 300 项、64000 字符。拒绝 system/developer、半轮调用、孤立结果和非法 JSON。把这个校验提取成 agent-history.ts 的 `parseToolHistory(value)`，供主进程入口复用。Renderer 的类型不能代替主进程校验。

通过后作为 runToolLoop 的第 6 个参数传入。成功结果改为 `{ status: 'done', answer: completed.answer, items: completed.items, trace }`。90 秒超时、窗口刷新取消、finally 清理和进度通道全部保留。

parseToolHistory 只验证协议结构；会话归属与模拟/真实模式由会话控制器选择和版本 3 关联校验保证。本课仍只有可信的应用页面入口，不把这个接口描述成任意第三方都能调用的安全服务。

## 10. 第六步：修正模拟响应的固定 call_id

当前 createMockResponse 每次使用 `call_mock_1`。有跨轮历史后，同一链中会重复，所以需要改。

在 tool-response.ts 从 node:crypto 导入 randomUUID，在 createMockResponse 的函数体里、返回异步函数之前创建：

```ts
const callId = `call_mock_${randomUUID()}`
```

原来返回的 call_id 和检查 function_call_output.call_id 的两处 `call_mock_1` 都改用 callId。每次任务创建一次，每次模型请求不能重新创建，否则同一轮调用和结果会对不上。

为了看见历史确实传入，可以在 step === 1 时统计 input 中的 user 项数量，在模拟最终回答中显示“收到 N 轮用户问题”。模拟仍固定查询香港，不能把这个计数演示说成模型已经理解“那换成 UTC 呢”。

真实模式仍使用原有 tools、store: false、include、phase 保留规则。不要把 tool_choice 永久改为 required：拿到工具结果之后也可能被迫继续调用，无法自然结束。本课不修改模型服务配置。

## 11. 第七步：终态一次性提交到会话库

截至 2026-09-16，本课第 6、7 项的正式前端接线已完成：发送时选择连续工具历史，工具轮开始时写入 pending 记录，结束时在同一次会话更新中提交消息与 `toolRuns`，由会话数据派生已保存的执行记录，并在发送前按全库预留本轮空间。下面的时序、第 12 节和“保存容量需要提前检查”仍作为代码核对标准；第 13 节的窗口验收尚未完成。

这是本课最重要的前端改动。消息和 toolRuns 必须在同一次 setSnapshot 更新里提交，不能先把消息设为 complete，另一个 Effect 再补协议。

在 useConversation 内新增稳定的会话更新函数：

```ts
const updateConversation = useCallback(
  (conversationId: string, update: (previous: Conversation) => Conversation): void => {
    setSnapshot((previous) => ({
      ...previous,
      conversations: previous.conversations.map((item) =>
        item.id === conversationId ? update(item) : item
      )
    }))
  },
  []
)
```

给 useModelStream 的 options 增加当前 `toolRuns` 和这个回调。已有 updateMessages 可保留给普通增量更新，但必须保持 useCallback 稳定，避免每次渲染都重建订阅并取消任务。

按下面时序接线：

1. 工具发送前执行 selectToolHistory，并捕获其深拷贝。连同 conversationId/requestId/userId/assistantId/mode 一起绑定本次任务，异步阶段不重新读当前会话。
2. 通过 begin 后，在一次 updateConversation 中追加两条 pending 消息和一条 ToolRun：`trace: []`、`items: []`、mode 为 mock/live。
3. 实时进度仍写临时 toolActivity，不逐条改快照。另在 active 上保存同样限长的 trace 副本，用于 invoke 异常时保留已经收到的说明。
4. startAgentPractice 的第 4 个参数传捕获的 history。
5. done：一次更新中将两条消息设为 complete、助手正文写入 answer、相应 ToolRun 的 trace/items 替换为 result.trace/result.items。
6. cancelled/error：一次更新中结束两条消息，并写 result.trace、items: []；error 保留原错误提示。
7. invoke 抛异常：两条消息 failed，工具轮保存 active 中已有的 trace、items: []，不能提交半轮协议。
8. 提交后删除该 assistantId 的临时记录，finally 中才清空 active 并 finish('generating')。

更新 ToolRun 时同时匹配 requestId 和 assistantId，更新会话时匹配发送时的 conversationId。终态回调仍先检查 activeRequest 的 requestId，避免迟到结果写入下一轮。

finishTurn 原来只改 messages。普通聊天可以继续用它；工具分支应改用同时更新消息与 ToolRun 的终态函数，不能两处同时结束同一轮。

### 保存容量需要提前检查

发送前除了原问题长度检查，还要检查会话轮次及全库容量。工具发送至少预留：2 条消息、1 条 ToolRun、正文 18000 字符（问题 2000 + 回答 16000）、协议 128000 字符、整库格式化 JSON 1000000 字节。已用量加预留量超限时返回 false，保留草稿并提示新建会话或整理记录。全库容量用全库快照检查，不能只看当前会话。

建议由 useConversation 在 send 包装函数中做容量检查，用控制器的独立错误状态展示提示；成功发送或切换时清除该提示。useModelStream 内负责本次历史长度检查。最终写入仍执行完整 parseLibrary，不能仅相信发送前的估算。即使发生保存失败，仍保留内存数据、dirty 和关闭保护，不能自动丢掉协议后假装保存成功。

## 12. 第八步：展示由持久记录和临时进度派生

useConversation 返回给 MessageList 的 toolActivity 改为派生值：

const savedActivity = Object.fromEntries(

复述提示：围绕“终态提交、按轮存储、完整回传、不自动重放”解释，不需要背函数名。遇到不会的题，带着对应的输入/输出例子提问。

收到，第 20 课你已完成。下面按这八道题逐一解释，重点理解“为什么这样设计”。

**1. trace、最终回答、完整协议历史分别给谁使用？为什么不能互相替代？**

- **trace：给用户查看执行过程。** 例如“开始查询时间 → 查询完成 → 获得最终回答”。
- **最终回答：给用户看结论。** 例如“香港现在是下午三点”。
- **完整协议历史：供程序在下一轮请求中回传给模型。** 包括用户问题、工具调用、工具结果、助手消息，以及需要保留的 reasoning、phase 等字段。

例如 trace 只写了“查询完成”，它没有完整保存调用参数、结果和 `call_id`。最终回答也可能只是工具结果的概括。

因此，**显示出执行记录，不代表模型收到完整历史；保存了最终文字，也不能据此还原原始协议。**

**2. 为什么 ToolRun 关联 userId / assistantId，却不重复保存 status 和 answer？**

因为对应的两条消息已经保存了状态、问题和答案。

`ToolRun` 通过 ID 找到它们，只补充工具专属的数据：

```text
用户消息：问题、状态
助手消息：答案、状态
ToolRun：关联两条消息的 ID、模式、trace、items
```

如果再保存一份答案，就可能出现：

```text
助手消息的答案：香港现在是 15:00
ToolRun 的答案：香港现在是 14:00
```

状态也可能一处 `complete`、另一处 `failed`。

**关联 ID 是为了知道“属于哪一轮”；不重复保存，是为了避免同一事实出现两个版本。**

**3. 为什么第二轮只保存新增 items？整个 input 都存下来会发生什么？**

设第一轮协议是 A，第二轮新增协议是 B。

第二轮运行结束时，完整 `input` 包含：

```text
A + B
```

正确保存：

```text
第一轮 items = A
第二轮 items = B
第三次发送的旧历史 = A + B
```

如果第二轮把整个 `input` 保存下来：

```text
第一轮 items = A
第二轮 items = A + B
第三次拼接 = A + A + B
```

第一轮重复了，里面的工具 `call_id` 也重复了，会造成校验失败，并浪费上下文空间。

**请求时需要拼接旧历史；保存时只保存本轮新增部分。**

**4. 为什么恢复历史不能重新执行旧 function_call？它与处理本次 response.output 有什么区别？**

历史里的 `function_call` 表示：**过去模型提出过这个调用，而且这段成功历史已经包含对应结果。**

本次 `response.output` 中的 `function_call` 表示：**模型刚刚提出了一个新调用，需要程序检查并执行。**

例如昨天查询时间，保存的结果是“昨天 15:00”。今天恢复历史时再执行，会得到今天的时间，破坏原来那轮问答的含义。将来有写入工具，还可能重复产生副作用。

所以：

```text
旧历史 → 回传给模型，帮助理解之前发生了什么
本次模型返回的新调用 → 校验后执行，追加本次结果
```

**读取记录不会触发执行。** 如果用户重新问“现在几点”，应由本次流程发起新的查询。

**5. 为什么消息 complete 和 ToolRun.items 必须在同一次快照更新中提交？**

因为它们一起描述“一轮成功完成的工具问答”。

分开更新，可能产生不合法的中间状态：

```text
先把消息改成 complete
但对应 items 还没有写进去
→ 消息说成功了，成功协议却不存在
```

反过来也不行：

```text
先写入成功 items
消息仍然是 pending
→ 未完成轮次却带着成功协议
```

这时如果发生校验或保存，就可能报错或写入不一致的数据。

因此要在一次状态更新中同时提交：

```text
消息状态和最终回答 + 对应 ToolRun 的 trace、items
```

这里的“原子更新”可以理解为：**其他逻辑看到的，要么是更新前的完整状态，要么是更新后的完整状态。**

**6. 为什么版本 2 可以迁移出空 toolRuns，却不能接受缺少 toolRuns 的版本 3？备份为什么必须在写新版本之前？**

版本号代表数据应该遵守的结构。

- **版本 2 本来就没有 `toolRuns`。** 迁移时补上 `[]`，表示旧记录没有保存工具协议。
- **版本 3 规定必须有 `toolRuns`。** 缺失意味着数据不符合约定，可能是文件损坏或保存代码遗漏字段。

如果版本 3 缺字段也自动填 `[]`，程序就可能把“历史丢了”误认为“从来没有历史”，随后覆盖原文件。

备份必须先完成，是因为写新版本会覆盖旧文件。先保留原始字节，迁移出问题才有恢复依据。

```text
读取并校验旧数据 → 成功备份原文件 → 写入新版本
```

**备份失败，就不能继续覆盖旧文件。**

**7. 停止、失败、刷新、正常保存重启分别能恢复哪些数据？哪些情况会中断连续工具上下文？**

先记住一个前提：**重启只能恢复已经成功写入磁盘的数据。**

| 情况                 | 能恢复什么                                             | 对后续工具上下文的影响                           |
| -------------------- | ------------------------------------------------------ | ------------------------------------------------ |
| 停止后保存成功       | 已提交的消息、`cancelled` 状态、已有 trace；`items=[]` | 停止轮次切断连续链                               |
| 失败后保存成功       | 已提交的消息、`failed` 状态、已有 trace；`items=[]`    | 失败轮次切断连续链                               |
| 生成中突然刷新       | 上一次成功保存的快照；当前未保存的一轮可能全部丢失     | 按实际恢复出的消息重新选历史                     |
| 成功完成并保存后重启 | 消息、trace、成功轮次的完整 items                      | 重新选相同工具模式后，可以继续符合规则的尾部历史 |

如果磁盘上确实存在 `pending` 消息，加载时要改成 `failed`，**不会恢复请求连接，也不会自动执行工具**。

连续工具历史的规则是：**从消息尾部往前找，只取连续、成功、同模式的工具问答；遇到断点就停。**

断点包括普通聊天、失败或取消的轮次，以及不同工具模式的问答。例如：

```text
真实工具 A 成功 → 普通聊天 → 真实工具 B 成功 → 新的真实工具问题
```

新问题只能携带 B，不能跨过普通聊天再拿 A。

仅仅切换下拉框而没有发送消息，不产生断点；保存重启本身也不产生断点。

**8. TypeScript 类型、运行时协议解析、会话 ID 归属、工具参数校验分别解决什么问题？只写类型为什么不够？**

它们负责不同层次：

| 检查             | 解决的问题                                                 |
| ---------------- | ---------------------------------------------------------- |
| TypeScript 类型  | 写代码时，字段和函数参数是否按约定使用                     |
| 运行时协议解析   | 实际读到的数据是否合法，调用和结果是否配对，是否超限       |
| 会话 ID 归属检查 | 这轮工具记录是否属于当前会话中的正确消息，是否串到其他会话 |
| 工具参数校验     | 即将执行的工具是否收到合法参数，例如时区是否有效           |

TypeScript 类型编译后会被移除，不能替你检查磁盘文件、IPC 参数或模型返回值。

例如：

```ts
const items = JSON.parse(text) as ProtocolItem[]
```

`as` 只是告诉类型检查器“把它当作这个类型”，**不会验证或转换实际数据**。即使 `text` 是 `"123"`，解析出来仍然是数字，不会变成数组。

因此，类型帮助你正确编写程序，运行时检查则负责确认程序实际收到的数据符合要求。
