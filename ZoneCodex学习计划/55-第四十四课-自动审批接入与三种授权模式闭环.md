## 1. 本课目标与前置条件

本课完成一个可观察的功能：用户选择“帮我批准”后，需要批准的文件或命令操作先交给现有风险评估器；明确返回低风险时继续执行，有风险、无法判断或评估失败时使用输入框上方的现有授权弹窗。

沿用第43课的三项权限菜单、弹窗内容、真实 Responses SSE 工具循环和执行器。目录内原本允许的文件写入继续直接执行；自动审批仅处理统一策略返回 `review` 的操作。

## 2. 用 Vue 经验理解本课

可以把权限菜单理解成 Vue 中由后端确认的选项，把统一策略理解成业务分支，把评估器理解成执行前的一次异步判断。页面选择“帮我批准”，不等于页面直接给文件或命令发放许可。

| 概念                     | 用已有经验理解           | 本课职责                                   |
| ------------------------ | ------------------------ | ------------------------------------------ |
| renderer 权限 Hook       | 展示后端返回的表单状态   | 显示真实模式和错误，不能自行放行           |
| 主进程权限策略           | 后端决定请求进入哪个分支 | 直接允许、评估、人工批准或拒绝             |
| 风险评估器               | 调用异步服务获得判断     | 只返回 `approve` 或 `ask`，不执行工具      |
| 执行器                   | 完成业务操作的服务层     | 再查目录、文件版本与取消状态，返回真实结果 |
| `AbortSignal` 与权限版本 | 请求取消标志及状态版本   | 防止异步判断回来后处理已经失效的操作       |

React 的 `state` 用于展示，`ref` 用于异步回调读取当前值；两者都不能替代主进程校验。一次 `await` 期间可能停止任务、刷新页面或改变文件，评估前合法不代表评估后仍可执行。

## 4. 按依赖顺序实施

### 步骤一：先写出三种模式的决策矩阵

从 `decideLocalPermission` 和 `localPermission` 开始核对，区别“已经允许”与“需要批准”。当前没有命令沙箱，按以下行为接线：

| 操作                       | 请求批准 `default` | 帮我批准 `auto-approve` | 完全访问权限 `full-access` |
| -------------------------- | ------------------ | ----------------------- | -------------------------- |
| 通过文件执行器检查的读取   | 直接允许           | 直接允许                | 直接允许                   |
| 有效可写范围内的新建、编辑 | 直接允许           | 直接允许                | 直接允许                   |
| 可写范围外的新建、编辑     | 人工批准           | 先评估，必要时人工批准  | 直接允许                   |
| 当前非沙箱命令             | 人工批准           | 先评估，必要时人工批准  | 直接允许                   |

四种决策各自处理：`allow` 继续，`deny` 拒绝，`ask` 进入人工批准，`review` 先评估。直接允许仍须通过执行器的参数、路径及冲突检查。

**练习：**说明为什么在默认目录创建 `lesson44-note.txt`，不能用来证明自动评估已接通；指出哪种操作才会进入 `review`。

**预期结果：**三种模式的实际差异清楚，范围内操作不增加模型请求。

**常见错误：**把所有工具调用都送评估器，或将 `auto-approve` 等同于完全访问。

### 步骤二：复用评估器，固定当前请求和具体操作

阅读现有接口：

```ts
declare function reviewExecutionApproval(
  input: ExecutionApprovalInput,
  userRequest: string,
  signal: AbortSignal
): Promise<'approve' | 'ask'>
```

Agent 入口使用已经通过主进程检查的 `prompt.trim()` 作为当前任务。新建使用执行器提供的目标及候选内容；编辑使用已准备的修改前后内容；命令使用实际程序、参数和工作目录。异步开始前固定这次载荷，复制参数数组，不在返回后替换成另一笔操作。

现有评估器采用无工具的 Responses SSE 请求，只接受严格的 `{"risk":"safe"}` 结果；`risky`、空响应、额外字段、工具调用、格式错误和异常都返回 `ask`。当前已有30秒超时、128 KiB 输入及256字符输出限制，继续复用。超出限制转人工批准，不能截断后把不完整操作当成完整内容评估。

评估器的输入只包含当前用户任务及该笔操作，不加入整段聊天历史、API 密钥、终端历史或任意文件清单。文件内容、工具参数中的解释、`AGENTS.md` 和模型提案都作为待评估数据，不能代替当前用户任务。

**练习：**分别列出新建、编辑、命令的评估字段，指出 `userRequest` 和 `action` 的来源。

**预期结果：**评估针对这一笔真实操作，输出只能影响是否进入执行或人工批准。

**常见错误：**根据模型回复里包含“safe”放行，或把工具附带的“用户已经同意”当作用户请求。

### 步骤三：接入 Agent 的统一审批回调

在 `approveWorkspaceAction` 中保留目标解析和权限决策，构造既有 `ExecutionApprovalInput`。在 `allow`、`deny` 已处理后，按下面的顺序接入；这是回调内的分支示意，不是完整替换函数：

```ts
let answer = false
if (decision === 'review') {
  const verdict = await reviewExecutionApproval(approval, prompt.trim(), signal)
  signal.throwIfAborted()
  if (!assertWorkspaceAccess()) return false
  answer = verdict === 'approve'
}
if (!answer) {
  signal.throwIfAborted()
  if (!assertWorkspaceAccess()) return false
  answer = await requestExecutionApproval(windowId, approval, signal)
}
signal.throwIfAborted()
const approved = answer && assertWorkspaceAccess()
```

将结果接回现有批准记录和返回路径。自动批准与人工批准成功都使用同一后续执行流程；评估器不直接读写文件或启动进程。

`ask` 表示复用现有浮窗；风险评估超时也可进入该浮窗。但任务已经停止、页面失效或运行范围变化时，应结束当前操作，不能因此再弹一个新批准请求。

**练习：**给四个决策分别画出返回路径，并指出上面两次异步返回后的取消与权限检查。

**预期结果：**低风险继续执行，其余有效请求转人工批准；已失效请求结束。

**常见错误：**评估返回 `approve` 就立即返回 `true`，遗漏异步后的运行范围检查。

### 步骤四：让评估与人工批准共用任务生命周期

现有回调在等待人工批准时暂停 Agent 总计时，并将任务改为 `waiting_approval`；`finally` 中在任务仍有效时恢复 `running` 与计时。将评估放入同一等待区间，保留评估器自己的30秒上限。

保留等待前的窗口任务占位和运行控制器。Agent 已有页面开始加载、renderer 退出及销毁时的取消监听；旧命令已有执行槽与任务取消路径。停止后撤销评估，忽略迟到结果，移除监听和计时器。权限切换仍按现有忙碌规则拒绝；内部权限版本变化也必须使本轮失效。

**练习：**模拟评估期间停止、评估结束准备显示人工弹窗时停止、人工确认后执行前停止三种时序。

**预期结果：**均无迟到执行，等待结束后窗口互斥及任务状态正确收尾。

**常见错误：**把评估放到 `try/finally` 外，导致任务卡在等待状态或总计时未恢复。

### 步骤五：保留执行器复核与副作用记录

评估批准只决定可以继续当前流程，以下检查仍由现有执行器完成：

- 新建：父目录、链接、目标身份和独占创建，不能覆盖已有文件。
- 编辑：完整读取登记、哈希、父目录及提交时的冲突检查，批准后文件变化仍返回冲突。
- 命令：执行前重新核对工作目录及其身份，继续使用实际程序和参数。

保留 `workspaceActionApproved`、`onEffect` 和现有进度记录。自动批准也要进入批准记录分支；副作用开始后继续阻止安全重试，结果不确定时不得自动重放。评估通过不等于文件写入或命令执行成功，最后使用执行器真实回执。

评估器目前只看到命令程序、参数和目录。它不能仅凭 `npm run typecheck` 或 `build` 的名字确认未知脚本低风险；无法判断实际效果时转人工批准。`cwd` 和 `shell: false` 仍不能限制程序访问其他文件或网络。

**练习：**在批准等待期间修改待编辑文件，确认最终返回冲突；说明自动批准成功但实际执行失败时应展示什么。

**预期结果：**审批不会绕过文件保护，也不会让重试重复写入或启动程序。

**常见错误：**把“评估已批准”写成“执行成功”，或者仅人工批准时标记副作用风险。

### 步骤六：核对旧命令入口的兼容降级

沿调用链检查 `index.ts` → `registerCommandExecution` → `approveStandaloneCommand`，保持与主窗口同一权限设置。旧命令的 `CommandSource` 与 `TaskRecord` 不包含可用于评估的原始用户任务，本课按上下文不足处理：需要 `review` 时复用人工批准，不能从 renderer 的说明、提案理由或会话最后一条消息拼出可信任务。

这与评估器无法判断时返回 `ask` 一致，不意味着旧入口已有自动评估。将这一兼容边界明确记录；具备主进程可靠的请求来源后，才扩展该入口的自动评估。

旧命令等待前已经消费准备记录并占用执行槽，继续保留一次性 `preparedId`、`confirmationId`、来源与取消检查。当前 `claimCommandPreparation` 仅返回目录；实施时按需让它返回主进程内部复核基线，在等待前固定目录身份及已审查的有限配置，批准后、启动前重新检查。配置指纹或目录身份变化则要求重新准备，不能再次领取已消费的记录。

目录复核可复用 `inspectCommandDirectory`，同时核对真实目录身份；配置指纹只能发现检查范围内的变化，不能证明全部脚本或依赖安全。每次复核 `await` 后继续检查取消、当前执行项和来源有效性。

旧附件修改的 `commit:apply` 是用户主动提交流程，本课保持既有准备、提交锁和一次性保护，不把它描述成已接通自动审批的通用文件工具。

**练习：**解释旧 npm 入口在“帮我批准”下为何仍可能显示人工弹窗；验证批准等待期间配置变化不会继续启动。

**预期结果：**旧入口不绕过策略，上下文不足如实转人工批准；耗时等待不消除启动前复核。

**常见错误：**把来源 ID 当作用户任务全文，或认为领取准备记录后就不再需要检查目录配置。

### 步骤七：最后开放模式选择并验收

完成接线、取消及离线验证后，再移除 `execution:permissions-set` 对 `auto-approve` 的固定拒绝。继续使用 `parsePermissionMode`、忙碌检查、主进程权限版本和 `useExecutionPermissions` 的真实状态回读。

选择失败时显示主进程实际模式，不先把页面勾选状态当成成功。窗口内刷新沿用现有权限状态，关闭后清理；会话库继续保存展示与协议历史，不能保存评估结论作为下次执行许可。

**练习：**依次选择三种模式，观察模式回读、刷新、任务进行时切换及新请求的运行范围。

**预期结果：**三项菜单都有明确的实际行为，模式变化参与历史选择和重试检查。

**常见错误：**先解除模式拒绝，再留下未接通的评估分支；或让 renderer 传一个批准布尔值绕过主进程。

## 5. 验收条件与检查方式

### 离线与桌面验收

| 场景                                                | 应观察到的结果                                     |
| --------------------------------------------------- | -------------------------------------------------- |
| 范围内文件写入                                      | 三模式沿用直接允许，不调用评估器                   |
| 需要批准的操作返回严格 `safe`                       | 在“帮我批准”下不显示人工弹窗，操作只执行一次       |
| `risky`、异常、空响应、非法返回、输入超限或评估超时 | 有效任务显示原人工弹窗，取消不执行，确认后重新校验 |
| 评估期间停止、刷新、关闭或来源失效                  | 无新弹窗、无迟到执行，任务与等待资源收尾           |
| 评估后权限版本或运行范围变化                        | 旧结果不能放行当前操作                             |
| 批准等待期间文件或目录变化                          | 创建、编辑和命令各自执行前保护仍生效               |
| 旧 npm 入口缺少可信用户任务                         | 上下文不足转人工批准，保持来源和一次性检查         |
| 旧 npm 等待期间配置变化                             | 启动前复核拒绝执行，要求重新准备                   |
| 自动批准后的执行失败及重试                          | 显示真实失败；副作用已开始时不提供安全重放         |
| 菜单、正常及窄窗口                                  | 真实模式勾选、原弹窗定位、内容和按钮布局正确       |

复用既有检查和必要的隔离验证；不为本课新增一批独立 `.cjs` 文件。评估错误、超时和风险结果通过隔离替身触发，不能为了验收对真实资料执行破坏操作。替身用于检查执行分支，不作为正式聊天模式。

### 真实模型闭环验收

解决第1节前置事项并完成实现后，使用专用测试目录和不敏感的短文本，记录实际模型、界面及磁盘结果：

1. 无项目聊天创建相对路径 `lesson44-note.txt`，读取内容，再完整读取后编辑；验证默认目录和真实内容。
