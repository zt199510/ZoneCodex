## 1. 目标与范围

本课完成一个可观察的小功能：用户审查 ready 面板后点击“确认写入此文件”，主进程一次性领取准备记录，再次检查磁盘，保存原始字节备份，提交精确候选内容，显示实际结果并使旧附件授权失效。

## 5. 练习一：设计一次性的确认请求

提交请求只携带用于核对的 ID，不再传路径、候选正文、候选字节或备份位置。例如：

```ts
type CommitRequest = {
  conversationId: string
  snapshotId: string
  preparationId: string
  checkId: string
  commitId: string
}
```

`checkId` 对应第24课的检查轮次；`commitId` 是本次提交动作的新 ID。严格拒绝数组、访问器、未知字段、非法或超长 ID。检查所属 BrowserWindow 与 main frame，使用 `captureProjectAccess` 核对现有授权。

增加主进程内部的领取方法，核对窗口、会话、快照、preparationId、checkId、过期时间，以及记录基线确实来自当前授权快照。通过后，在第一个 await 之前同步登记提交任务、取走记录并清除定时器。不要暴露整个 records Map，也不要仅靠定时器判断是否过期。

领取失败不接触目标；领取成功后，即使提交失败或取消，旧 preparationId 也不能重试。需要重新检查并由用户重新确认。requestId/callId 仍只是消息关联信息，不是模型调用本地写入的授权证明。

预期：并发提交同一准备 ID，最多只有一次进入文件服务；伪造其他窗口、会话或快照全部失败。

## 6. 练习二：先定义失败和取消的含义

建议内部阶段为 validating → staging → replacing → verifying → finished。前两个阶段尚未请求替换目标，取消可以终止；进入 replacing 并发出文件替换请求后，不再承诺取消能阻止写入。

结果至少区分以下语义，可自行设计字段，但必须写严格解析器：

| 结果 | 准确含义 |
|---|---|
| applied | 替换请求成功，提交后的有限读取确认目标身份与候选字节；只代表核验时的状态 |
| conflict | 提交前发现磁盘/身份变化，本次没有替换目标 |
| cancelled | 在发出替换请求前完成取消，本次没有替换目标 |
| error | 参数、授权、备份或暂存等阶段失败，明确记录未尝试替换 |
| uncertain | 已尝试替换，但无法确认最终磁盘状态；需要保留备份并人工检查 |

所有返回值包含本次 commitId 和上下文归属；错误有界，不直接把包含绝对路径的系统异常发给模型或聊天历史。备份通过不透明 recoveryId、文件名等有限信息标识，真实路径留在主进程。IPC 拒绝/断连时前端显示“未收到提交结果，请检查文件”，不能默认显示“未写入”。

先画出自己的阶段转换，再实现文件操作。不要写一个总 catch，把所有错误都转换成“原文件未变”。

## 7. 练习三：备份与暂存精确字节

本课选择“同目录暂存候选，再替换目标”的方案。避免先以 `w` 打开源文件，因为它会立即截断内容；也不要先删除目标再 rename。

按以下顺序练习：

1. 从领取记录取得可信基线和候选；重新校验原文、候选上限及编码策略。需要重算时，重算字节必须与已确认的 candidateBytes 完全一致。
2. 复用现有逐级路径、链接、普通文件、非硬链接和有界读取检查；将当前文件身份与字节和准备记录基线比较。不同则 conflict，不能自动更新基线继续提交。
3. 在验证过的目标父目录中，用随机 ID 派生本次专用备份名和临时名，例如 `.zonecodex-<id>.bak`、`.zonecodex-<id>.tmp`。名称只由主进程生成，用 `wx` 独占创建；碰撞则换新 ID 或失败，不覆盖已有文件。
4. 将基线 originalBytes 写入备份；将已确认 candidateBytes 写入临时文件。若使用低层 write，处理短写，直到全部字节写完。空候选同样处理，带 BOM 的空正文应为 3 字节。
5. 对两份文件执行 sync、关闭，再有限读取核对长度和字节。备份失败、候选校验失败或任何无法确认都不得替换目标。
6. 记录本次创建文件的身份。再次检查父目录和临时文件没有变成链接、硬链接或其他对象。finally 清理时只能操作本次明确拥有且身份匹配的临时文件；清理失败单独记录，不掩盖提交结果。

备份保存的是“用户审查的基线版本”，不是对最后一瞬间外部磁盘版本的保证。保留完整备份，不在成功后自动删除。不要把备份加入附件或发送给模型，也不要递归清理目标目录。

本课只对练习文件的内容字节负责。普通 rename 替换可能改变 inode、权限继承和其他元数据；无法保持所需文件属性时应拒绝，而不是宣称保留所有属性。

预期：模拟磁盘满、备份失败和临时文件短写，目标均不被本功能修改；基线为 BOM/CRLF 时，备份与候选都保持各自精确字节。

## 8. 练习四：最后复核与实际提交

备份和暂存耗时也可能让磁盘变化，因此在它们完成后再检查一次目标。最终顺序为：

```text
重新读取目标并核对身份/原始字节
→ 核对窗口、快照授权、任务身份与取消状态
→ 同步切换为 replacing，立即发起同目录 rename
→ 替换结果与目标的有界核验
→ 记录终态，清除旧授权，释放任务
```

第二次复核不得只看 size 或 mtime。读取完成后再次核对当前授权仍是捕获的快照；在最终授权检查和发出 rename 之间，不安排无关的异步工作。提交核验需要将目标与暂存文件身份、候选字节比较，不能拿已经被替换的原始 inode 判断“成功后仍是原文件”。

若 Windows 上目标被编辑器占用导致 rename 失败，不退化为“删除目标再重试”或“直接覆盖”。已发出替换请求但最终状态无法可靠分类时，按 uncertain 保留证据。

### 本课必须理解的并发边界

Node 的普通 `fs.rename` 没有“仅当目标还是这些字节时才替换”的参数。即使文件系统提供单次 rename 的原子可见性，它也不是对外部编辑器的原子比较并替换。

例如：最后复核读到 A → 编辑器保存 B → 本程序 rename 候选 C。B 仍可能被覆盖，而且备份可能只有 A。增加一次检查只能缩短窗口，不能消灭窗口；进程内 Map 锁和自建 lock 文件也不能约束不配合的编辑器。

因此本课是在受控副本上的有限提交练习。若产品必须保证绝不覆盖任意外部并发修改，应拒绝在当前能力下给出该保证，另行设计原生平台锁、协作写入协议或不同的输出方式。不要靠“先 stat 再 rename”推导零风险。

`sync` 也不等于整个多文件操作形成事务。断电、进程被杀或目录项持久化不足时可能只有备份、临时文件或目标中的一部分状态；本课不承诺跨崩溃自动恢复。

## 9. 练习五：按阶段处理失败与恢复

| 出错位置 | 本课处理 |
|---|---|
| 领取前 | 拒绝请求，不创建任何文件 |
| 备份/暂存/最后复核阶段 | 不替换目标；清理身份匹配的临时文件，保留已完整写好的备份并说明情况 |
| 已发起替换但收到错误或核验失败 | 保留备份，记录 uncertain；不盲目覆盖目标来“回滚” |
| 替换和核验成功，但 IPC 断开 | 磁盘可能已经提交；不要重复执行，客户端按未知结果处理 |
| 进程中断或断电 | 备份供人工检查；本课无自动恢复事务，不自动重放旧 ID |

失败恢复练习先在测试目录中完成：对比当前目标、备份和暂存候选，明确哪份是原始基线；将备份复制为一个新的恢复副本并核对字节。恢复副本独占创建，不能无提示覆盖当前目标。

如果要把恢复副本再覆盖回目标，需要一次新的具体审查、当前磁盘基线和用户确认，不能复用本次失败的 preparationId。即使覆盖前再比较候选，也仍然存在同样的外部并发窗口。本课不提供“一键无条件回滚”按钮。

正常结束时可通过限定的主进程动作定位本次备份，例如按 recoveryId 调用 `shell.showItemInFolder`；不接受 renderer 传任意路径。进程重启后的备份可由用户在练习目录中人工识别，备份名带本次 ID。完整持久化恢复日志与管理界面留到后续，不混入聊天库版本 4。

预期：恢复操作能证明原始字节可找回，又不会在异常处理时覆盖用户后来编辑的内容。

## 10. 练习六：提交生命周期与授权失效

renderer 增加独立的 `committing` 操作值，检查所有依据 Operation 分支的地方。提交期间禁用重复确认、发送、文件选择/移除/主动撤销、会话切换以及聊天保存；保存聊天不应把源文件提交描述成已保存聊天。

主进程同样互斥：Agent、准备、选择和提交接口互相检查；同一窗口只能有一个提交任务。如存在多个窗口，对相同真实文件身份也应串行拒绝本应用内的重叠提交。这里的锁只是任务协调，不新增文件授权，也不用于替代真实操作路径。

窗口关闭在 renderer 和 main 两侧均检查提交状态，包括 `window:finish-close` 的 allow 分支；不能让伪造的关闭许可越过主进程占用。

强制刷新、销毁或授权撤销发生时：

- replacing 之前：请求取消，等待本次清理 finally 后释放占用，旧页面不得接收迟到结果。
- replacing 已开始：不释放占用、不声称回滚成功；只抑制发往旧页面的结果，主进程继续完成核验和清理。进程被强制终止则进入上一节的人工恢复边界。
- `cleanupChangePreparation` 只能删除未领取的准备记录；领取后的副本由提交任务负责，过期定时器与旧 Hook 的取消不能中途销毁它。

本课采用保守策略：有效领取后的终态都撤销该窗口对应的整个旧快照授权，并清理前端 pendingSelection/contextSelection；其他附件也需要重新选择。非法请求不得撤销别人的授权。回调触发撤销时避免递归取消已进入终态的提交任务。

成功回执应独立于 preparation 状态保存，先在主进程完成终态和授权清理，再返回结果；前端上下文清空不能误删成功说明，也不能把旧回执显示到另一会话。仍然保留原消息建议为历史阅读内容，但它已无当前授权，不能再次提交。

## 11. 练习七：具体确认面板

只在当前有效 ready 面板显示“确认写入此文件”。继续展示文件名、附件别名、差异、编码换行、预计字节数，并明确告知会修改该文件且保留基线备份；空候选要提示正文将被清空。

点击时重新核对会话、快照、来源、checkId、preparationId 和空闲状态，取得独占操作后发送有限请求。提交过程中显示“正在提交，请等待结果”，不提前显示成功。

进入提交后，“关闭/返回审查/Escape”不能再沿用第24课立即释放占用的逻辑：请求取消并等待主进程答复；已进入替换阶段则提示正在完成收尾。结果 uncertain 时引导检查文件与备份，不能把按钮改成无条件重试。

成功显示“已提交，旧附件授权已清除，请重新选择文件后继续”，并提供本次备份定位信息。不要将系统反馈伪装成模型声称已写入，也不要改写历史工具结果为提交成功。

## 12. 验收清单

沿用现有离线检查及 Electron 工作台脚本，不新增测试框架。文件操作只能发生在本次创建、路径已核实的隔离目录内；故障注入使用内部文件服务适配器，不在正式 IPC 暴露“跳过检查”参数。

| 场景 | 必须观察到的结果 |
|---|---|
| ready 后明确确认 | 一次提交，目标为精确候选，备份为精确基线 |
| 双击或重复发送同一 ID | 最多一次领取和替换，第二次拒绝 |
| ID 过期或窗口/会话/快照不匹配 | 不写目标，不影响其他记录 |
| ready 后外部编辑，包括同长度、BOM、LF/CRLF 变化 | conflict，不自动接受新基线 |
| 备份完成后、最后复核前编辑目标 | conflict，目标保持外部版本 |
| 最后复核后、rename 前注入外部修改 | 记录残留竞态，不能标记为已保证阻止覆盖 |
| 路径删除、替换、变链接或硬链接 | 提交前能发现时拒绝，不换同名文件继续 |
| 备份/暂存失败、短写、磁盘满、rename 失败 | 按阶段分类，检查目标和备份实际字节 |
| 空正文、BOM、CRLF、末尾无换行 | 与第24课确认的字节一致 |
| 检查中取消与已发起替换后取消 | 前者不提交；后者收尾并报告实际结果 |
| 刷新、窗口销毁、IPC 响应丢失 | 不产生新页面迟到结果，不盲目重试或回滚 |
| 成功、失败或取消后 | 已领取记录不可重用，旧授权清除，任务最终释放 |
| 人工恢复副本 | 能找回原始字节，当前目标不被恢复练习覆盖 |

运行 `npm run typecheck`、`npm run build`、适配后的 `npm run check:workspace` 和相关 lint。实际观察 680×560 窗口下确认按钮、差异滚动、错误提示与关闭保护。把故障注入结果和真实平台行为分别记录；无需为每个磁盘用例重复调用模型。
