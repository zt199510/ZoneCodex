# 第三十二课：任务生命周期与可恢复后台执行

创建日期：2026-09-25。状态：基础实现已完成，桌面生命周期验收待完成。

前一课：[第三十一课：工作区、项目指令与任务状态基础](41-第三十一课-工作区项目指令与任务状态.md)。

本课先把第31课的当前窗口状态推进为可观察、可恢复的任务记录。这里的“可恢复”指刷新或窗口重载后恢复任务展示和结果，不指恢复一个已经失去上下文的 Node 进程。当前仍不进入并发 Agent、自动批准、SSH、MCP 或任意命令。

## 1. 本课目标

本课完成一个小而完整的任务生命周期基础：

1. 主进程成为任务生命周期的唯一权威，负责创建、推进、取消和收尾。
2. 会话保存可展示的任务记录和提案结果，不保存运行时句柄或一次性授权。
3. 页面刷新、窗口重载和会话切换后，可以恢复任务卡片、状态和最终结果。
4. 运行中的任务、等待批准的任务和已经失效的权限不会被伪装成可继续执行。
5. 取消、失败、超时、窗口销毁和权限撤销都能释放订阅、计时器、进程引用和短期许可。

目标状态分成两层：

```text
任务记录：created → running → waiting_approval → completed
                                      ├──────────→ cancelled
                                      ├──────────→ failed
                                      └──────────→ timed_out

权限状态：unscoped → scoped → expired / revoked
```

`waiting_approval` 不代表进程正在运行。等待用户确认时，进程数必须为 0；确认之后才可以创建执行句柄。

## 2. 为什么第31课之后要先做任务生命周期

第31课已经把工作区、项目指令、文件快照和执行许可分开，但当前请求状态仍主要存在于 Hook 和短期主进程 Map 中。页面一刷新，用户可能还能看到历史消息，却无法知道上一项任务是完成、取消还是在等待批准。

第32课先补齐“任务记录”和“运行时句柄”的区别：

| 可持久化的任务记录 | 只能存在于主进程内存的运行时句柄 |
|---|---|
| `taskId`、`requestId`、`conversationId` | `AbortController` |
| 任务种类和状态 | 子进程或执行器引用 |
| 创建、开始、结束时间 | 窗口归属和事件监听器 |
| 展示结果和错误摘要 | `preparedId`、`confirmationId`、目录 grant |

记录可以帮助页面恢复展示，不能把旧记录变成新的执行许可。刷新后发现旧任务仍是 `running`，应把它收尾为明确的 `interrupted`/`failed`/`cancelled` 展示状态，或要求用户重新发起；不能假设旧进程仍可被当前页面控制。

## 3. Vue 经验对应

| Vue 习惯 | 本课 React/TypeScript 设计 |
|---|---|
| Pinia 中保存任务列表 | 会话库保存受限的 `TaskRecord[]`，主进程维护运行时任务 Map |
| `watch(route)` 取消请求 | 会话切换事件显式调用取消和清理，不把 Effect 当成业务命令 |
| `computed` 显示状态文字 | 从 `TaskRecord.status` 派生按钮和状态文本 |
| 页面重新挂载继续显示列表 | 从持久化快照恢复记录，但重新建立订阅，不恢复旧执行许可 |
| `onUnmounted` 清理 | 窗口销毁和主进程清理函数释放句柄、计时器和监听器 |

任务记录、运行时句柄、目录授权和消息历史是四种数据。它们不能合并成一个“可恢复任务对象”。

## 5. 实现步骤

### 第一步：定义任务记录协议

在共享文件中定义最小的可持久化记录，例如：

```ts
type TaskKind = 'chat' | 'agent' | 'command'

type TaskRecord = {
  taskId: string
  requestId: string
  conversationId: string
  kind: TaskKind
  status: TaskStatus | 'timed_out' | 'interrupted'
  createdAt: string
  startedAt: string | null
  finishedAt: string | null
  result: string | null
  error: string | null
}
```

要求：

- 所有 ID、时间、状态、结果和错误都要做运行时解析，不只依赖 TypeScript。
- 结果和错误限制长度，避免任务记录无限增长。
- `TaskRecord` 不得包含 `AbortController`、进程对象、回调、目录路径授权、grant、`preparedId` 或 `confirmationId`。
- `requestId` 防止迟到事件写入另一轮，`taskId` 标识可展示的生命周期记录；二者不能混用。
- 任务记录写入会话前，先确认会话 ID 仍然属于当前记录。

### 第二步：在主进程建立生命周期权威

增加主进程内存结构：

```ts
type RuntimeTask = {
  record: TaskRecord
  controller: AbortController
  windowId: number
  timer: NodeJS.Timeout | null
}
```

页面只能请求“创建、取消、重新发起”这类动作，不能直接改变任务状态。主进程负责：

1. 创建唯一 `taskId`，拒绝重复的 `requestId`。
2. 在真正开始工作前发布 `created` 或 `running`。
3. 命令提案产生后进入 `waiting_approval`，此时不创建子进程。
4. 用户确认通过主进程的现有一次性准备接口后，才进入 `running`。
5. 所有终态统一经过一个收尾函数，清理计时器、监听器、任务 Map 和短期许可。

状态事件至少包含 `taskId`、`requestId`、状态和必要的结果摘要。页面收到事件时，必须先检查会话和任务 ID，再更新当前视图。

### 第三步：接入取消、失败和超时

给每个运行时任务设置明确的取消和超时边界：

- 取消是请求，不是立即把页面文字改成完成；收到主进程终态后才结束任务。
- 超时要先停止底层工作，再发布 `timed_out`；不能只在界面显示“超时”。
- 启动失败、非零退出、网络异常和主进程异常都进入 `failed`，错误摘要可展示但不写入敏感信息。
- `finally` 必须释放计时器、事件订阅、AbortController 关联和窗口任务引用。
- 旧 `requestId` 的迟到输出不能改变已经结束的记录。

### 第四步：处理刷新、窗口销毁和会话切换

页面重新加载时：

1. 只从会话库恢复允许保存的 `TaskRecord` 和提案展示。
2. 对没有对应运行时句柄的 `running` 或 `waiting_approval` 记录做明确收尾或标记中断。
3. 不恢复旧的 `preparedId`、`confirmationId`、grant、AbortController 或进程引用。
4. 需要继续执行时，创建新的 `taskId`，重新检查工作区、快照、指令指纹和权限，并重新取得用户确认。

窗口销毁和切换会话时：

- 取消属于旧窗口/旧会话的运行时任务。
- 移除旧任务的事件监听，阻止迟到事件污染新会话。
- 清理命令准备、文件预览、审查面板和一次性许可。
- 只保留可解释的终态或中断记录，不留下可领取的旧准备记录。

### 第五步：接入页面显示

工作台至少显示：

- 当前任务的状态和更新时间。
- 等待批准时的明确文字，且不显示“正在执行”或进程输出。
- 完成、取消、失败、超时和中断的不同结果。
- 刷新后恢复的历史任务卡片与“重新发起”入口；重新发起必须走新任务和新授权。

按钮状态由任务状态和权限状态共同决定。关闭审查面板不等于取消任务，也不等于批准任务。

## 6. 常见错误

### 把任务记录当作运行句柄

JSON 中保存一个 `running` 状态，不代表 Node 进程仍存在。页面恢复后必须重新确认运行时句柄和权限。

### 让 renderer 直接推进状态

renderer 可以发起取消和确认请求，但不能自行把任务改成完成或执行中。否则迟到事件和重复点击会产生不一致历史。

### 用 requestId 代替 taskId

请求 ID 用于过滤一次请求的事件，任务 ID 用于关联整个可展示生命周期。重试应创建新的任务 ID，不能覆盖旧任务。

### 等待批准时启动进程

提案卡片和准备记录都不等于执行。等待批准阶段必须保持进程数为 0。

### 刷新后恢复 preparedId

一次性许可属于主进程短期状态。刷新只能恢复“曾经有一个待确认任务”的展示，不能恢复点击执行的资格。

### 只清理界面订阅

卸载页面不等于停止主进程任务。必须同时取消底层工作并释放计时器、进程、Map 和窗口监听器。

## 7. 验收场景

| 场景 | 必须观察 |
|---|---|
| 正常完成 | 任务进入 `completed`，结果可恢复，资源已释放 |
| 用户取消 | 取消后不再追加输出，最终状态为 `cancelled` |
| 启动失败或非零退出 | 状态为 `failed`，错误可见，后续可新建任务 |
| 超时 | 底层工作停止，状态为 `timed_out`，没有残留计时器或进程 |
| 等待批准 | 状态为 `waiting_approval`，进程数为 0 |
| 重复 requestId | 第二次请求被拒绝，不创建第二个运行时任务 |
| 刷新页面 | 恢复任务记录和提案展示，不恢复 grant/prepared/confirmation |
| 切换会话 | 旧任务取消或明确收尾，迟到事件不污染新会话 |
| 撤销工作区 | 运行任务被取消，旧文件快照和命令准备不可领取 |
| 窗口销毁 | 无孤儿进程、计时器和事件订阅 |
| 重新发起 | 使用新的 taskId/requestId，并重新取得当前权限 |

入口拦截继续确认：不做跨重启进程恢复，不并发运行多个 Agent，不自动批准，不加入 SSH、MCP、命令队列或任意命令。
