## 1. 目标与范围

完成后的过程：

1. 添加自己创建的小文件 `greet.ts`。
2. 在现有聊天框输入：“把问候语改为欢迎，在名字后加中文感叹号；只生成修改建议。”
3. 模型读取文件，调用 `propose_file_change` 提交完整候选内容。
4. 主进程验证参数、快照归属和大小，返回“建议已接收，未写入”。
5. 本轮成功结束后，对应助手消息出现建议卡片。
6. 点击卡片，主进程重新验证当前授权，原差异面板显示一删一增。

本课一次成功轮次最多接收一份单文件建议。练习文件限定最多 80 行、规范化原文与候选各不超过 2000 个 JavaScript 字符；工具 arguments 序列化字符串仍不得超过现有 4096 字符。不要承诺支持所有第 22 课可预览的大文件。

不增加依赖、回复模式、第二个输入框、通用文件接口或磁盘写入。继续用当前模型与配置，继续保留 `store: false`、非流式工具协议和既有停止机制。多文件、建议编辑、真正写入与冲突保护后续安排。

## 2. 开课前先修正上一课的接线

本次源码核对：第 22 课共享类型、主进程服务、IPC 模块、preload、Hook 与面板均存在，`npm run typecheck` 的 Node/Web 两组通过。但 `src/main/index.ts` 尚未导入或调用 `registerChangePreview`，因此不能把类型检查通过视为预览接口已经可调用。

先在主进程入口补充：

```ts
import { registerChangePreview } from './agent/change-preview-ipc'
```

在现有业务 IPC 注册区域、`registerProjectAccess(...)` 附近调用一次：

```ts
registerChangePreview()
```

不要放进每次创建窗口都会执行的函数，也不要在组件渲染时注册。重启开发主进程后，用第 22 课调试入口完成一次手填预览。若出现 `No handler registered for 'preview:change'`，先检查这里。本次仅把修正作为练习写入文档，没有代改源码。

另外，`ChangePreview.createdAt` 当前由服务生成，是预览生成时间；面板所需快照时间来自 `contextSelection.createdAt`，不要混用。

## 5. 练习一：定义结构化建议与工具

在共享模块定义：

```ts
export type ChangeProposalArgs = {
  path: string
  proposedText: string
}

export type ChangeProposalOutput =
  | { status: 'proposal_ready'; path: string }
  | { status: 'error'; error: string }

export type MessageChangeProposal = {
  conversationId: string
  requestId: string
  assistantId: string
  callId: string
  snapshotId: string
  path: string
  proposedText: string
}
```

模型只提供 `path` 和 `proposedText`。conversationId、snapshotId、消息关联和请求归属由应用绑定，不能让模型自己决定。path 必须是清单中的附件别名，不能接收绝对路径。空 proposedText 合法，含义仍是清空内容。

自己实现 `parseChangeProposalArgs(value: unknown)` 与 `parseChangeProposalOutput(value: unknown)`，成功返回新对象，失败返回 null。沿用上一课拒绝数组、null、访问器、未知字段的检查；字符串、别名格式和长度都要验证。不要把错误的候选全文拼进提示。

在主进程模块定义工具，采用工程已有 Responses 函数工具结构：

```ts
export const changeProposalTool = {
  type: 'function',
  name: 'propose_file_change',
  description:
    '为已完整读取的附件提交一份完整的新文件内容，只创建供用户审查的建议，不写入磁盘。每次任务最多接收一份。',
  strict: true,
  parameters: {
    type: 'object',
    properties: {
      path: { type: 'string', minLength: 1, maxLength: 240 },
      proposedText: { type: 'string', maxLength: 2000 }
    },
    required: ['path', 'proposedText'],
    additionalProperties: false
  }
} as const
```

`strict: true` 是模型侧的格式约束，不替代本地授权和语义检查。若当前第三方网关不支持这些参数，应记录兼容性问题；不能因此删除本地校验或宣称真实模型验收通过。

预期：合法对象、空文本通过；伪造字段、非字符串、错误别名及超限候选被拒绝。

## 6. 练习二：每次任务创建独立执行器

设计 `createChangeProposalExecutor(snapshot, conversationId)`，内部复用 `createProjectExecutor(snapshot)`，返回和现有 `ExecuteTool` 兼容的函数。快照必须来自 agent IPC 已完成的 `captureProjectAccess`，不要另建授权 Map。

闭包里维护：

- `fullyReadPaths: Set<string>`：本次任务已完整读取的文件。
- `accepted: boolean`：本次任务是否已经成功接收一份建议。

先实现读取分支：调用原文件执行器，检查返回 JSON 是成功读取结果。只有结果 path 对应当前别名、startLine 为 1、endLine 等于快照总行数、`truncated === false`，并且返回 text 与 `snapshot.files.get(path)!.join('\n')` 一致时，才加入集合。错误结果、搜索摘要、局部读取不能算完整读取。本课不用累加多段读取，最多 80 行的限制让一次读取足够。

再实现 `propose_file_change` 分支，按此顺序：

1. 检查 AbortSignal；在 JSON.parse 前检查原始 arguments 不超过 4096 字符。
2. 用共享解析器获取 path 与 proposedText。
3. 验证 path 属于捕获的快照，原文最多 80 行、2000 字符；候选最多 80 行、2000 字符。长度按换行规范化后检查，参数解析时也保留原字符串上限。
4. 验证该 path 在本次 fullyReadPaths 中，且 accepted 尚为 false。
5. 直接调用第 22 课的纯计算服务 `buildChangePreview`，复用字节数、行数与快照取原文规则；此处不调用 `preview:change` IPC，因为当前 Agent 任务正在运行，IPC 的忙碌检查会拒绝它。
6. 再检查取消，然后设 accepted 为 true，返回简短 JSON：`{ status: 'proposal_ready', path }`。

不要把 before/after 全文放进工具结果：候选已经在 function_call.arguments 内，旧文已由读取工具提供。工具结果只说明接收成功，不能写成“文件已修改”。本课不把返回的 ChangePreview 放进全局状态。

无效参数、未完整读取、超限或第二份建议返回有界错误结果；不要修改 accepted。取消异常必须继续抛出，不能被 catch 转成普通工具错误。其他文件工具继续交给原执行器，时间工具沿用现有路由。

预期：两次独立任务互不影响；同一任务第二份建议被拒绝；即使模型跳过读取直接建议，也不能成功。成功接收后整轮若取消或失败，页面仍不得展示可用建议。

## 7. 练习三：接入现有工具循环

修改 `isToolAllowed`，只在 `scope.kind === 'project'` 时允许 `propose_file_change`。时间范围仍不允许它。这个白名单同时用于执行和历史解析，不能只改发给模型的 tools 数组。

在 `agent-ipc.ts` 的项目分支：

1. tools 列表改为 `[timeTool, ...projectTools, changeProposalTool]`。
2. 在已捕获快照和已验证项目 conversationId 的分支中创建一次新执行器；不要每执行一个工具都重新创建，否则完整读取和 accepted 状态会丢失。
3. 保持时间工具分流，文件搜索、读取与建议统一交给新执行器。
4. 给项目指令补充：用户提出修改要求时，先完整读取目标小文件；只提交该文件完整的新内容；保留未要求改变的内容及末尾换行；每次任务最多一份建议；不能声称已写入；若超限或无法确定，应说明原因。
5. 文件内容和工具结果仍是数据，不能把文件里的指令提升为系统指令。

不要修改 `runToolLoop` 的执行顺序：模型提出调用 → 应用检查并执行 → 以同一个 call_id 返回 function_call_output → 再请求模型给出最终回答。`call_id` 对应一次工具调用，requestId 对应一次聊天生成任务，两者不是同一个 ID。

预算继续是 5 次模型请求、4 次工具执行、90 秒。搜索→读取→建议→最终回答需要 4 次模型请求、3 次工具执行，适合本课；不要为了让超大任务勉强成功而移除预算。arguments 的 4096 限制在循环和历史解析中都保留；即使候选小于 2000 字符，JSON 转义后仍可能超限，必须拒绝，不能截断源码。

## 8. 练习四：先改模拟链，再接真实模型

扩展 `createProjectMock` 的现有步骤，仍保留普通搜索问答。可以约定只有本轮最后一条 user.content 严格等于“模拟修改 greet”时，进入建议分支，其他输入走旧逻辑。不要根据整个历史数组长度决定当前步骤。

建议分支采用固定四步：

1. 搜索 greet，获得清单中的准确别名。
2. 从第 1 行读到该文件总行数，最多 80 行；检查返回范围完整且未截断。
3. 从刚读取的 text 生成候选，只将 `你好，` 换为 `欢迎，` 并在模板字符串名字后加 `！`。确认匹配预期练习内容再替换，保留其余文字和末尾换行。使用本次独立生成的第三个 call_id 调用新工具。
4. 检查匹配 call_id 的结果：proposal_ready 才回答“已生成建议，未写入文件”；error 要说明失败，不伪造成功。

搜索、读取和建议分别使用不同 call_id，每次任务重新生成。没有命中、文件过大或内容不符合练习样例时，直接给出说明，不随便选另一个文件修改。

模拟分支跑通后，再使用现有真实聊天入口，发送自然语言修改要求。网络配置沿用当前工程，不在课件里保存密钥，也不新建独立模型请求接口。

## 9. 练习五：从成功轮次派生消息卡片

在共享建议模块实现纯函数，输入是 conversationId、一条经过现有解析器校验的 ToolRun，以及对应消息状态；输出是零个或一个 MessageChangeProposal。

派生步骤：

1. 仅处理用户/助手消息均 complete、scope 为 project 的轮次，核对消息 ID 与轮次关联。
2. 遍历该轮 items，找到 name 为 propose_file_change 的 function_call，解析 arguments。
3. 按 call_id 找到它对应的 function_call_output，解析 output。只接受 status 为 proposal_ready 且 path 与参数一致的结果。
4. 从外层会话和 ToolRun 绑定 conversationId、requestId、assistantId、snapshotId；callId 来自这次调用；候选来自已解析的 arguments。
5. 如果没有成功结果则不生成卡片；若异常数据包含多份成功建议，拒绝派生，不擅自选择最后一份。

这里不执行工具，只解释历史。不要把 items 再传给工具执行器，也不要扫描 trace 文案判断成功。

在 `useConversation` 中从 `active.toolRuns` 与 messages 派生卡片，按 assistantId 传给 MessageList。卡片显示文件名、附件别名、“修改建议 · 未写入”和“查看差异”。必须放在对应助手消息下，不能一律挂到最后一条消息。

候选全文不放进普通 Markdown 渲染，继续由差异面板用纯文本展示。普通说明文字可以沿用原 Markdown 组件。

## 10. 练习六：点击后复用预览，并处理失效

控制器提供类似 `openProposal(proposal)` 的入口。执行前确认：

- 当前会话 ID 与建议一致，当前 messages/toolRuns 中仍能找到这条已完成的成功建议。
- 当前 `contextSelection.snapshotId` 与建议 snapshotId 一致，path 仍在清单里。
- 当前没有生成、保存、选择等互斥操作，也没有退出保护等待。

然后调用现有 `changePreview.requestPreview(proposal.path, proposal.proposedText)`。主进程通过现有 IPC 再检查窗口、会话、快照、别名，重新构造 before/after。前端检查改善提示，不能替代主进程检查。

不要在 agent 的 done 分支里直接自动调用预览：该处 `generating` 尚未被 finally 释放，预览的 selecting 互斥会失败。本课明确让用户在本轮结束后点击卡片。

交互收尾：

- 同时只显示一个预览，点击其他建议时更新当前来源；loading 时禁用重复入口。
- 关闭按钮和 Escape 只关闭预览，卡片仍可再次打开。
- “丢弃建议”关闭预览并隐藏本次页面生命周期内该建议的入口。用 conversationId、requestId、callId 组成的稳定标识记录在组件内存集合中，不删聊天和 ToolRun，也不撤销文件授权。
- 原面板目前让关闭和丢弃共享 onDiscard；本课应拆成 onClose 与 onDiscard，二者都复用 Hook 的 discard 清理临时预览，只有后者记录隐藏标识。调试手填预览没有消息建议来源，只需关闭。
- 接住“打开成功”的返回值，记录当前面板对应哪条建议；打开失败不标记为已丢弃，允许重试。上下文变更时同时清空面板来源。
- 复用已有按钮 ref，在打开时指向实际触发按钮，关闭后归还焦点；按钮已消失时回到聊天输入框。
- 新选文件、移除文件、清除授权、切换会话或清空聊天后，旧建议不可作为当前建议打开。可保留灰色历史卡片，说明“原快照已失效，请重新提出修改要求”。

本课的丢弃隐藏状态不持久化。刷新后历史卡片可能重新显示，但授权快照不会从聊天记录恢复，卡片只能显示失效状态。不要把同名文件重新选入，就自动给旧建议换上新的 snapshotId。

## 11. 历史与存储：保持一份事实来源

本课不新增会话库字段，继续版本 4。新工具调用的候选内容本来就位于 `ToolRun.items`，成功轮次仍由 `finishToolTurn` 原子提交 messages 与 items。不要另存一份候选导致内容不一致。

这意味着：候选全文会随成功工具历史保存，不能称它“完全不持久化”；真正不持久化的是可操作预览状态、当前授权和本课的丢弃隐藏集合。历史中有建议，不代表应用有权再次访问或写入文件。

核对 `parseProtocolTurn`、`parseToolHistory`、`parseAgentResult` 和容量预检查仍能接受新工具，保持未知工具拒绝、call_id 配对、失败轮 items 为空等约束。保留完整 reasoning、message、phase 和 function_call_output，不只保存文本答案。

存储形状未变，但允许的工具名扩展了：新代码应能读取旧版 4 数据，旧应用可能拒绝含新工具名的记录。开发前备份自己的会话文件；不要把这种语义扩展说成可无条件降级兼容，也不要删除损坏保护。

## 12. 完整练习与排错

自己新建 `greet.ts`，保持与第 22 课一致：

```ts
export function greet(name: string): string {
  return `你好，${name}`
}
```

先选择模拟调试入口，发送“模拟修改 greet”，完成搜索、全文读取、提交建议、最终回答、点击卡片、丢弃。再切回真实入口，对同一练习文件提出自然语言修改要求。模型建议后用编辑器确认原文件仍是“你好”。

| 现象 | 优先检查 |
|---|---|
| 预览没有 handler | main/index.ts 是否注册过一次，主进程是否重启 |
| 模型调用后提示工具不允许 | tools 列表、共享 isToolAllowed、执行器是否都接入 |
| 总提示没有完整读取 | 是否只读了 greet 附近三行；是否核对 truncated、范围和 text |
| 第二个工具调用又忘了读取状态 | 是否每次调用都重新创建了执行器 |
| 有代码块却没有卡片 | 是否真的有成功的 propose_file_change 调用，而非普通回答 |
| 生成结束后自动预览失败 | 是否在 generating 尚未释放时抢占 selecting |
| 重启后有建议却无法预览 | 正常：历史恢复不恢复文件授权 |
| 点击丢弃后卡片又立即出现 | 是否只是关闭面板，没有记录当前生命周期的隐藏标识 |
| 生成成功却无法保存 | 是否漏掉历史白名单，或超过已有协议/整库容量限制 |

下面按课件的 8 道题逐一讲解。

1. 为什么从工具调用生成卡片，而不从助手 Markdown 代码块提取？

   普通回答中的代码块可能只是示例，也可能缺少文件名或完整内容。它不代表应用已经校验并接受了一份建议。

   卡片需要同时找到 `propose_file_change` 调用和对应的 `proposal_ready` 成功结果，才能确认这份建议经过了应用检查。

2. `strict` schema 与主进程检查分别解决什么问题？

   `strict: true` 约束模型输出的结构，例如只能提供 `path` 和 `proposedText`，字段类型必须正确。

   主进程负责验证实际是否允许执行：文件是否属于当前授权快照、本轮是否完整读取、内容是否超限、是否已经接收过建议。**格式正确，不等于有权操作。**

3. 为什么要求本次任务完整读取文件？搜索摘要或旧历史不够吗？

   本课提交的是完整的新文件内容。模型只看到几行摘要，就可能遗漏其他代码，导致候选内容意外删除未看到的部分。

   旧历史可能对应旧快照，不能证明模型已经读取本次授权的文件内容。因此要求本轮完整读取，再生成候选。

4. 四种 ID 各关联什么？

   | ID | 关联对象 |
   |---|---|
   | `call_id` | 一次工具调用及其返回结果 |
   | `requestId` | 一整轮聊天生成任务，可能包含多次工具调用 |
   | `assistantId` | 这轮任务对应的助手消息，用来确定卡片显示位置 |
   | `snapshotId` | 一份已授权的文件内容快照，用来判断建议是否仍适用 |

   例如一轮“搜索→读取→建议”有三个不同的 `call_id`，但属于同一个 `requestId`。

5. 为什么建议工具内部调用纯计算服务，而不调用 `preview:change` IPC？

   提交建议时，Agent 任务仍在运行。预览 IPC 为避免操作冲突，会拒绝忙碌期间的请求。

   此时主进程已经持有经过授权检查的快照，可以直接调用 `buildChangePreview` 验证内容。等任务结束、用户点击卡片时，再通过 IPC 重新检查当前授权并打开预览。

6. 为什么必须整轮成功后才展示卡片？

   工具接收建议后，模型还需要返回最终回答。这期间可能发生取消、超时或网络失败。

   如果工具刚成功就显示卡片，就会出现“本轮已失败，却留下可操作建议”的矛盾。等待整轮成功，可以让消息状态、工具历史和建议卡片保持一致。

7. 候选已保存在工具历史里，为什么重启后仍不能直接预览或写入？

   历史保存的是“当时提出了什么建议”，授权表达的是“现在允许访问哪些文件”。这两者有不同的生命周期。

   重启会恢复聊天历史，但不会恢复文件授权。即使重新选择同名文件，也会生成新快照，旧建议不能自动绑定过去。另外，本课只实现建议和预览，还没有磁盘写入能力。

8. 为什么关闭、丢弃、撤销授权和删除聊天需要分开？

   它们表达的是四种不同意图：

   | 操作 | 含义 |
   |---|---|
   | 关闭预览 | 暂时不看，保留卡片，之后还能打开 |
   | 丢弃建议 | 本次页面生命周期内隐藏这份建议，保留聊天历史 |
   | 撤销文件授权 | 不再允许使用当前文件快照，相关旧建议失效 |
   | 删除聊天 | 清除对话消息和工具历史；本项目清空聊天时也会撤销当前授权 |

   分开之后，用户关闭面板就不会意外删除记录，丢弃建议也不会影响其他附件的授权。

这课最值得记住的是：**建议来自经过验证的工具协议；卡片属于具体消息；能否打开取决于当前授权；预览始终不等于写入。**
