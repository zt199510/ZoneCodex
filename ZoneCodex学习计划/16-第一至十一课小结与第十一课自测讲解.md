## 2. 第十一课八道自测讲解

### 1. 为什么聊天已显示，关闭后仍可能丢失？

页面显示说明 React 内存更新了，磁盘保存是另一个异步过程。可能仍在生成、等待 800 毫秒、写文件，或者保存已失败。关闭后内存消失，下次只能读取最后一次成功保存的数据。

例如磁盘只有第一轮，第二轮已经显示但尚未保存，此时退出，重启就只有第一轮。自动保存缩短未保存的时间，不保证任意时刻退出都不丢失。

### 2. 防抖和主进程串行队列分别解决什么？

防抖减少保存次数：短时间连续变化，只在最后一次变化后空闲 800 毫秒保存。它决定何时提交请求。

串行队列保证提交到同一个 store 的操作按顺序执行，避免文件读写交叉。它决定已提交的操作如何排队。防抖不保证磁盘操作互斥；队列也不会自动合并十次保存为一次。

另外，renderer 的 diskBusy 同步阻止重复进入保存函数，isSaving 驱动界面提示和禁用状态。

### 3. 为什么只有 800 毫秒防抖还会保存 pending？

模型输出可能停顿超过 800 毫秒，但请求并没有结束。没有新文字只表示暂时没收到数据，不能推断已经完成。

因此 Effect 还检查 isSending，保存入口还检查 sendingRef.current。等待 done、cancelled 或 error 终态被处理后，再保存 complete、cancelled 或 failed 状态。

### 4. useCallback 依赖中删掉 messages 会怎样？

React 回调捕获创建它那次渲染的变量。若仅 messages 变化，其他依赖没变，useCallback 可能继续返回旧函数，保存旧消息。

例如旧回调捕获了 messages=[]，页面后来已有聊天，它仍可能保存空数组。workspacePath 等其他依赖变化时可能碰巧重建函数，让问题看起来偶发。

依赖数组用于声明函数依赖的数据。useCallback 不会自动把旧闭包中的 messages 换成最新值。

### 5. 失败后为什么不能只把 isSaving 改回 false？

失败时当前快照仍与保存基线不同，hasUnsavedChanges 仍为 true。如果只释放忙碌状态，Effect 又满足条件，800 毫秒后再次保存，持续失败时就不断循环。

所以失败要保留原 savedSignature、显示错误、设置 autoSavePaused=true，然后在 finally 释放锁和忙碌状态。用户修复问题后手动重试，成功才更新基线并恢复自动保存。

### 6. 保存 A 时页面变成 B，成功后记录哪个 signature？

记录 A，因为磁盘确认写入的是 A。当前 B 与 A 不同，应继续显示有未保存修改，之后再保存 B。

如果把 B 标为已保存，页面会错误地认为 B 已经落盘。本课通过禁用和入口保护尽量避免这种变化，但成功结果只确认本次请求快照的原则仍应遵守。

### 7. clearTimeout 能取消保存 IPC 吗？卸载保护保证退出保存吗？

都不能。clearTimeout 只能阻止尚未执行的计时器回调；回调已调用 saveConversation 后，清除计时器无法撤回 IPC。

storageMounted 用来避免异步结果更新已卸载的 UI，不取消主进程写入，也不保证应用退出前写完。可靠的“保存后退出”需要关闭流程等待保存成功，失败时保留窗口供用户处理，后续课程单独实现。

### 8. 清空自动保存后为什么找不回旧聊天？如何支持撤销？

目前只有一个 conversation.json。清空后成功保存的是 messages=[]，原快照已被替换，下次读取自然为空。

临时文件用于保护替换过程，不是历史备份。想在当前运行期间撤销，需要保留清空前的快照；想重启后也能找回，需要持久化备份、版本历史或回收站，并设计保留数量、恢复入口和恢复后的保存规则。

## 5. 把各项技术连起来

```text
用户输入
  → ChatInput 调用 onSend（同一页面内的函数回调）
  → App 创建消息并构建模型文本历史
  → window.api → preload → IPC
  → Electron 主进程通过 HTTP 请求模型
  → 解码 SSE → IPC 推送增量
  → App 更新对应助手消息 → React 显示
  → 生成终态到达 → 空闲 800 毫秒
  → 保存接口 → 主进程校验并串行写 JSON
  → 下次启动读取 JSON → 恢复 React 状态
```

preload 是桥接层，不应简单理解为独立的第三个进程。TypeScript 类型声明描述接口，不创建运行时方法；来自 IPC 和磁盘的数据仍需实际校验。

## 6. 当前最需要巩固的五点

1. **内存、磁盘、模型上下文是三份不同用途的数据。** 更新其中一份，不代表另外两份自动改变。
2. **state 与 ref 职责不同。** state 变化安排重新渲染，ref 适合同步标记；二者都不是磁盘存储。
3. **每次渲染都有自己的状态快照和闭包。** setState 不会立即替换正在执行的函数所捕获的变量。
4. **异步开始后必须考虑成功、失败、停止和清理。** finally 负责释放资源，不代表任务成功。
5. **界面可见不等于业务完成。** 收到部分文字不等于模型成功，发出保存请求不等于磁盘已保存。

这些课程已形成一个带多轮流式聊天与本地持久化的桌面应用基础。完成代码练习的反馈已经记录，独立解释原理的能力仍需通过复述和实验巩固。
