# 第十三课：多会话数据结构与版本迁移

## 1. 本课目标与范围

第十二课你已反馈退出弹窗和三个选择都正常。本课开始为侧栏多会话打地基：定义一个包含多条会话的版本 2 快照，把版本 1 的单会话转换进去，并用测试数据验证。

本课可观察成果：运行练习脚本，看到两条会话互不串消息，旧版消息迁移后内容和 ID 保留，非法数据被拒绝。

继续由你亲手编写代码。无需安装依赖，无需请求模型，也不读取真实聊天文件。

## 2. 从 Vue 经验理解新结构

目前 snapshot.messages 只有一组消息，像页面只编辑一篇文章。多会话像文章列表：每篇文章有自己的 ID、标题和内容，另外记录当前选中的文章 ID。

先看数据形状，不要把这段示意粘进正式文件：

```json
{
  "version": 2,
  "activeConversationId": "conversation-a",
  "conversations": [
    { "id": "conversation-a", "title": "学习 React", "messages": [] },
    { "id": "conversation-b", "title": "学习 Electron", "messages": [] }
  ]
}
```

activeConversationId 存一个引用目标的 ID，不再复制一份 activeMessages。界面从列表里找到当前会话，再读取它的 messages，这样只有一份消息数据源。

Vue 中可以用 computed 查找当前项；React 中先直接用 find 计算，不需要为了派生值再加 useState 和 useEffect。后续更新消息仍要创建新对象/数组，不能直接 push 到 React state 的内部数组。

本课约定：会话列表允许为空，此时活动 ID 必须是 null；有会话时，活动 ID 必须指向其中一条。最多 100 条会话，全库最多 1000 条消息、总正文长度最多 1,000,000 个 JS 字符单位；单条消息仍遵守第十课限制。这些是教学版限制，不是框架限制。

## 3. 文件职责与 ID

| 文件 | 本课操作与职责 |
|---|---|
| src/shared/conversation.ts | 保留版本 1 类型与解析器，作为旧格式入口 |
| src/shared/conversation-library.ts | 新建；版本 2 类型、校验、版本 1 迁移和活动会话查询 |
| scripts/check-conversation-library.cjs | 新建；只用内存里的测试数据验收 |
| src/main/conversation-store.ts | 本课不接入；下一课负责磁盘读取、兼容迁移与写入 |
| features/conversation/useConversation.ts | 本课不接入；下一课管理整个会话库和当前会话 |

区分四种 ID：会话 ID 定位一个聊天；消息 ID 定位该聊天内的一条消息；模型 requestId 定位一次生成；关闭请求 ID 定位一次退出确认。数组下标和可修改的标题都不适合作为会话 ID。

会话 ID 在整个库内唯一。消息 ID 在所属会话内唯一，不同会话可以出现相同消息 ID；因此以后更新消息时必须先定位会话，再定位消息。

## 4. 编写共享模型与校验器

新建 src/shared/conversation-library.ts，填写以下完整代码。先读完每个函数再输入，尤其注意 parse 与 migrate 的区别。

```ts
import { parseSnapshot } from './conversation'
import type { ChatMessage } from './conversation'

export type Conversation = {
  id: string
  title: string
  messages: ChatMessage[]
}

export type ConversationLibrary = {
  version: 2
  activeConversationId: string | null
  conversations: Conversation[]
}

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value)
}

function isId(value: unknown): value is string {
  return typeof value === 'string' && value.trim().length > 0 && value.length <= 80
}

export function parseLibrary(value: unknown): ConversationLibrary | null {
  if (!isRecord(value) || value.version !== 2 ||
    !Array.isArray(value.conversations) || value.conversations.length > 100) return null

  const conversations: Conversation[] = []
  const ids = new Set<string>()
  let messageCount = 0
  let contentLength = 0

  for (const item of value.conversations) {
    if (!isRecord(item) || !isId(item.id) || ids.has(item.id) ||
      typeof item.title !== 'string' || !item.title.trim() || item.title.length > 80) return null

    // 复用已验证的消息规则，不复制一套可能逐渐不一致的校验。
    const checked = parseSnapshot({
      version: 1,
      messages: item.messages,
      workspacePath: null
    })
    if (!checked) return null

    messageCount += checked.messages.length
    contentLength += checked.messages.reduce((sum, message) => sum + message.content.length, 0)
    if (messageCount > 1000 || contentLength > 1_000_000) return null

    ids.add(item.id)
    conversations.push({ id: item.id, title: item.title, messages: checked.messages })
  }

  const activeId = value.activeConversationId
  if (conversations.length === 0) {
    if (activeId !== null) return null
  } else if (!isId(activeId) || !ids.has(activeId)) {
    return null
  }

  return {
    version: 2,
    activeConversationId: activeId as string | null,
    conversations
  }
}

export function migrateV1(value: unknown, conversationId: string): ConversationLibrary | null {
  const old = parseSnapshot(value)
  if (!old || !isId(conversationId)) return null

  return {
    version: 2,
    activeConversationId: conversationId,
    conversations: [{
      id: conversationId,
      title: '历史会话',
      messages: old.messages
    }]
  }
}

export function readLibrary(
  value: unknown,
  legacyConversationId: string
): ConversationLibrary | null {
  if (!isRecord(value)) return null
  if (value.version === 2) return parseLibrary(value)
  if (value.version === 1) return migrateV1(value, legacyConversationId)
  return null
}

export function getActiveConversation(library: ConversationLibrary): Conversation | null {
  return library.conversations.find((item) => item.id === library.activeConversationId) ?? null
}
```

这里的类型断言只发生在 activeId 已经经过条件验证之后，不是用 as 把未知数据强行变成可信数据。你也可以把两个分支分别 return，从而不使用这个断言。

parseLibrary 只接受版本 2，返回由可信字段组成的新对象，不修改输入。migrateV1 先验证旧数据，再把它包装成一条“历史会话”。readLibrary 根据版本选择路径，不认识的版本返回 null，不能当成空库继续保存。

复用 parseSnapshot 是本课减少改动的方式；新模型并不因此包含 workspacePath。后续可以单独提取 parseMessages，让两个版本共享规则。

## 5. 迁移要保留什么

迁移保留消息的 ID、顺序、角色、内容与状态。版本 1 没有会话 ID，因此由调用者提供一个新 ID。生产接入时由主进程生成并随版本 2 保存；不能每次渲染或每次校验版本 2 都重新生成。

本练习用固定的 legacy-chat 便于核对。相同输入和相同 ID 得到相同结果，这种函数方便测试，也不依赖 Electron。

版本 1 的 workspacePath 不进入版本 2，因为项目已经移除工作目录功能。正式落盘迁移前，下一课会设计保留旧文件备份；本课完全不改旧文件。

空的旧消息数组也迁成一条空的历史会话，这是明确的产品规则。全新空库则可以是 conversations: [] 和 activeConversationId: null；缺失文件是存储层判断的结果，不把 null、坏 JSON 或未知版本当成“文件缺失”。

注意 pending：迁移只换结构，不判断运行中的请求是否还存在。当前 main/conversation-store.ts 在启动读取时把 pending 改为 failed；下一课要把这一步扩展到每条会话，不能在通用解析器中修改状态，否则正常保存时也会把生成中的消息标成失败。

## 9. 自测题

1. 为什么不能把原 messages 数组旁边再放一个 activeMessages state？
2. 会话 ID、消息 ID、模型 requestId、关闭请求 ID 分别定位什么？
3. 为什么 activeConversationId 必须能在 conversations 中找到？空库时是什么？
4. parseLibrary 与 migrateV1 有什么不同？为什么都接收 unknown？
5. 为什么版本 2 的数据不能每次读取都重新生成会话 ID？
6. 为什么未知版本要报错，不能返回空库？
7. 两个会话可以有相同消息 ID，更新消息时因此要先定位什么？
8. 为什么纯迁移函数不写文件，也不把 pending 改成 failed？这两件事分别在哪层做？

用测试脚本里的 legacy-chat 和 second-chat 举例回答，不要求背术语。

**1. 为什么不再放一个 `activeMessages` state？**

因为当前消息可以从会话库中找到，不需要再保存一份：

```ts
const activeConversation = library.conversations.find(
  item => item.id === library.activeConversationId
)
const activeMessages = activeConversation?.messages ?? []
```

假设你给 `legacy-chat` 添加了消息，却忘记同步另一个 `activeMessages` state，保存的数据和界面就可能不一致。

这里的 `activeMessages` 是每次渲染时算出来的普通变量。类似 Vue 的 `computed`，数据源只有会话库这一份。

**2. 四种 ID 分别定位什么？**

| ID | 定位对象 | 例子 |
|---|---|---|
| 会话 ID | 哪一场聊天 | `legacy-chat`、`second-chat` |
| 消息 ID | 该会话里的哪条消息 | `m1` |
| 模型 `requestId` | 哪一次模型生成请求 | 判断增量是否属于本次生成 |
| 关闭请求 ID | 哪一次退出确认 | 防止旧弹窗的处理结果影响新的关闭请求 |

一次会话可以包含多条消息，也可以先后发起多次模型请求，所以这些 ID 不能混用。

**3. 为什么活动 ID 必须能在列表里找到？**

`activeConversationId` 表示“目前打开哪条会话”。

如果它是 `second-chat`，但列表里只有 `legacy-chat`，程序就无法找到要展示的聊天。因此这种数据要拒绝。

本课约定：

```ts
// 没有会话
conversations: []
activeConversationId: null

// 有会话
activeConversationId: 'legacy-chat' // 必须存在于列表中
```

**4. `parseLibrary` 和 `migrateV1` 有什么不同？为什么接收 `unknown`？**

- `parseLibrary`：检查输入是否为合法的 **版本 2** 数据，提取可信字段组成新对象。
- `migrateV1`：先检查 **版本 1** 数据，再将原来的消息包装成一条“历史会话”。

结构变化是：

```text
版本 1：messages
          ↓ 迁移
版本 2：conversations[0].messages
```

使用 `unknown`，是因为外部数据还没有经过验证，不能直接相信它符合类型。

**TypeScript 类型不会在运行时检查文件内容。**即使你写了类型断言，缺失字段也不会自动补上，所以函数内部仍要实际检查。

**5. 为什么版本 2 不能每次读取都重新生成会话 ID？**

会话 ID 是稳定身份。

假设 `legacy-chat` 重新读取后变成了 `new-chat`，原先指向 `legacy-chat` 的活动 ID、后续按会话保存的草稿等引用就可能失效。

版本 1 没有会话 ID，因此迁移时需要新增；版本 2 已经有了，就应保留。

**6. 为什么未知版本不能返回空库？**

假设文件是未来的版本 3，里面有很多聊天，但当前程序只认识版本 1、2。

如果把“不认识”当成“空库”，后续自动保存可能把原文件覆盖成空数据，导致聊天丢失。

因此应当：

```text
未知版本 → 返回 null 表示无法读取 → 上层提示错误并阻止覆盖
```

注意：本课的 `readLibrary` 本身返回 `null`，具体错误提示由调用它的上层负责。

**7. 两个会话有相同消息 ID，更新时先找什么？**

**先找会话，再找该会话里的消息。**

例如：

```text
legacy-chat
  └─ m1：「学习 React」

second-chat
  └─ m1：「学习 Electron」
```

只说“修改 `m1`”，无法确定是哪一条；必须说“修改 `second-chat` 里的 `m1`”。

这也是后续流式更新需要明确会话归属的原因，否则可能把回复写进另一场聊天。

**8. 为什么迁移不写文件，也不把 `pending` 改成 `failed`？**

迁移函数只负责：**把合法旧结构转换成新结构，保留消息信息。**

另外两件事各有负责位置：

| 操作 | 应由哪里负责 | 原因 |
|---|---|---|
| 备份旧文件、写入新格式 | 主进程存储层 | 涉及磁盘操作和写入失败处理 |
| 启动恢复时将遗留的 `pending` 改成 `failed` | 主进程存储层的启动读取流程 | 上次进程已经结束，原来的生成请求无法继续 |

`pending` 表示正在生成。应用正常运行时，正在保存的消息也可能是 `pending`；如果通用解析或迁移函数擅自将它改成 `failed`，就会把正常生成误判为失败。

因此，**结构迁移保留状态，启动恢复再处理上次中断的状态。**
