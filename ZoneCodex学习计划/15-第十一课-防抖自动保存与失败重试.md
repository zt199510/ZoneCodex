# 第十一课：防抖自动保存与失败重试

## 1. 本课目标与前置条件

完成聊天、清空记录或更换工作目录后，空闲 800 毫秒自动保存；生成过程中不写盘；保存失败后暂停自动重试，由你点击按钮重试。仍保留手动保存。

本课继续由你亲手修改应用代码。只改 App.tsx，不新增依赖，不新增 IPC，不改变第十课的文件格式和损坏保护。

2026-09-15 已核对当前源码：共享类型、主进程存储、preload、启动读取和手动保存已实现；旧独立真实流区已移除挂载。但发送、清空和选目录还缺少加载/保存保护。本课先补齐这一项。当前项目 Node、Web 类型检查通过，不代表交互验收全部通过。

本课完成后，关闭窗口仍不会弹出退出确认。800 毫秒内退出、生成中退出、保存尚未完成或保存失败时退出，都可能丢失尚未保存的修改。先学会可靠判断保存状态，下一课再接窗口关闭流程。

## 2. 用 Vue 经验理解这次变化

| 你熟悉的概念 | 本课 React 做法 |
|---|---|
| 根据数据变化触发副作用 | useEffect 根据依赖变化安排保存计时器 |
| 防抖 watch | 下一次变化先清理旧计时器，再安排新的计时器 |
| computed 派生结果 | currentSignature 和 hasUnsavedChanges 直接计算 |
| 保存函数读响应式状态 | 回调读取创建它那次渲染的状态快照，依赖必须完整 |
| 清理副作用 | Effect 的返回函数清除计时器；卸载时也会执行 |

useCallback 让函数在依赖未变时保持引用稳定，不会自动让函数读到最新状态，也不会执行保存。计时器负责“何时调用”，保存函数负责“能否开始以及保存哪份快照”。

三份数据仍要分清：React 内存是当前显示，磁盘是最后成功保存的版本，模型上下文是发送时筛选的成功问答。自动保存只连接前两者。

## 3. 文件地图与行为规则

| 文件 | 本课职责 |
|---|---|
| src/renderer/src/App.tsx | 补齐互斥、统一保存入口、安排和清理计时器、显示失败暂停状态 |
| src/main/conversation-store.ts | 复用串行队列、格式检查、临时文件替换、损坏文件保护 |
| src/shared/conversation.ts | 复用 ConversationSnapshot；pending 恢复仍由主进程处理 |
| src/shared/api.ts、src/preload/index.ts | 继续使用 loadConversation 和 saveConversation |

规则先于代码：

1. 加载未完成或加载失败时不保存，也不允许修改聊天/目录。
2. 有未保存修改，且不在生成、选择目录或保存时，才开始等待 800 毫秒。
3. 等待期间发生新变化，取消旧计时器，重新等待。
4. 生成期间即使很久没有 delta，也不保存；完成、停止或失败后再保存终态。
5. 保存失败不修改 savedSignature，并暂停自动重试，避免每 800 毫秒失败一次。
6. 手动保存与自动保存共用一个入口和同一把 diskBusy 锁。

## 4. 起步练习：补齐第十课的操作保护

以下代码替换各函数开头已有的对应判断，其余函数内容保留。

```

```

同步修改 JSX，不能只改按钮而漏掉函数入口：

| 控件 | disabled |
|---|---|
| ChatInput | !streamReady \|\| !storageReady \|\| isSaving \|\| isSending |
| 清空对话按钮 | !storageReady \|\| isSaving \|\| isSending |
| 选择工作目录按钮 | !storageReady \|\| isSaving \|\| isSelecting |
| 保存按钮 | !storageReady \|\| isSaving \|\| isSending \|\| isSelecting |

停止生成按钮维持原逻辑。输入框草稿不保存；切换输入框的实验也不属于本地快照变化。

预期：读取时不能发消息或选目录，保存时不能清空。先手动保存一轮、重启、确认恢复，再继续下面的步骤。

常见错误：disabled 只限制用户点击，不能替代同步入口检查；diskBusy 是 ref，改变它不会重绘界面，因此还要 isSaving。

## 5. 定义自动保存的起点

在 React 导入中加入 useCallback：

```ts
import { useCallback, useEffect, useRef, useState } from 'react'
```

在已有存储状态旁新增：

```tsx
const [autoSavePaused, setAutoSavePaused] = useState(false)
const storageMounted = useRef(false)

useEffect(() => {
  storageMounted.current = true
  return () => { storageMounted.current = false }
}, [])
```

保留原有 snapshot、currentSignature、hasUnsavedChanges 和读取 Effect。在读取成功分支，将 setSavedSignature 的那一行替换为：

```ts
setSavedSignature(JSON.stringify(result.snapshot))
```

这次将“读取后的状态”作为比较基线。即使文件缺失，也不会仅因启动就自动创建空文件；首次使用提示仍可保留。用户实际修改后才会触发自动保存，手动保存仍可创建空文件。

因此 savedSignature 更准确的含义是“已加载或已成功保存的基线”。文件缺失时它不证明磁盘存在文件。pending 在加载时转为 failed 的结果也作为基线，本课不为这个规范化动作单独写盘；下次修改或手动保存时才落盘。

预期：启动后不操作，在主进程 conversation:save 处理器上的断点不会命中。加载失败时 storageReady 仍是 false，计时器不会启动。

## 6. 替换手动保存函数：统一保存入口

用下面代码替换整个原 handleSaveConversation 函数。放在下一节自动保存 Effect 之前，其他处理函数不需要改成 useCallback。

```tsx
const handleSaveConversation = useCallback(async (): Promise<void> => {
  if (!storageMounted.current || !storageReady || diskBusy.current ||
      sendingRef.current || isSelecting) return

  diskBusy.current = true
  setIsSaving(true)
  setStorageError(null)
  setStorageStatus('正在保存…')

  const toSave: ConversationSnapshot = { version: 1, messages, workspacePath }
  const signature = JSON.stringify(toSave)
  try {
    const result = await window.api.saveConversation(toSave)
    if (!storageMounted.current) return
    if (!result.ok) {
      setAutoSavePaused(true)
      setStorageError(result.error)
      setStorageStatus('保存失败，自动保存已暂停，请手动重试')
      return
    }
    setSavedSignature(signature)
    setAutoSavePaused(false)
    setStorageStatus('保存成功')
  } catch {
    if (!storageMounted.current) return
    setAutoSavePaused(true)
    setStorageError('保存通信失败，请点击保存按钮重试。')
    setStorageStatus('保存结果未确认，自动保存已暂停')
  } finally {
    diskBusy.current = false
    if (storageMounted.current) setIsSaving(false)
  }
}, [storageReady, isSelecting, messages, workspacePath])
```

依赖数组里的 messages 和 workspacePath 保证回调使用对应渲染的数据；不要为了保持函数引用不变而删掉依赖。toSave 在函数内创建，避免把每次渲染都新建的 snapshot 对象作为依赖。

只有主进程确认成功才更新基线，而且记录的是本次请求的 signature。即使以后放开保存期间编辑，也不能在旧请求完成时把最新页面内容误标为已保存。

暂停状态只限制自动触发，不能放进保存函数的拒绝条件，否则手动重试也会被挡住。重试成功后恢复自动保存；重试失败则继续暂停。不要在 finally 中清除错误或设置“保存成功”。

storageMounted 防止保存结果回写已经卸载的 App；它不取消已提交的磁盘操作。主进程的队列和临时文件清理仍然负责完成该操作。本课 App 是根组件，不设计卸载重挂载时复用旧保存任务。

## 7. 添加防抖 Effect

在上面的 useCallback 后新增一个独立 Effect：

```tsx
useEffect(() => {
  if (!storageReady || !hasUnsavedChanges || isSending ||
      isSelecting || isSaving || autoSavePaused) return

  const timer = window.setTimeout(() => {
    void handleSaveConversation()
  }, 800)

  return () => { window.clearTimeout(timer) }
}, [
  storageReady, hasUnsavedChanges, currentSignature,
  isSending, isSelecting, isSaving, autoSavePaused,
  handleSaveConversation
])
```

为什么还依赖 currentSignature？有修改时 hasUnsavedChanges 一直是 true，仅看这个布尔值不能描述第二次、第三次变化；快照签名让变化的含义明确。本例保存回调也随消息和目录变化而变化。

为什么依赖 isSaving？保存开始时取消仍在等待的自动保存；保存完成后重新判断是否还有未保存内容。失败时 autoSavePaused 为 true，不会因 isSaving 变回 false 就无限重试。

为什么判断 isSending？仅做防抖仍会在模型输出停顿 800 毫秒时写入 pending 快照。这里主动等待整轮终态，停止或失败的半截内容以 cancelled/failed 保存，不进入成功上下文。

清理函数只能取消尚未触发的计时器，不能撤回已经发出的 IPC。保存入口的 diskBusy 同步检查用于拦住重复进入，主进程串行队列则是另一层保护。

预期：清空后等待会保存空消息；这与第十课不同，现在重启后旧聊天不会自动回来。自动保存覆盖的是当前单份记录，不是撤销历史或备份系统。

## 8. 调整提示并观察流程

保留原保存按钮的 onClick 和 disabled，将按钮内容改为：

```tsx
{isSaving ? '正在保存…' : autoSavePaused ? '重试保存' : '立即保存'}
```

将原来的 hasUnsavedChanges 提示替换为下面两段，保留 storageStatus 和 storageError 的显示：

```tsx
{hasUnsavedChanges && (
  <p>{autoSavePaused
    ? '有未保存的修改，请修复问题后点击重试保存。'
    : '有未保存的修改，将在生成结束且操作空闲 800 毫秒后自动保存。'}</p>
)}
<p>关闭前请确认保存成功；当前还没有退出确认功能。</p>
```

storageStatus 显示最近一次读写结果，hasUnsavedChanges 显示当前是否偏离基线。上次“保存成功”之后再改数据，仍可能有未保存提示，应以当前提示为准。

可以把断点设在计时器回调、saveConversation 调用和主进程 save 处理器，依次观察：

```text
修改状态 → 等待 800 ms → 同步检查并加锁 → IPC → 主进程写入
                                                ↓
                         成功：更新基线 / 失败：保留基线并暂停
```

不要在 Effect 中每次渲染都直接调用保存，也不要在清理函数或窗口卸载时临时发异步保存来承诺“退出不会丢失”。

## 9. 检查与验收

完成上述修改后运行 npm run typecheck，并完整重启 Debug All。用测试聊天验收，不需要新增模型配置或打印聊天内容。

| 实验 | 应观察到的结果 |
|---|---|
| 只启动，不做修改 | 不触发自动写入；缺失文件也不因启动创建 |
| 正常完成一轮聊天 | 生成中不保存；结束后约 800 ms 保存终态 |
| 等待期间再次更换目录或清空 | 原计时器取消，最终保存最新快照 |
| 等待期间立即手动保存 | 两个入口不能并发执行；成功后不再保存同一脏状态 |
| 停止生成 | 终态到达后保存 cancelled 和已收到的文字，重启可见 |
| 生成失败 | 保存 failed；该轮仍不进入后续成功上下文 |
| 清空后等待保存成功再重启 | 旧消息不再恢复，工作目录保留 |
| 等待时关闭或刷新页面 | 旧计时器清理，最新修改可能尚未保存 |
| 已开始保存时卸载 | 不回写已卸载 UI；不宣称磁盘操作被取消 |

失败实验可先在调试器中让保存接口返回 { ok: false, error: '教学保存失败' }，或临时替换该次调用来模拟 Promise 拒绝，实验后还原。观察 savedSignature 不变、有错误提示，等待几秒也没有不断重试；改动页面后仍保持暂停。恢复正常接口，点击“重试保存”，成功后下一次修改又能自动保存。

不要为了制造失败去修改真实聊天文件或系统权限。损坏保护仍按第十课备份测试数据后实验：加载失败不启动自动保存，主进程也拒绝覆盖损坏文件。网络生成错误与磁盘保存错误是不同路径，需分别观察。

明确验收条件：类型检查通过；加载保护生效；无逐 delta 写盘；防抖清理有效；保存失败不循环重试；手动重试恢复自动保存；成功后重启恢复最新快照。实际观察结果由你记录，文档创建不代表完成这些实验。
