# 第四十三课：默认工作目录与统一执行权限

## 1. 本课目标与前置条件

本课承接[第四十二课](53-第四十二课-Agent指令与行为规则统一.md)，按用户最新要求对齐 Codex 的工作方式：工作区是可选项目上下文；没有手动选择工作区的聊天也有运行目录；文件和命令沿同一套工具执行；能否执行和是否需要审批由实际权限配置决定。

本课的可观察目标是：新建聊天，不选择工作区，输入“在 `D:\AiTools\Test` 创建一个测试文本”，模型能使用现有工具链处理这个绝对路径；有写入权限时创建成功，需要审批时进入正常审批流程，拒绝或失败时如实报告。使用绝对路径不会自动把目标目录变成聊天工作区，也不会自动增加整个目录的权限。

不新增“路径级临时授权”、无项目专用创建工具、路径授权向导、特殊聊天模式或第二套回复通道。项目聊天与无项目聊天使用同一执行机制。截图中没有选择工作区和没有出现审批弹窗是两个独立事实，不能据此默认开放全部磁盘。

前置条件：第39课工作区与项目指令、第40、41课消息展示、第42课统一 Agent 请求，以及既有文件创建、修改、命令执行、任务和协议历史。2026-10-02 核对的源码已经具有这些入口，但第40至42课的真实模型和桌面验收仍有未完成项。本课创建只编写学习文档，核心代码由学习者亲手实施。

### 官方机制与本课实施范围

依据 2026-10-02 实际读取的 OpenAI 官方文档：

- [项目与聊天](https://learn.chatgpt.com/docs/projects)：可以不依附项目开始聊天；本地项目的主文件夹提供默认工作目录，项目用于组织上下文。
- [沙箱](https://learn.chatgpt.com/docs/sandboxing)：沙箱决定文件和网络的执行边界，审批决定何时暂停；边界内允许的操作不要求每次确认。
- [Windows 沙箱](https://learn.chatgpt.com/docs/windows/windows-sandbox)：原生 Windows 使用系统级文件与网络限制；普通 `spawn` 和设置 `cwd` 不能替代它。

官方文档没有在上述页面公布无项目聊天内部目录的完整命名规则。本课为 ZoneCodex 的无项目聊天使用应用管理的稳定目录，不把自己选择的目录名称说成 Codex 的内部实现。

本课先完成默认运行上下文、通用路径处理及统一权限决策，形成文件新建与读取闭环。文件执行器的路径检查只约束其自身读写，不证明进程及网络层面的 OS 沙箱已经实现。现有直接启动程序的执行器不因此成为沙箱：受限命令必须交给真正支持对应策略的执行后端；后端未接通时明确返回不可执行，不能悄悄使用普通 `spawn`。Windows 原生沙箱及自动审批的完整接入列为后续实施项；未实际接通、验收的模式不能显示为已经可用。整个项目继续以 Codex 的行为和权限机制为目标，不把阶段成果记录成全部对齐完成。

## 2. 用 Vue 经验理解本课

可以把“当前项目”理解成 Vue 页面中的可选上下文，把“运行上下文”理解成后端为每次请求确定的运行环境。页面没有选择项目，不代表后端没有运行环境；类似没有选中业务分类，仍然可以发送正常请求。

`cwd` 是相对路径的起点；目标路径是文件实际保存的位置；权限决定这个位置是否允许访问。三者各有职责：

| 概念 | 作用 | 本课例子 |
| --- | --- | --- |
| 可选工作区 | 提供项目目录、项目指令和展示信息 | 聊天可以没有选定工作区 |
| 默认工作目录 `cwd` | 解析相对路径、作为命令默认启动位置 | `notes.txt` 相对当前聊天运行目录解析 |
| 绝对目标路径 | 明确某次文件操作的目标 | `D:\AiTools\Test\codex-test.txt` 不依赖 `cwd` |
| 文件与网络边界 | 限定实际可访问资源 | 可写目录由有效权限配置确定 |
| 审批策略 | 决定何时等待批准 | 边界内继续执行；需要越界时按策略处理 |

React Hook 负责展示运行目录、项目和权限选择，通过 preload 请求业务操作。主进程确定实际目录、配置和执行边界。不要让 renderer 传一个 `allowed: true` 就获得文件写入权限，正如前端表单不能自行决定后端是否授权。

## 4. 按依赖顺序实施

### 步骤一：核对当前限制，确定目标调用链

找到以下现状：构造器以 `workspaceId` 注入工具；IPC 以工作区是否存在创建执行器；共享白名单以 `workspaceId` 允许本地工具；文件参数拒绝绝对路径；写入与运行每次调用固定确认框。

将目标调用链写清楚：

```text
同一聊天请求
  → 主进程确定运行目录与有效权限配置
  → 构造同一套可用工具和指令
  → 模型提交工具调用
  → 解析实际目标并进行权限判断
  → 按需审批，再交给对应执行器
  → 返回真实结果，继续原有 Responses SSE 工具循环
```

**练习：**指出上述五个限制分别位于哪个函数，并解释只删除 `agent-instructions.ts` 中的条件为何仍不能执行。

**预期结果：**知道工具提供、运行时白名单、路径校验、审批和执行器需要一起调整。

**常见错误：**只改提示词或只展示一个工作目录，就声称已支持无项目文件操作。

### 步骤二：为每个聊天确定默认运行目录

在主进程确定 `cwd`：有有效选定工作区时使用其根目录；没有选定工作区时使用应用管理的聊天目录。可以在 Electron `userData` 下按已经校验的会话 ID 管理目录；不要使用应用安装目录，也不要依赖开发环境偶然的 `process.cwd()`。

这个默认目录是运行环境，不是通过文件夹选择框生成的 `WorkspaceGrant`。保持 `workspace: null`，不悄悄把用户消息里的 `D:\AiTools\Test` 改成会话项目。绝对路径只影响对应操作的目标。

目录创建、存在性和真实路径检查由主进程完成。窗口/会话归属、任务取消和有效配置在请求开始时固定；执行前仍检查是否发生失效或变化。renderer 只接收用于展示和历史关联的信息，不持有可复用的执行许可。

**练习：**为 A、B 两个无项目聊天确定各自稳定的默认目录；选择、清除工作区后，说明下一轮 `cwd` 的变化。运行中的任务不跟随界面切换改变目录。

**预期结果：**无项目聊天可以开始本地任务；清除工作区后回到默认运行目录，普通问答不被文件夹选择阻塞。

**常见错误：**默认目录通过伪造 `workspaceId` 注入；将保存的工作区标签当作已恢复权限；每轮随意换目录而使相对路径失去含义。

### 步骤三：统一运行权限和审批来源

使用 Codex 已有的概念，不根据“用户消息里出现了某个路径”自创另一种授权。运行配置区分以下字段：

```text
sandbox_mode       文件与网络的执行边界
approval_policy    何时允许请求批准
approvals_reviewer 谁处理需要批准的请求
writable_roots     除默认工作范围之外的有效可写目录
```

这些名称用于说明与官方配置的对应关系；ZoneCodex 是否保存为 `config.toml` 不在本课另建一套设置系统。当前仓库尚无这些统一设置，本课必须实际接通来源，不能假设已有配置可加载。

最小实施在主进程维护当前进程的运行设置，默认 `sandbox_mode = workspace-write`、`approval_policy = on-request`、`approvals_reviewer = user`；额外可写目录初始为空，实际默认运行目录和有效附加项目目录参与文件边界构造。输入框权限选择通过类型化 IPC 读取和修改设置，“完整访问”对应 `danger-full-access` 与 `never`。IPC 校验窗口和主 frame 来源，生成期间不切换配置；改变配置使原运行描述和未使用批准失效。主进程返回用于展示的模式及版本信息，模型工具参数、附件和 `AGENTS.md` 都不能修改设置。设置持久化可以后续补齐，本课验收明确重启恢复受限默认，不声称已经实现完整 `config.toml` 配置系统。

| Codex 配置语义 | 对齐行为 |
| --- | --- |
| `read-only` | 在实际允许的范围读取；写入需要按策略处理，不能自行写入 |
| `workspace-write` + `on-request` | 有效范围内的文件操作按策略执行，越界操作需要批准，不要求所有新建都弹窗 |
| `danger-full-access` + `never` | 用户主动选择完整访问后，执行器不施加沙箱限制，也不再套用每次写入确认 |
| `approval_policy = never` | 不请求批准；这一个设置不会扩大文件权限，越界操作仍失败 |
| `approvals_reviewer = auto_review` | 需要批准的请求交给实际审批器；没有该审批器时不得假装自动审批成功 |

界面只使用与 Codex 对应的权限表达，例如“请求批准”“完整访问”；“自动审批”须在实际接入后提供。不增加“授权这个路径”模式。默认保持受限配置，不因本课目标把完整访问设成默认。

权限决策至少区分“当前边界内可执行”“需要批准”“禁止或执行后端不可用”。审批通过后仍要重新核对目标和任务状态；只对获批的具体操作执行，不自动修改整个会话的可写目录。等待批准继续复用 `waiting_approval`、停止和超时暂停机制。

**练习：**列出“范围内新建”“范围外新建且允许请求批准”“范围外新建且不允许请求批准”“用户选择完整访问”的决策结果。不要根据命令字符串看起来温和就批准任意程序。

**预期结果：**权限和工作区选择分离；边界内操作无需固定重复确认，越界操作按有效策略处理。

**常见错误：**把 `never` 当成完整访问；把审批成功当成文件已创建；直接删除所有确认框却没有有效的执行边界。

### 步骤四：让现有文件工具同时处理相对和绝对路径

改造现有文件工具及执行器，不另建 `create_local_file` 等无项目专用工具。项目聊天和无项目聊天只是在运行上下文不同，列出、搜索、读取、新建、编辑沿同一组入口运行。

共享目标解析分两步：先把相对路径基于 `cwd` 解析为实际目标，绝对路径直接作为目标；再进行路径有效性与权限判断。必须移除当前把所有反斜杠、冒号和绝对路径一概判为无效的工作区参数规则，同时保留 Windows 非法路径、设备名、替代数据流及控制字符等检查。不能简单“允许所有包含冒号的字符串”。

现有文件读取的规模、编码与结果长度限制继续约束资源消耗。链接及目录联接需要检查实际指向，不能仅用字符串前缀确认目标在可写范围内。例如 `D:\AiTools\Test2` 不属于 `D:\AiTools\Test`；检查路径组成和真实父目录，创建时使用不存在目标的已存在父目录进行复核。

复用现有文件操作保护：新建不覆盖、父目录检查、完整读取登记、内容哈希、修改前冲突检测和写后校验。完整读取缓存使用统一的实际目标标识，使 `notes.txt` 和指向同一文件的绝对路径能正确关联；仍须按当前请求及文件版本校验，不能跨轮误用。

绝对路径编辑还要同步准备与提交：当前 `workspace-actions.ts` 使用 `cwd` 建立快照并按原相对路径查基线，这不能处理位于 `cwd` 外的已允许文件。先校验实际目标的权限，再以其真实父目录作为该文件快照的根、文件名作为内部相对标识，只读取目标文件；完整读取缓存与修改建议关联到同一实际目标和 SHA-256。准备、冲突检测及提交继续使用这份快照，确认最终路径仍是原目标。这个快照根只是内部定位，不会授予整个父目录权限，也不生成新的目录授权流程。

**练习：**对同一个目标分别传相对路径和绝对路径，核对读取与编辑基线；在已有目录中新建小文本文件，再验证同名文件不会被覆盖。本课不额外扩展文件大小、二进制修改或创建整棵目录树。

**预期结果：**绝对路径不会因“未选工作区”或“不是相对路径”被提前拒绝；执行结果仍由实际文件状态证明。

**常见错误：**将全部目标强行拼在 `workspace.root` 后；只校验显示路径而忽略链接指向；用两个独立创建工具分别处理有项目和无项目聊天。

### 步骤五：接通统一工具与命令执行边界

`buildAgentRequest` 按运行上下文提供实际可用的本地工具；`workspaceId` 只决定是否附加显式项目上下文。主进程白名单与执行器采用同一能力描述，不能只放开模型请求里的 `tools`。附件快照工具继续按照已授权附件提供，不因此变成任意磁盘读取入口。

共同规则保留诚实报告，工具规则改为基于实际 `cwd` 和权限处理路径，去掉“必须先选择工作区”“所有写入必须逐次确认”等已经被新机制替代的固定说法。项目指令仍从有效运行目录按现有约束读取；不会因为某次访问另一个目录，就自动加载那里全部项目指令。

通用命令也使用同一运行上下文：默认启动位置为 `cwd`，工具明确提供工作目录时按配置校验。模型命令不能注入正在供用户交互的 node-pty 终端。受限模式下，系统执行后端必须实际限制子进程的文件和网络访问；`shell: false`、固定环境变量或对命令字符串做检查均不足以实现该边界。

当前普通 `spawn` 只能如实作为非沙箱执行路径使用：在用户选择的完整访问模式，或按有效策略批准的具体非沙箱操作中运行。受限后端未就绪时，不允许将范围内命令自动交给普通 `spawn`，也不宣称这一阶段已完成 Codex 的命令沙箱。

同时处理旧 `command-execution:start` 链：`command-execution-ipc.ts` 目前直接启动 npm，`index.ts` 只核对附件快照来源。把它的执行阶段交给相同的权限决策和后端；旧提案、审查和准备记录可以继续保留，但不能仅凭旧“确认运行”绕过当前配置。对应受限后端不可用时，执行部分返回不可用；已消费的准备记录和原批准也不得在权限变化后复用。

**练习：**核对无项目、有项目、只有附件、项目与附件并存时的工具配置；记录一次本地文件调用如何回到原有工具循环。为命令写出受限后端可用、后端不可用和显式完整访问三种结果。

**预期结果：**同一聊天、同一 Responses SSE、同一工具循环；上下文差别不形成新的用户请求模式。

**常见错误：**用“本地聊天”按钮另起一套请求；用固定 `npm_typecheck` 提案代替通用执行层；给普通 `spawn` 加一个 `sandbox: true` 字段就宣称实现沙箱。

### 步骤六：同步历史、存储与安全重试

内部 `ToolScope` 继续描述工具历史适用的运行上下文，不能只靠 `workspaceId` 区分有无本地能力。区分历史描述和当前执行权限：保存的记录用于恢复消息，不是重新授予磁盘访问的凭据。

当前版本5会话采用严格解析，`agent-history.ts` 在恢复时校验工具名及范围。更改工具名、范围结构或会话中的运行目录字段时，先确定兼容和迁移，再修改保存协议；不要直接覆盖旧记录或放宽所有工具白名单。若保存格式改变，需要相应版本迁移、旧文件备份及旧版读取路径；若只改变主进程运行时信息，不为此无故升级会话版本。

需要先改清请求顺序：目前 `useChatRequest.send` 在调用主进程前选择历史并保存 `scope`，preload 也从旧 `context` 直接推导范围。这里不能等待主进程启动后才知道 `cwd`，却仍按旧范围提交历史。

本课采用内部的运行信息解析接口：在发送流程中先由主进程核对会话、可选项目及附件，返回本轮的 `cwd`、权限配置版本和可序列化的范围描述；renderer 再据此选择完整历史并提交正式 Agent 请求。解析期间也受既有操作锁保护；首次消息接受与失败恢复的调用顺序同步调整，如 `send` 改为异步，上游接受回调也必须一起更新。preload 按已校验的运行描述检查请求形状，正式开始时主进程重新计算并比对描述，变化则返回可理解错误，不执行工具。运行描述只用于上下文和历史关联，不是审批凭据；无需用户新增任何操作步骤，也不能让 renderer 自选可写目录。

旧项目工具轮次可以继续显示，但不能按新规则把旧记录解释成新的执行许可。重试同时核对原会话、附件、运行目录和权限配置；不复用已经失效的批准。发生写入后状态不确定时，保留现有核对结果后再重试的边界。

工作区刷新后需要重新授权的历史行为，不再阻止所有普通聊天。保存的项目目录重新使用前仍按有效配置验证；无项目聊天可建立默认运行上下文，不能为了省步骤把旧 grant 永久恢复。

**练习：**加载旧版无项目会话和第42课工作区工具记录，验证能展示；切换项目、修改权限及刷新后，再核对历史选择和重试。

**预期结果：**旧会话可读，运行权限来自当前主进程，目录或权限变化不会重放旧写入。

**常见错误：**新白名单使旧会话整份加载失败；把过去成功的工具调用当作本轮授权；只比较附件 ID 而漏掉运行目录变化。
