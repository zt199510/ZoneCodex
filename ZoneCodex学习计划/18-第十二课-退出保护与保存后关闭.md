# 第十二课：退出保护与保存后关闭

## 1. 目标与当前起点

关闭窗口时，先确认已发送的聊天是否保存。有未保存修改时提供“继续编辑”“不保存并关闭”“保存并关闭”；保存失败必须留在原窗口。

用户已确认工作台布局没有问题。本次已核对当前的 TitleBar、useWindowControls、useConversation、useConversationStorage、useOperation 和主进程窗口模块，并运行 npm run typecheck，Node/Web 均通过。

现在的关闭按钮经 controlWindow('close') 调用 BrowserWindow.close()，没有退出保护。storage.save() 的返回类型还是 Promise<void>，失败时也可能正常返回，因此不能写成 await save(); close() 就认为安全。

本课由你亲手实现。不调整 UI 布局、不新增依赖、不恢复已经移除的目录选择，不把逻辑重新堆回 App.tsx。新文件编号是 18，课程编号是第十二课。

### 本课明确的行为

| 关闭时的情况 | 行为 |
|---|---|
| 读取、生成或保存中 | 取消本次关闭并提示等待；生成中可先点击停止，收到终态后再关闭 |
| 空闲、加载成功、没有未保存修改 | 直接允许关闭 |
| 空闲、有未保存修改 | 显示三选一确认框，暂停自动保存和内容编辑 |
| 加载失败 | 留在确认框，不允许保存；可以继续留在窗口或不保存关闭 |
| 保存并关闭失败 | 确认框保留，允许重试或继续编辑 |
| 连续点击关闭 | 同一关闭请求复用 ID，不叠加确认框 |
| 页面无响应或尚未订阅 | 默认阻止关闭；恢复后可再次点击，不静默放行 |

这里保护的是已发送消息的磁盘快照。输入草稿仍不持久化，也不计入本课 dirty 判断；有重要草稿时请先自行保留。草稿恢复、多窗口退出、系统关机和强制结束进程另行设计。本课不自动执行“停止生成然后退出”，忙碌时明确留窗，便于理解。

## 2. 用 Vue 经验理解这次变化

自定义 Hook 类似 composable，用来组织可复用逻辑，但仍遵守 React 的渲染快照和闭包语义。useConversation 只有一份快照，useCloseGuard 不再复制一份 messages。

| 概念 | 本课理解 |
|---|---|
| 点击关闭按钮 | 只是一个关闭入口，Alt+F4 也可能关闭窗口 |
| BrowserWindow 的 close 事件 | 主进程统一拦截正常关闭请求的位置 |
| event.preventDefault() | 必须在 close 事件内同步调用，先留住窗口 |
| 异步保存 | 等结果后，再发出一次被允许的 close() |
| requestId | 标识一次关闭协商，不是模型请求 ID 或消息 ID |
| closePending ref / state | ref 同步挡住操作，state 驱动界面禁用与 Effect 清理 |

```text
关闭按钮 / Alt+F4
  → 主进程 close 事件：先阻止
  → 发送本次关闭 requestId
  → renderer 检查忙碌状态与保存基线
  → 用户选择，必要时等待 save() 返回 true
  → 回复同一个 requestId
  → 主进程允许下一次 close 通过
```

不能在 useEffect 的卸载清理里临时发异步保存，期待窗口等你写完；也不能在 close 事件 await 之后才 preventDefault。

## 4. 共享接口与 preload

在 AppAPI 中增加：

```ts
onCloseRequested: (listener: (requestId: string) => void) => () => void
finishClose: (requestId: string, allow: boolean) => Promise<boolean>
```

requestId 由主进程创建。finishClose 返回 false 表示该请求已失效，不是“保存失败”。保存结果来自另一条 saveConversation 调用。

在 preload 的 api 对象内增加以下属性，原属性保留：

```ts
onCloseRequested: (listener) => {
  const handler = (_event: IpcRendererEvent, requestId: unknown): void => {
    if (typeof requestId === 'string' && requestId.length > 0 && requestId.length <= 80) {
      listener(requestId)
    }
  }
  ipcRenderer.on('window:close-requested', handler)
  return () => { ipcRenderer.removeListener('window:close-requested', handler) }
},
finishClose: async (requestId, allow) => {
  const result: unknown = await ipcRenderer.invoke('window:finish-close', requestId, allow)
  if (typeof result !== 'boolean') throw new Error('关闭确认结果格式不正确')
  return result
},
```

预期：订阅只是接收业务 ID，不把 Electron event 暴露给页面。index.d.ts 已引用 AppAPI，不重复写一套接口。

## 5. 主进程统一拦截关闭

新建 src/main/close-guard.ts：

```ts
import { BrowserWindow, ipcMain } from 'electron'
import type { Event } from 'electron'
import { randomUUID } from 'node:crypto'

type Guard = { requestId: string | null; allowOnce: boolean }
const guards = new WeakMap<BrowserWindow, Guard>()

export function registerCloseGuard(): void {
  ipcMain.handle('window:finish-close', (event, requestId: unknown, allow: unknown): boolean => {
    const owner = BrowserWindow.fromWebContents(event.sender)
    if (!owner || owner.isDestroyed() || event.senderFrame !== event.sender.mainFrame) {
      throw new Error('不支持的关闭确认来源')
    }
    if (typeof requestId !== 'string' || !requestId || requestId.length > 80 ||
        typeof allow !== 'boolean') throw new Error('关闭确认参数不正确')
    const guard = guards.get(owner)
    if (!guard || guard.requestId !== requestId) return false

    guard.requestId = null
    if (allow) {
      guard.allowOnce = true
      owner.close()
    }
    return true
  })
}

export function attachCloseGuard(window: BrowserWindow): void {
  if (guards.has(window)) return
  const guard: Guard = { requestId: null, allowOnce: false }
  guards.set(window, guard)
  const sender = window.webContents

  function onClose(event: Event): void {
    if (guard.allowOnce) {
      guard.allowOnce = false
      return
    }
    event.preventDefault()
    if (sender.isDestroyed()) return
    guard.requestId ??= randomUUID()
    // 连续关闭复用请求 ID。页面恢复订阅后，再次点击仍可收到请求。
    try {
      sender.send('window:close-requested', guard.requestId)
    } catch {
      guard.requestId = null
    }
  }

  function reset(): void {
    guard.requestId = null
    guard.allowOnce = false
  }

  window.on('close', onClose)
  sender.on('did-start-loading', reset)
  window.once('closed', () => {
    reset()
    window.removeListener('close', onClose)
    sender.removeListener('did-start-loading', reset)
    guards.delete(window)
  })
}
```

在 main/index.ts 顶部导入：

```ts
import { registerCloseGuard, attachCloseGuard } from './close-guard'
```

在 app.whenReady 内，registerWindowControls() 之后增加 registerCloseGuard()。在 createWindow 内，observeWindowState(mainWindow) 之后增加 attachCloseGuard(mainWindow)，应位于 loadURL/loadFile 之前。

阅读重点：

- IPC 处理器只注册一次；保护状态每个窗口一份，页面不能给别的窗口发关闭许可。
- 第一次 close 被阻止；确认后再调用 close，allowOnce 只让这一次通过，然后立即归零。
- 不使用 destroy()、app.exit() 绕过正常生命周期。
- 取消时清掉请求 ID，下次关闭生成新 ID；旧回复不能放行新请求。
- 提前保留 sender 引用；closed 时窗口的 webContents 可能已不可访问，清理监听器不能再从已关闭窗口取它。
- 页面重新加载时使旧请求失效。刷新本身不属于本课保护范围；不要据此宣称刷新也会保存。
- 本课没有“超时就强制关闭”。页面不响应时保留窗口，不冒险放行。

先运行类型检查并重启。此时 renderer 还没接入，点击关闭会被阻止，这是本步骤预期；完成后面的订阅再验收完整关闭。中间调试可以用 VS Code 停止调试，不要把它记为正常退出实验。

## 6. 为关闭协商增加同步锁

### 6.1 同步读取当前操作

useOperation.ts 的 OperationControl 类型增加：

```ts
getOperation: () => Operation
```

在 isIdle 声明后增加并加入返回对象：

```ts
const getOperation = useCallback(() => current.current, [])
return { operation, begin, finish, isIdle, getOperation }
```

operation state 用于渲染；getOperation 读 ref，可以发现已经 begin 但界面尚未重新渲染的保存/生成操作。

### 6.2 会话层记录关闭意图

useConversation.ts 的 React 导入增加 useRef。在创建 operations 前增加：

```ts
const [closePending, setClosePendingState] = useState(false)
const closePendingRef = useRef(false)
const setClosePending = useCallback((value: boolean): void => {
  closePendingRef.current = value
  setClosePendingState(value)
}, [])
const isClosePending = useCallback(() => closePendingRef.current, [])
```

ConversationController 类型增加：

```ts
setClosePending: (value: boolean) => void
getOperation: () => Operation
```

调用存储 Hook 改为（下一节会补齐其参数类型）：

```ts
const storage = useConversationStorage({
  snapshot, setSnapshot, operations, closePending, isClosePending
})
```

clear 的入口改为：

```ts
if (closePendingRef.current || !storage.ready || !operations.isIdle()) return false
```

canEdit 改为：

```ts
const canEdit = storage.ready && operations.operation === 'idle' && !closePending
```

返回对象增加 setClosePending、getOperation，并替换 send 属性：

```ts
setClosePending,
getOperation: operations.getOperation,
send: (content: string): boolean =>
  !closePendingRef.current && storage.ready && stream.send(content),
```

这里的关闭锁和 saving 状态用途不同：确认框正在等待你选择时，磁盘还没有开始保存，但页面也不能再修改快照。

## 7. 保存函数必须告诉调用者是否成功

在 useConversationStorage.ts 的 StorageOptions 中增加：

```ts
closePending: boolean
isClosePending: () => boolean
```

函数参数解构也加入 closePending、isClosePending。ConversationStorage 中 save 的类型改为：

```ts
save: (reason?: 'normal' | 'close') => Promise<boolean>
```

用下面代码替换整个 save 回调：

```ts
const save = useCallback(async (reason: 'normal' | 'close' = 'normal'): Promise<boolean> => {
  if (!mounted.current || !ready ||
      (reason === 'normal' && isClosePending()) || !begin('saving')) return false
  setError(null)
  const submittedSignature = JSON.stringify(snapshot)
  try {
    const result = await window.api.saveConversation(snapshot)
    if (!mounted.current) return false
    if (!result.ok) {
      setError(result.error)
      setPaused(true)
      return false
    }
    setSavedSignature(submittedSignature)
    setHasFile(true)
    setPaused(false)
    return true
  } catch {
    if (mounted.current) {
      setError('保存结果未确认，请重试保存。')
      setPaused(true)
    }
    return false
  } finally {
    if (mounted.current) finish('saving')
  }
}, [ready, snapshot, begin, finish, isClosePending])
```

自动保存 Effect 的入口条件增加 closePending，依赖数组也增加它：

```ts
if (!ready || !dirty || operation !== 'idle' || paused || closePending) return
```

原有按钮和自动保存调用 void save() 不用改。退出流程调用 save('close')，仅绕过“确认框期间暂停普通保存”这一条件，仍然检查 ready、mounted 和操作互斥。

为什么两处都检查？Effect 清理取消尚未触发的计时器；isClosePending() 让已经走到回调入口的普通保存也能读到同步关闭锁。确认框打开后，“不保存并关闭”不会被后台防抖保存悄悄变成保存。

保存前已在进行的磁盘操作不能撤回，所以本课在 saving 时直接取消关闭请求，不提供中途“放弃写入”。

## 8. 编写关闭协商 Hook

新建 features/conversation/useCloseGuard.ts：

```ts
import { useCallback, useEffect, useLayoutEffect, useRef, useState } from 'react'
import type { ConversationController } from './useConversation'

export function useCloseGuard(conversation: ConversationController): {
  open: boolean
  busy: boolean
  message: string | null
  choose: (allow: boolean) => void
  saveAndClose: () => Promise<void>
} {
  const [open, setOpen] = useState(false)
  const [busy, setBusy] = useState(false)
  const [message, setMessage] = useState<string | null>(null)
  const latest = useRef(conversation)
  const pendingId = useRef<string | null>(null)
  const busyRef = useRef(false)
  const mounted = useRef(false)
  const { setClosePending } = conversation

  // 订阅只建立一次；回调读取最近一次提交的会话，而不是最初的空数组。
  useLayoutEffect(() => { latest.current = conversation }, [conversation])

  const finish = useCallback(async (id: string, allow: boolean): Promise<void> => {
    try {
      const accepted = await window.api.finishClose(id, allow)
      if (mounted.current && !accepted) setMessage('关闭请求已失效，请再次点击关闭。')
    } catch {
      if (mounted.current) setMessage('关闭通信未完成，请再次点击关闭。')
    } finally {
      if (mounted.current && pendingId.current === id) {
        pendingId.current = null
        busyRef.current = false
        setBusy(false)
        setOpen(false)
        setClosePending(false)
      }
    }
  }, [setClosePending])

  useEffect(() => {
    mounted.current = true
    const unsubscribe = window.api.onCloseRequested((id) => {
      if (pendingId.current) return
      pendingId.current = id
      setClosePending(true)
      const current = latest.current
      const operation = current.getOperation()
      if (operation !== 'idle') {
        setMessage(operation === 'generating'
          ? '正在生成，请先停止或等待回复结束，再关闭窗口。'
          : '正在读取或保存，请等待完成后再次关闭。')
        busyRef.current = true
        void finish(id, false)
      } else if (current.storage.ready && !current.storage.dirty) {
        setMessage(null)
        busyRef.current = true
        void finish(id, true)
      } else {
        setMessage(current.storage.ready
          ? '有未保存的聊天修改，你希望如何关闭？'
          : '本地记录读取失败。关闭不会改写原文件，当前不能保存。')
        setOpen(true)
      }
    })
    return () => {
      mounted.current = false
      unsubscribe()
      const id = pendingId.current
      pendingId.current = null
      if (id) {
        setClosePending(false)
        void window.api.finishClose(id, false).catch(() => undefined)
      }
    }
  }, [finish, setClosePending])

  function choose(allow: boolean): void {
    const id = pendingId.current
    if (!id || busyRef.current) return
    busyRef.current = true
    setBusy(true)
    setMessage(null)
    void finish(id, allow)
  }

  async function saveAndClose(): Promise<void> {
    const id = pendingId.current
    if (!id || busyRef.current) return
    busyRef.current = true
    setBusy(true)
    setMessage('正在保存，请稍候…')
    const saved = await latest.current.storage.save('close')
    if (!mounted.current || pendingId.current !== id) return
    if (!saved) {
      busyRef.current = false
      setBusy(false)
      setMessage('保存未成功，窗口保持打开。可以重试或继续编辑。')
      return
    }
    await finish(id, true)
  }

  return { open, busy, message, choose, saveAndClose }
}
```

latest 是指向最近一次已提交会话的 ref，不是另一份会话数据。用 useLayoutEffect 更新它，不在组件渲染期间随意写 ref。getOperation 进一步覆盖“操作已同步开始但 state 尚未提交”的间隙。

busyRef 防止同一时刻点两次“保存并关闭”，busy 则禁用三个确认按钮。失败时仍保持 closePending，必须由用户重试或继续编辑；不能失败后自动放行。

finishClose(true) 最终会销毁页面，最后一次 IPC 回复可能已没有接收者，所以不能把“页面必须显示关闭成功”当作退出前置条件。主进程匹配请求与 save 的成功结果才是关键。

## 9. 挂载确认框，不改 App 布局

新建 features/conversation/CloseGuard.tsx：

```tsx
import { useEffect, useRef } from 'react'
import type { ConversationController } from './useConversation'
import { useCloseGuard } from './useCloseGuard'

export function CloseGuard({ conversation }: {
  conversation: ConversationController
}): React.JSX.Element {
  const guard = useCloseGuard(conversation)
  const dialog = useRef<HTMLDialogElement>(null)
  const stayButton = useRef<HTMLButtonElement>(null)

  useEffect(() => {
    if (guard.open) {
      dialog.current?.showModal()
      stayButton.current?.focus()
    } else dialog.current?.close()
  }, [guard.open])

  return <>
    {!guard.open && guard.message && <p className="close-feedback" role="status">{guard.message}</p>}
    <dialog ref={dialog} className="confirm-dialog close-dialog" aria-labelledby="close-title"
      onCancel={(event) => {
        event.preventDefault()
        guard.choose(false)
      }}>
      <h2 id="close-title">关闭窗口</h2>
      <p role="status">{guard.message}</p>
      <div className="dialog-actions">
        <button className="quiet-button" ref={stayButton} disabled={guard.busy}
          onClick={() => guard.choose(false)}>继续编辑</button>
        <button className="quiet-button" disabled={guard.busy}
          onClick={() => guard.choose(true)}>不保存并关闭</button>
        <button className="quiet-button" disabled={guard.busy || !conversation.storage.ready}
          onClick={() => { void guard.saveAndClose() }}>
          {guard.busy ? '请稍候…' : '保存并关闭'}
        </button>
      </div>
    </dialog>
  </>
}
```

```ts

```

```tsx

```

main.css 末尾追加：

```css
.close-feedback {
  flex-shrink: 0;
  margin: 0 24px 12px;
  color: var(--muted);
  font-size: 12px;
}
.close-dialog .dialog-actions {
  flex-wrap: wrap;
}
```

Escape 默认会关闭原生 dialog，但不一定更新你的关闭锁，所以这里先 preventDefault，再走“继续编辑”的同一条流程。保存等待期间 choose 会被 busyRef 挡住，不能只关弹窗却让保存继续在后台执行。

“不保存”是放弃相对于最后一次成功保存的修改，不是删除聊天文件，也不是撤销已经完成的自动保存。

## 10. 验收与现有检查脚本的变化

先执行 npm run typecheck，再完整重启 Debug All。每次使用测试聊天，不直接破坏真实记录。主进程断点放在 onClose、window:finish-close；renderer 断点放在收到关闭 ID 和保存返回的位置。

| 实验 | 预期 |
|---|---|
| 空闲且已保存，点击关闭 | 第一次拦截，第二次单次放行，窗口正常关闭 |
| 新修改后在 800ms 内关闭 | 弹出确认，不在等待选择期间自动写盘 |
| 选择继续编辑 / 按 Escape | 留窗，恢复编辑；自动保存按原规则恢复 |
| 选择不保存并关闭 | 不发新的 save，重启只恢复之前保存的快照 |
| 选择保存并关闭 | 先确认写盘成功，再关闭；重启恢复最新内容 |
| 让 save 返回 ok:false 或 Promise 拒绝 | 留在弹窗，不发允许关闭；恢复条件后能重试 |
| 模型生成中关闭 | 留窗并提示；停止到达终态后再关闭 |
| 加载/保存尚未结束时关闭 | 本次关闭取消；完成后需要再次点击 |
| 连点关闭、连点保存并关闭 | 一个确认框、一次有效保存；不叠加请求 |
| 使用 Alt+F4 | 与自绘关闭按钮进入同一个主进程 close 事件 |
| 加载失败后关闭 | 保存按钮禁用，允许不保存关闭；损坏文件不被覆盖 |
| 回复旧 ID、伪造来源、非 boolean 参数 | 旧 ID 返回 false，非法来源/参数拒绝 |
| 刷新或卸载之后旧结果回来 | 旧请求失效，取消订阅，不允许旧许可关闭新页面 |

可以在测试替身中延迟 load/save，或让 save 失败；不要改系统权限来制造错误。记录保存次数和结果，不打印聊天或密钥。

## 11. 自测题

1. 为什么只在 TitleBar 的关闭按钮里弹确认框还不够？
2. 为什么 preventDefault 必须同步执行，不能等 save 完成再调用？
3. allowOnce 为什么需要在下一次 close 事件里立即重置？
4. save 从 Promise<void> 改为 Promise<boolean> 解决了什么问题？
5. 弹窗期间为什么同时需要 closePending state 和 ref？
6. 不保存并关闭为什么不能删除 conversation.json？已经自动保存的内容会被撤销吗？
7. 为什么生成中先拒绝关闭，不能只看 dirty=false 就放行？
8. 关闭请求 ID、模型 requestId、消息 id 各自代表什么？旧关闭回复为什么不能继续使用？

回答时尽量用一次实际操作说明“谁发起 → 谁拦截 → 谁保存 → 谁最终关闭”。


第 12 课已记录为**实践完成，原理继续巩固**。下面结合你刚刚操作的弹窗，讲解 1–8 题。

**1. 为什么只在标题栏的关闭按钮里弹确认框还不够？**

因为用户也可以按 **Alt+F4**，这不会触发 React 按钮的 `onClick`。

两种操作最终都会触发主进程窗口的 `close` 事件，所以在这里统一拦截，才能同时保护它们。

**2. 为什么 `preventDefault()` 必须同步执行？**

Electron 不会等待异步保存完成再决定是否关闭窗口。

```ts
event.preventDefault() // 先阻止这次关闭
// 再通知页面，让用户选择、等待保存
```

如果先 `await save()`，窗口可能已经关闭，页面和保存流程就来不及继续了。

顺序必须是：**先留住窗口 → 等待决定 → 满足条件后重新关闭。**

**3. `allowOnce` 为什么要立即重置？**

因为确认退出后调用 `owner.close()`，会再次触发同一个 `close` 事件。

```ts
if (guard.allowOnce) {
  guard.allowOnce = false
  return
}
```

这相当于一张**只能使用一次的通行证**：让这次确认过的关闭通过，避免再次弹窗。

立即重置，是为了不把后续关闭也永久放行。

**4. `save` 改成 `Promise<boolean>` 解决了什么？**

让调用者明确知道：**保存到底成功了没有。**

`Promise<void>` 只表示没有返回值。尤其当保存函数内部已经捕获错误时，`await save()` 正常结束，也不代表写盘成功。

现在可以明确判断：

```ts
const saved = await storage.save('close')
if (!saved) return // 保存失败，留在窗口
await finish(id, true)
```

**5. 为什么同时需要 `closePending` 的 state 和 ref？**

它们负责不同事情：

| 变量 | 作用 |
|---|---|
| state | 触发重新渲染，禁用编辑，并让自动保存 Effect 暂停或恢复 |
| ref | 立即更新，供发送、清空、保存等回调读取最新的关闭状态 |

调用 `setState` 后，当前回调里的 state 不会立刻变成新值；写入 `ref.current` 则立即生效。

所以：**state 管界面更新，ref 管即时判断。** React 的 ref 改变不会自动更新界面，这和 Vue 的响应式 `ref` 不一样。

**6. “不保存并关闭”为什么不能删除文件？自动保存会撤销吗？**

“不保存”表示：**不把这次尚未保存的修改写入文件。**

例如：

- 文件已经保存了消息 A。
- 页面新增消息 B，但 B 还没保存。
- 选择“不保存并关闭”。
- 重启后仍有 A，没有 B。

如果删除 `conversation.json`，连 A 也丢了，这就变成了“删除历史记录”。

如果 B 已经自动保存，它也会保留，**不会被撤销**。

**7. 为什么生成中不能只看 `dirty=false` 就放行？**

因为 `dirty` 只回答：

> 当前聊天数据和上次保存的数据是否不同？

它不回答：

> 是否还有任务正在运行？

例如模型请求刚发出，还没产生新的内容，或者数据恰好与保存版本一致，并不能据此认定关闭安全。

所以先检查 `operation`：生成、读取或保存中，本课都先拒绝关闭。等任务结束，再判断是否有未保存修改。

**8. 三种 ID 分别是什么？为什么不能使用旧关闭回复？**

| ID | 标识什么 |
|---|---|
| 关闭请求 ID | 这一轮关闭确认 |
| 模型 `requestId` | 这一次模型生成任务 |
| 消息 `id` | 聊天列表中的某一条消息 |

它们都用于确定：**这个操作或结果属于谁。**

例如第一次关闭的 ID 是 A，你取消后重新关闭，得到 ID B。这时即使 A 的“允许关闭”迟到了，也不能关闭正在等待 B 确认的窗口。

因此主进程必须检查：**回复的 ID 是否等于当前等待的关闭 ID。**

把你点击“保存并关闭”的全过程串起来，就是：

**Alt+F4 → 主进程拦截 → 页面收到关闭 ID → 弹窗 → 等待保存成功 → 携带同一个 ID 回复允许关闭 → 主进程单次放行。**
