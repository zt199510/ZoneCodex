# 第四十一课：Codex 风格 AI 回复 UI 对齐

## 1. 本课目标与前置条件

本课把重点放在 AI 回复的可读结构和交互层次，向 Codex App 的回复体验靠拢。第40课已将工具记录和附件接入消息上下文；本课按用户反馈收口展示方式，不再使用自创的“处理步骤”卡片或“最终回答”标题。

前置条件是第35至40课：真实 Agent Responses SSE 已统一，消息和工具记录可以恢复，用户消息可以显示本轮附件。会话分支、并发 Agent、MCP、SSH、自动批准和任意命令继续后置。

本课目标：

- 形成清楚的回复层次：用户消息、附件摘要、真实工具活动、回答正文和消息操作。
- 让真实工具活动、修改/命令建议和回答正文在视觉上彼此分开；普通直接回答不显示虚构过程或时长。
- 让 Markdown 正文更接近聊天阅读密度，而不是长文档排版。
- 让代码块具备语言标签、复制入口和稳定的横向滚动边界。
- 保持真实 SSE、原始消息、工具历史和任务记录不变。

OpenAI 官方说明中，代码块应与正文分离，并可提供复制、语言标签、编辑、预览或运行等操作；本课只先落实复制和语言标签，预览、运行和写作块需要独立的权限与资源边界。

## 2. 用 Vue 经验理解本课

可以把一条助手消息看作一个由多个展示区组成的组件，而不是一段一次性 HTML：真实工具活动、正文和操作各自接收明确 Props。Vue 中可能通过 slot 组合内容，React 中则由 `MessageList` 组合 `MarkdownContent`、活动行和建议卡片。

Markdown 是原始文本的派生视图。原始回答继续保存在 `ChatMessage.content`，渲染器只负责安全转换，不能把 HTML 或带样式的副本写回会话。这样刷新、重试和后续上下文仍使用同一份原文。

实时活动来自 `toolActivity`，完成后的记录来自 `ToolRun.trace`；这些是请求和工具执行记录，不是模型原始思考。当前网关只有加密推理内容，没有可直接展示的思考文本；不能将 trace 命名为“思考过程”，也不能为了做 UI 增加一条普通文本请求。

## 3. 实际文件及职责

- `src/renderer/src/features/chat/MessageList.tsx`：组合用户消息、附件摘要、真实工具活动、回答正文和消息操作。
- `src/renderer/src/features/chat/MarkdownContent.tsx`：使用 `react-markdown` 和 `remark-gfm` 将助手原文派生为安全视图。
- `src/renderer/src/assets/chat.css`：消息状态、工具活动、附件和操作按钮的布局。
- `src/renderer/src/assets/markdown.css`：段落、标题、列表、引用、表格、任务列表和代码块样式。
- `src/renderer/src/features/chat/useChatRequest.ts`：提供实时增量和请求终态，不新增展示协议。
- `src/renderer/src/features/conversation/useConversation.ts`：合并持久化 trace，并保持会话切换边界。
- `src/shared/conversation.ts`、`src/shared/agent-history.ts`：保持原始消息和工具历史的校验、保存与恢复。
- `src/main/index.ts`：外部链接最终打开边界；renderer 不应直接信任任意协议。

## 4. 按依赖顺序实施

### 步骤一：先画出回复结构

从 `MessageList` 当前 JSX 画出一条完整回复：用户文字和附件、实际发生的工具活动、助手 Markdown 正文、修改建议或命令提案、复制/重试等操作。确认生成中、完成、失败和停止四种状态的显示差异。

预期结果：工具活动不混进回答正文，附件不拼进 Markdown 正文；普通回答不出现“处理步骤”卡片或“最终回答”标题。

常见错误：在 `MarkdownContent` 里读取任务状态，或让消息操作反向创建新的请求状态。

### 步骤二：收紧聊天排版

调整助手正文的段落、标题、列表和引用间距，使内容适合连续阅读；保留表格的横向滚动，避免窄窗口撑破消息区域。用户消息继续使用紧凑气泡，助手正文保持无多余容器背景的阅读面。

预期结果：短回答不显得稀疏，长回答仍能扫描，代码和表格不会改变页面宽度。

常见错误：为了视觉效果给每个 Markdown 节点套卡片，造成卡片嵌套或内容密度过低。

### 步骤三：增加代码块的最小工具栏

为围栏代码显示语言标签和图标复制按钮，复制成功后给出短暂状态反馈；代码继续使用原文并保持水平滚动。先不引入语法高亮依赖，也不把代码块变成可执行终端。

预期结果：用户可以辨认语言并一键复制完整代码，复制不会提交聊天表单或修改消息原文。

常见错误：通过字符串拼接生成 HTML，复制时误删最后换行，或让自定义代码组件产生嵌套 `<pre>`。

### 步骤四：处理链接、图片和其他内容块边界

链接只允许经过协议校验的 `http`/`https` 地址，并由主进程的外部打开策略最终拦截；相对路径和危险协议继续显示为不可用。图片、Mermaid、React 预览和 Python 运行暂不加入，等待明确的资源加载、沙箱和权限设计。

预期结果：链接行为可解释，Markdown 不会因为模型输出而在应用内导航或加载任意资源。

常见错误：只在 renderer 使用 `target="_blank"` 就认为完成了安全边界，或直接恢复原生 `img`。

### 步骤五：保持真实消息与工具链

验证 UI 改动只消费 `ChatMessage`、`toolActivity`、`ToolRun.trace` 和既有建议数据。不得增加模拟模型、普通文本回复入口、第二套 SSE、渲染后 HTML 持久化或新的工具执行器。

## 5. 验收条件

- 一条回复能清楚区分用户内容、附件、真实工具活动、回答正文和消息操作，不显示自创的“处理步骤”卡片或“最终回答”标题。
- 真实工具活动在生成中更新，终态和刷新后仍能恢复；普通直接回答不显示虚构活动或时长。
- Markdown 段落、标题、列表、引用、表格和任务列表在窄窗口不溢出。
- 代码块显示语言标签，可复制完整原文，复制按钮不会触发表单发送。
- 链接只允许安全的 `http`/`https` 外部打开；危险协议、相对路径和图片资源不会被执行或加载。
- 失败、停止、重试、编辑和会话切换不改变原始助手消息和工具历史格式。
- 真实 Agent Responses SSE、工具循环、附件请求和任务记录继续使用既有路径。

3. 自定义代码块组件为什么容易产生嵌套 `<pre>`？

## 7. 课程记录与下一步

第41课已实施，后按用户反馈继续调整：`MessageList` 将附件摘要、真实工具活动、回答正文、建议卡片和消息操作分开呈现，不再显示自创的“处理步骤”卡片或“最终回答”标题。助手仍只把原始 `ChatMessage.content` 交给 `react-markdown` 派生渲染。Markdown 排版收紧了段落、标题、列表、引用、表格和 GFM 任务列表，代码块增加语言标签、图标复制按钮、复制状态和横向滚动。
