# 第三十三课：任务状态收敛与生命周期闭环验收

创建日期：2026-09-26。状态：基础实现已完成，桌面生命周期验收待完成。

前一课：[第三十二课：任务生命周期与可恢复后台执行](42-第三十二课-任务生命周期与可恢复后台执行.md)。

本课是第32课的收口课。目标是让一条任务链真正满足“主进程管理运行时、会话保存展示记录、刷新后恢复展示、旧授权不能继续执行”的闭环，再决定后续是否进入权限模式或 MCP。

本课不新增跨重启进程恢复、并发 Agent、自动批准、SSH、MCP、命令队列、任意命令或全局状态库。也不搬移现有目录。局部整理只服务于任务生命周期的正确性和验收。

## 1. 本课目标

完成后应达到以下结果：

1. 主进程是任务状态的唯一权威，renderer 只发起操作并显示主进程事件。
2. 所有任务使用同一套窗口归属规则，不能混用 `webContents.id` 和 `BrowserWindow.id`。
3. 状态只能按允许的方向转换，终态不可回退或重复收尾。
4. 取消和超时先停止底层工作，收到可靠终态后再写入最终记录。
5. 刷新、窗口重载、会话切换、工作区撤销和窗口销毁都能清理运行时句柄，并留下可解释的展示状态。
6. 页面能显示任务历史、更新时间和重新发起入口；重新发起使用新的 `taskId`、`requestId` 和当前授权。
7. 任务记录的数量和文本长度限制与会话保存策略一致，不因超过上限导致整库保存失败。

`TaskRecord` 与运行时句柄分离、`taskId` 与 `requestId` 分离、授权不持久化仍然是本课必须保留的边界。严格运行时解析不是本课要删除的对象；只有在协议回归保持通过后，才可以把手写日期校验收敛为更简单的实现。

## 2. 当前源码中的收口问题

开始修改前，先阅读并在纸上画出当前链路：

```text
页面发送
  → preload IPC
  → 主进程创建任务和运行时句柄
  → 主进程发布状态事件
  → renderer 按任务 ID 更新展示
  → 会话保存允许持久化字段
```

当前需要重点核对的事实：

| 位置 | 收口问题 |
|---|---|
| `src/main/model/model-stream.ts` | 任务注册和 `jobs` 使用了 `webContents.id`，需要统一为窗口 ID |
| `src/main/agent/task-registry.ts` | 允许的状态转换、取消终态和运行时清理需要明确化 |
| `src/renderer/src/features/chat/useChatRequest.ts` | 不能继续作为第二个任务状态权威 |
| `src/renderer/src/features/conversation/useConversation.ts` | 刷新不能无条件把所有活动记录标成 `interrupted` |
| `src/renderer/src/features/project/WorkspaceStatus.tsx` | 目前只有最新状态，需要补历史、更新时间和重新发起入口 |
| `src/shared/conversation-library.ts` | 任务数量上限必须和保存前裁剪策略一致 |
| `src/preload/index.ts`、`src/shared/api.ts` | 核对 `task:list`、`task:cancel`、状态事件的来源和返回值 |

第31课遗留的根目录选择器、真实 `AGENTS.md` UI 读取和刷新后重新授权，只补足影响本课验收的最小链路，不借本课重做整个工作区功能。

## 3. 状态转换与收尾规则

先写一个允许转换表，再把所有入口对照它检查。可以使用以下最小范围：

```text
created
  ├─→ running
  ├─→ waiting_approval
  ├─→ cancelled / failed / interrupted

running
  ├─→ waiting_approval
  ├─→ completed / cancelled / failed / timed_out / interrupted

waiting_approval
  ├─→ running
  ├─→ cancelled / failed / timed_out / interrupted

completed / cancelled / failed / timed_out / interrupted
  └─→ 不再转换
```

实际项目可以根据某种任务的业务链路减少分支，但不能允许 `running → created`、终态回退或任意跳到成功终态。

统一收尾函数至少要负责：

- 清理计时器、事件监听器和运行时 Map；
- 释放工作区快照关联的短期授权；
- 先停止底层工作，再写入 `cancelled` 或 `timed_out`；
- 忽略旧 `requestId` 的迟到输出；
- 只向所属窗口发送状态事件。

取消按钮表示“请求取消”。页面不能因为按钮点击就自行把任务显示为完成或取消，最终文字应由主进程终态事件驱动。

## 4. 按依赖顺序实现

### 第一步：统一窗口归属

为模型流、Agent、命令执行和任务注册表确定同一种 `windowId` 获取方式。事件来源应先通过 Electron 的窗口关系得到 `BrowserWindow.id`，再交给任务注册表。

验收：同一个窗口创建的任务可以被 `task:list` 查询、被 `task:cancel` 取消，并能在窗口销毁时被清理；另一个窗口不能查询或取消它。

### 第二步：让主进程成为唯一状态权威

renderer 可以保存任务展示结果，但不能直接调用本地状态更新函数。发送、取消、确认和重新发起都走明确 IPC；状态变化只接受主进程返回值或 `task:state` 事件。

验收：在 renderer 中搜索任务状态写入点，确认没有“先改页面为完成，再等待主进程结果”的路径；迟到事件不会覆盖另一轮请求。

### 第三步：限制转换并统一取消/超时

在 `task-registry` 或共享纯函数中集中判断允许转换。把取消、超时、失败和窗口清理都接到同一个收尾路径，避免每种任务各自直接写终态。

验收：重复取消、终态后更新、非法回退、超时后的迟到成功事件都不会改变最终记录；底层句柄、计时器和监听器都释放。

### 第四步：实现刷新和会话切换恢复

页面加载时先读取会话库中的允许字段，再调用 `task:list` 对照主进程活动任务：

- 有运行时句柄的任务继续显示主进程事件；
- 没有运行时句柄的 `running` 或 `waiting_approval` 记录进入明确的 `interrupted` 展示；
- 不恢复旧的 grant、`preparedId`、`confirmationId` 或进程引用；
- 重新执行必须走新的任务和新的授权检查。

会话切换时要取消旧会话的运行时任务，检查事件中的会话 ID，防止旧任务污染新会话。

### 第五步：补任务历史和重新发起

页面至少显示任务种类、状态、更新时间、结果或错误摘要。等待批准不能显示为正在执行。对失败、取消、超时和中断记录提供重新发起入口，但入口只负责创建新请求，不复用旧任务或旧许可。

### 第六步：统一记录数量限制

确定任务记录的保留策略，例如保留最近的活动记录和有限数量的终态记录。renderer 追加、主进程存储和会话解析必须使用同一上限，不能出现主进程裁剪而会话保存仍无限追加的分裂行为。

### 第七步：只验证一条完整任务链

先选择一条可以稳定复现的任务链完成真实生命周期矩阵，再把同样的规则接到其他任务类型。不要为了“统一”同时重写聊天、Agent 和命令执行的全部实现。

## 5. Vue 经验对应

| Vue 习惯 | 本课 React/TypeScript 设计 |
|---|---|
| Pinia 只保存可展示任务列表 | 会话保存受限 `TaskRecord[]`，不保存运行时句柄 |
| `watch(route)` 触发取消 | 会话切换明确调用主进程取消和清理接口 |
| `computed` 派生状态文字 | 从主进程发布的 `TaskRecord.status` 派生页面状态 |
| 页面重新挂载读取 store | 读取会话记录后，再向主进程核对活动任务 |
| `onUnmounted` 清理订阅 | renderer 移除事件监听，主进程清理句柄和计时器 |

页面状态可以有自己的加载和错误状态，但不能另造一份任务生命周期。

## 6. 常见错误

### 把窗口 ID 当成任意数字

`webContents.id` 和 `BrowserWindow.id` 属于不同对象。只要注册、查询和清理没有使用同一命名空间，任务就可能看似创建成功，却无法被列表或窗口销毁流程找到。

### 取消后立即写入终态

取消回调只是通知底层停止。底层可能还在退出、回收或返回错误；必须等统一收尾路径确认后再记录最终状态。

### 刷新后直接假设任务仍可运行

持久化的 `running` 只是历史展示。刷新后需要重新核对运行时句柄，旧授权不能因为记录还在就重新生效。

### 为了简化而删除协议边界

任务记录限制、未知字段拒绝、结果长度限制和授权字段排除都有明确安全目的。收敛实现时先删除重复状态源，再考虑局部简化校验代码。

### 重新发起覆盖旧记录

重试是新任务。旧任务的失败、取消或中断记录应保留，新的 `taskId` 和 `requestId` 用于过滤新的事件。

## 7. 生命周期验收矩阵

至少逐项记录观察结果：

| 场景 | 必须观察 |
|---|---|
| 正常完成 | `completed`，结果可恢复，句柄和计时器释放 |
| 用户取消 | 不再追加输出，底层停止后为 `cancelled` |
| 启动失败或非零退出 | `failed`，错误可见，之后可新建任务 |
| 超时 | 底层停止，状态为 `timed_out`，没有残留资源 |
| 等待批准 | 状态为 `waiting_approval`，进程数为 0 |
| 重复 `requestId` | 第二次请求被拒绝，不产生第二个运行时任务 |
| 刷新页面 | 恢复记录，不恢复旧许可；无句柄任务明确中断 |
| 切换会话 | 旧任务取消或收尾，迟到事件不污染新会话 |
| 撤销工作区 | 关联任务取消，旧准备记录不可领取 |
| 窗口销毁 | 无孤儿进程、计时器和监听器 |
| 重新发起 | 使用新的 `taskId`、`requestId` 和当前授权 |
| 超过记录上限 | 会话仍能保存和重新加载，保留策略稳定 |

离线协议检查可以验证状态转换和字段边界；桌面验收至少需要覆盖一条真实 UI 链路。不能把类型检查或离线脚本通过写成全部生命周期场景已通过。
