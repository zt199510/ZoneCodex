# 第四十课：消息详情折叠与附件上下文展示

## 1. 本课目标与前置条件

第40课暂缓会话分支，当时将工具处理记录放进消息级折叠详情；本轮发送的附件出现在对应用户消息中，刷新后仍可恢复。这是第40课的历史实现。第41课按 Codex App 回复样式调整后，界面不再使用自创的“处理步骤”卡片；真实工具活动改为简洁的独立行，回答正文直接呈现。

前置条件是第35至39课已经完成：会话和工具历史可以保存恢复，附件通过真实项目快照授权，工作区上下文有独立生命周期，正式聊天统一使用 Agent Responses SSE。分支、并发 Agent、MCP、SSH 和任意命令继续后置。

本课完成后：

- 当时的实时 Agent 进度显示为消息下可折叠的处理记录；第41课后仅将真实发生的工具活动以独立行展示。
- 完成、失败或停止的轮次从已保存的 `ToolRun.trace` 恢复处理记录，不因清理实时状态而消失。
- 用户消息保存本轮实际发送的附件展示元数据；后续追问只复用授权，不重复标记旧附件。
- 附件只显示相对路径、文件大小和行数，不保存正文、绝对根目录、授权标识或协议内部 ID。
- 所有请求仍复用真实 Agent Responses SSE、既有工具循环、会话消息、工具记录和任务记录。

## 2. 用 Vue 经验理解本课

第40课曾用浏览器原生 `details` 实现局部折叠。消息只接收 `toolActivity` 和已保存的 `trace`，实时状态结束后由会话数据继续提供内容；不要为同一份记录再维护一套历史状态。第41课改变展示形式，但仍沿用这两个数据来源。`trace` 是请求与工具执行记录，不是模型原始思考。

附件授权和附件展示是两件事。授权快照可以继续服务后续追问，但用户消息只记录发送时的展示快照。可以把它理解成提交表单时复制一份不可变的摘要，而不是把整个文件对象或授权对象放入消息。

## 3. 实际文件及职责

- `src/shared/conversation.ts`：定义 `ChatAttachment` 和可选的用户消息附件字段，校验数量、相对路径、大小、行数和总容量，兼容旧消息。
- `src/renderer/src/features/chat/useChatRequest.ts`：请求被接受后复制本轮附件元数据，写入用户消息；重试保留原轮附件。
- `src/renderer/src/features/conversation/useConversation.ts`：把发送前仍待提交的附件传给请求层，区分本轮附件与持续授权。
- `src/renderer/src/features/chat/MessageList.tsx`：显示附件摘要和可折叠处理记录。
- `src/renderer/src/assets/chat.css`：提供消息详情和附件摘要的紧凑样式。
- `src/main/agent/tool-loop.ts`：处理记录只显示工具名称和结果长度，不把 `call_id` 等内部协议标识写入聊天详情。
- `src/renderer/src/components/ui/Icon.tsx`：提供附件文件图标。

## 4. 按依赖顺序实施

### 步骤一：核对现有处理记录

先确认实时进度进入 `useChatRequest.toolActivity`，终态记录进入 `Conversation.toolRuns[].trace`。完成请求时删除实时副本，但不能删除会话中的 `ToolRun`。

预期结果：生成中能看到新增步骤，完成、停止、失败和刷新后仍能从会话消息找到历史步骤。

常见错误：只渲染实时数组，或者把工具历史重新拼成一份与真实协议不一致的“展示历史”。

### 步骤二：收口消息级折叠

第40课在助手消息下使用原生 `details/summary` 显示步骤数量和记录列表；实时记录和持久化记录按消息 ID 合并，避免重复。第41课后的当前界面不再使用这一折叠卡片。

预期结果：每轮处理步骤都能独立展开，展开一条消息不会影响其他消息。

常见错误：把全部会话的步骤放在一个全局面板，或将 `requestId`、`call_id`、准备 ID 和执行 ID直接显示给用户。

### 步骤三：记录本轮附件摘要

发送前从待提交的项目选择中复制相对路径、字节数和行数。请求拒绝时不创建消息，也不写入附件；请求接受后只写入当前用户消息。授权仍由 `useProjectSelection` 管理，不进入 `ChatMessage`。

预期结果：一条用户消息能看到它实际携带的文件；下一条只使用已授权上下文的追问不会重复显示旧文件；重试同一轮仍显示原附件。

常见错误：把文件正文、绝对路径、快照 ID 或 grant 保存到会话 JSON，或者每次追问都从持续授权重新生成附件卡片。

### 步骤四：兼容旧会话并验证边界

旧用户消息没有 `attachments` 字段时按无附件读取。新增附件必须是用户消息、最多 8 个、路径为相对路径且不重复，大小和行数受限；非法会话快照整体拒绝，不能静默接受未知结构。

预期结果：旧会话仍可打开，新消息刷新后附件和处理记录仍在；附件元数据不会进入模型正文或第二套回复入口。

## 5. 验收条件

- 第40课原验收项：生成中的处理记录实时更新，完成后可按消息展开；第41课后的当前展示改为真实工具活动独立行。
- 切换会话、刷新后，已完成轮次仍能查看持久化处理记录。
- 处理记录不显示 `call_id`、请求 ID、绝对根目录或敏感路径。
- 用户消息显示本轮上传文件的文件名、大小和行数；无附件旧消息保持原样。
- 后续追问不重复标记上一轮附件，重试保留原轮附件。
- 空消息、发送拒绝、异步失败和停止不会产生孤立附件记录。
- 附件请求、普通聊天和工具调用继续走同一条真实 Agent Responses SSE；不恢复模拟模型、普通文本入口或第二套回复路径。

## 6. 自测题

1. 为什么 `ToolRun.trace` 可以作为刷新后的处理记录来源，而不需要新增展示历史文件？
2. 为什么第41课改为工具活动独立行后，仍需保留实时记录与持久化 trace 的归属和去重？
3. 持续有效的附件授权为什么不能直接等同于每条消息的附件列表？
4. 请求被拒绝时，为什么附件元数据也不能写入用户消息？
5. `ChatAttachment` 为什么只保存相对路径、字节数和行数？
6. 旧消息没有 `attachments` 字段时，解析器应该怎样处理？
7. 为什么 `call_id` 不适合显示在聊天处理步骤中？
8. 如何证明本课没有新增普通文本回复或第二套 SSE 路径？

## 7. 课程记录

第40课已实施。实际修改了共享消息校验、请求层附件快照、会话发送接线、消息详情折叠、附件摘要样式、文件图标和工具步骤脱敏。第40课暂不实现会话分支，分支功能后置。

已验证：`npm run typecheck:node`、`npx electron-vite build`、`npm run typecheck`、`npm run lint -- --quiet` 和 `git diff --check`。真实模型增量、附件选择后的桌面消息展示、刷新恢复和处理记录展开仍需在可用网关与桌面环境中验收。

第41课更新了显示方式：不再使用第40课的消息级“处理步骤”折叠卡片，真实工具活动改为独立简洁行。此处原有折叠设计只记录第40课当时的实现，不代表当前界面。真实模型增量、工具活动、附件展示和刷新恢复的桌面效果仍待验收。

本课明确不做：会话分支、并发 Agent、MCP、Skills、SSH、任意命令、工具历史诊断面板、文件正文持久化和第二套回复传输。
