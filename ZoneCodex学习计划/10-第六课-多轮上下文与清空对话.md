# 第六课：多轮上下文与清空对话

## 1. 本课目标与实际起点

第五课每次只发送当前一句话。本课让第二次请求带上第一次成功的问答，实现可观察的多轮文本对话，并增加“清空对话”按钮。

本次已核对代码：App 已显示 chatError 和等待提示；npm run typecheck 的 Node、Web 两组检查均通过。界面介绍仍写“模拟回复”，本课会替换。真实网关调用及第五课错误实验未由助手独立验证，先确保你能收到一次真实回复。

继续使用现有 gpt-5.5、Responses 和本地开发配置，保留 store: false、stream: false、30 秒超时、来源检查及输入防重复逻辑。文档不需要密钥，也不安装新依赖。核心代码仍由你亲手实现。

本课只重建 user/assistant 的文本上下文，不实现服务端会话、工具调用或完整推理状态回放。主进程每次接收完整的本次文本输入，不保存对话。模型能参考上文，是因为请求里带了上文。

## 2. 先把第五课的四个概念连起来

| 概念 | 在本课中的作用 |
|---|---|
| response.ok | HTTP 是否为 2xx，不代表一定生成了完整回答 |
| reply.ok | 应用自己的业务结果，false 表示这次没有可接受的回复 |
| sendingRef.current | 同步防止再次进入发送或清空操作 |
| finally | 不论成功、失败还是 try 内 return，都恢复请求状态 |

30 秒定时器负责触发 abort；AbortController 通知 fetch 中止本地等待；主进程 finally 清除定时器并释放 busy。React finally 恢复界面。两个 finally 负责的是不同层的资源。

Vue 中你可能直接修改响应式对象的 status；React 中用 map 创建新数组和新对象，通知界面更新。不要直接写 messages[0].status = 'complete'。

## 3. 本课的对话规则

第一次请求：

```text
user：请记住测试代号“蓝鲸27”。
```

第一次成功后，第二次请求：

```text
user：请记住测试代号“蓝鲸27”。
assistant：好的，测试代号是蓝鲸27。
user：刚才的测试代号是什么？
```

规则先确定，再写代码：

- 页面保留本次打开应用以来的消息；每条消息有 pending、complete 或 failed 状态。
- 只有成功的一问一答进入后续上下文。失败问题仍显示，并标为失败，但不会带到下一次请求。
- 每次最多携带最近 4 轮完整问答，再加当前问题，即最多 9 条消息。
- 本次请求正文总长度最多 24000 个 JavaScript 字符串长度单位；超出时整轮移除最旧历史。当前问题最多 4000。
- 这是教学用长度限制，不是模型 token 上限，也不是精确计费估算。历史变长会增加输入量。
- 等待回复时禁止清空；清空后删除页面消息、错误提示和输入草稿，下次请求不带旧历史。
- 工作目录独立于聊天，清空聊天后保留。刷新或重启仍丢失聊天内存状态。

本课的“清空对话”只是清除当前内存记录，不是多会话列表，也不删除服务商已经收到的数据。

## 5. 共享类型：字符串变为数组

将 src/shared/api.ts 改为：

```ts
export type ModelMessage = {
  role: 'user' | 'assistant'
  content: string
}

export type ModelReply =
  | { ok: true; content: string }
  | { ok: false; error: string }

export interface AppAPI {
  selectFolder: () => Promise<string | null>
  askModel: (history: ModelMessage[]) => Promise<ModelReply>
}
```

ModelMessage 是本课的文本输入类型，只有模型需要的 role 和 content；UI 的 id、status 不应发送给模型。共享类型不导入 React 组件类型。

此时旧的 askModel(content) 出现类型错误是正常的：这提醒你调用链还没全部改完。

## 6. 主进程：在边界检查数组

在 model.ts 的类型导入中加入 ModelMessage：

```ts
import type { ModelMessage, ModelReply } from '../shared/api'
```

在已有 isRecord 之后新增函数：

```ts
function parseHistory(value: unknown): ModelMessage[] | null {
  if (!Array.isArray(value) || value.length < 1 || value.length > 9 ||
      value.length % 2 !== 1) return null

  const history: ModelMessage[] = []
  let total = 0
  for (let index = 0; index < value.length; index++) {
    const item: unknown = value[index]
    const role = index % 2 === 0 ? 'user' : 'assistant'
    if (!isRecord(item) || item.role !== role ||
        typeof item.content !== 'string' || !item.content.trim()) return null
    if (role === 'user' && item.content.length > 4000) return null
    total += item.content.length
    if (total > 24000) return null
    history.push({ role, content: item.content })
  }
  return history
}
```

奇数条、从 user 开始、交替排列，所以最后一条必然是当前 user 问题。这是本课约定，不是所有模型 API 都要求这样的排列。

函数重新构造对象，只取 role、content，不转发额外属性。它验证数据结构，不证明历史真实，也不意味着过滤了聊天内容的语义。

在 askModel(input: unknown) 开头，用下面代码替换原来的字符串检查，紧接着保留原来的 if (busy)：

```ts
const history = parseHistory(input)
if (history === null) {
  return { ok: false, error: '对话格式或长度不符合要求，请清空对话后重试。' }
}
```

将 fetch 的 body 替换为：

```ts
body: JSON.stringify({
  model,
  input: history,
  store: false,
  stream: false
}),
```

其余配置检查、HTTP 状态处理、readReply、catch/finally 保留。

预期：主进程断点中的 history 是按顺序排列的数组，不再是字符串。不要打印密钥、请求头或真实私人聊天来调试。

在 main/index.ts 将 chat:ask 处理器改为（只改这一段，保留目录选择）：


## 8. 纯函数：从页面记录构造上下文

新建 src/renderer/src/context.ts：

```ts
import type { ModelMessage } from '../../shared/api'
import type { Message } from './components/MessageList'

export function buildContext(
  messages: readonly Message[],
  currentContent: string
): ModelMessage[] {
  const history: ModelMessage[] = [{ role: 'user', content: currentContent }]
  let total = currentContent.length

  for (let index = messages.length - 1; index >= 1; index--) {
    const assistant = messages[index]
    const user = messages[index - 1]
    if (assistant.role !== 'assistant' || assistant.status !== 'complete' ||
        user.role !== 'user' || user.status !== 'complete') continue

    const pairLength = user.content.length + assistant.content.length
    if (history.length + 2 > 9 || total + pairLength > 24000) break
    history.unshift(
      { role: 'user', content: user.content },
      { role: 'assistant', content: assistant.content }
    )
    total += pairLength
    index--
  }
  return history
}
```

这段代码按从新到旧的顺序寻找完整问答，再用 unshift 放到数组前面，最后得到从旧到新的请求顺序。移除历史只影响本次请求，不会删除页面消息。

为什么整轮保留？单独截掉用户问题、只留下助手回答，会缺少语境。为什么超长时 break？保留的是连续的最近成功问答范围，不会跳过一轮很长的近历史后又塞入更早的旧历史。若最近一轮本身过长，可能只发送当前问题。

readonly 表示此函数不能通过该参数修改原数组；它没有冻结运行时对象。函数只读 messages，并创建新的请求对象。

## 9. App：先构造快照，再等待回复

在 App.tsx 增加导入：

```ts
import { buildContext } from './context'
```

用下面内容替换整个 handleSend：

```tsx
async function handleSend(rawContent: string): Promise<void> {
  const content = rawContent.trim()
  if (!content || sendingRef.current) return
  if (content.length > 4000) {
    setChatError('请输入不超过 4000 个字符的消息。')
    return
  }

  const history = buildContext(messages, content)
  const userMessage: Message = {
    id: crypto.randomUUID(), role: 'user', content, status: 'pending'
  }

  sendingRef.current = true
  setIsSending(true)
  setChatError(null)
  setMessages((previous) => [...previous, userMessage])

  function markFailed(): void {
    setMessages((previous) => previous.map((message) =>
      message.id === userMessage.id ? { ...message, status: 'failed' } : message
    ))
  }

  try {
    const reply = await window.api.askModel(history)
    if (!reply.ok) {
      markFailed()
      setChatError(reply.error)
      return
    }
    const assistantMessage: Message = {
      id: crypto.randomUUID(), role: 'assistant',
      content: reply.content, status: 'complete'
    }
    setMessages((previous) => [
      ...previous.map((message): Message =>
        message.id === userMessage.id ? { ...message, status: 'complete' } : message
      ),
      assistantMessage
    ])
  } catch {
    markFailed()
    setChatError('应用通信失败，请重启应用后重试。')
  } finally {
    sendingRef.current = false
    setIsSending(false)
  }
}
```

重点观察两个地方：

1. history 在 setMessages 之前创建，并由 buildContext 加入当前问题一次。setMessages 之后立刻读取 messages，并不能得到刚追加的消息，这是 React 当前渲染的状态快照。
2. 成功时，一次状态更新将用户消息改为 complete，并追加 complete 的助手消息。失败时只标记本次用户消息，不把错误提示当作助手回复。

map 中按 ID 找消息，避免误改其他轮次。这里的嵌套 markFailed 只是普通函数，不是 Hook、生命周期方法或自动监听器。

## 10. 清空对话与输入草稿

在 App 的状态旁添加：

```tsx
const [inputVersion, setInputVersion] = useState(0)
```

在 App 内添加函数：

```tsx
function handleClearConversation(): void {
  if (sendingRef.current) return
  setMessages([])
  setChatError(null)
  setInputVersion((previous) => previous + 1)
}
```

在 MessageList 前添加按钮与说明：

```tsx
<button type="button" disabled={isSending} onClick={handleClearConversation}>
  清空对话
</button>
<p>每次携带最近最多 4 轮成功问答；内容过长时会减少，较早内容可能不再被记住。</p>
```

给现有 ChatInput 增加 key：

```tsx
{showInput && (
  <ChatInput
    key={inputVersion}
    disabled={isSending}
    onSend={(content) => { void handleSend(content) }}
  />
)}
```

改变 key 会卸载旧 ChatInput 并创建新实例，使它自己的 input 状态恢复为空。这是第三课卸载实验的实际应用，不会卸载 App。

只在清空时改变 key；不要使用 Math.random() 作为 key，否则普通重新渲染也可能丢失草稿。原来的 showInput 实验按钮可以保留。

等待时同时禁用清空按钮，并在函数中检查 sendingRef，防止清空后旧请求又把回复追加到新对话。这里还没有实现“请求中也能切换对话”；那需要请求 ID、会话 ID 和取消策略。

把页面“模拟回复”的介绍改为“多轮文本问答”。确认 ChatInput 的 input 已有以下属性，若没有则补上：

```tsx
disabled={disabled}
maxLength={4000}
```

保留第五课的等待和错误提示 JSX。

## 11. 本地实验与真实验收

先运行 npm run typecheck，停止 Debug All 后重新 F5。main、preload 和页面的接口签名需要一起更新。

先用断点验证数据，不只看模型是否答对：模型可能猜中或答错，请求内容才是上下文是否送达的直接证据。

| 实验 | 操作与预期 |
|---|---|
| 第一轮 | 告诉模型测试代号“蓝鲸27”；main 中 history 只有一条 user |
| 第二轮 | 问“刚才的测试代号是什么？”；history 按 user、assistant、user 排列，共 3 条 |
| 第三轮 | 再问“把代号最后的数字加一”；history 共 5 条，当前问题只出现一次 |
| 清空 | 请求完成后先输入草稿，再点清空；消息、错误、草稿都为空，工作目录保留 |
| 清空后的请求 | 再问代号；history 只有当前问题，不包含蓝鲸27 |
| 等待时清空 | 请求中按钮禁用；没有清空后旧回复回来的情况 |

失败实验：临时在主进程 askModel 的 try 内、fetch 前插入：

```ts
if (history[history.length - 1].content === '模拟失败') {
  return { ok: false, error: '学习实验：模拟失败' }
}
```

完整重启后，先完成一轮成功问答，再发“模拟失败”。应保留这条问题并显示失败标记和提示；按钮恢复。随后发送正常问题，主进程 history 应包含前一轮成功问答和当前问题，不包含“模拟失败”。try 中 return 仍会执行主进程 finally。

注意：完整重启会清除 React 历史，所以要在加入实验分支并重启后重新建立测试对话。实验结束后删除分支，再完整重启。

历史裁剪可只用本地数据验证：在 buildContext 返回前设置断点，通过调试器观察，或写一个一次性的本地脚本调用该纯函数。不要为了测试 4 轮上限反复付费请求。

| 输入数据 | buildContext 的预期结果 |
|---|---|
| 空数组 + 当前问题 | 只有当前 user |
| 5 轮 complete 问答 + 当前问题 | 最近 4 轮 + 当前问题，9 条；第一轮不在结果中 |
| 成功问答后夹一条 failed 用户消息 | failed 被跳过，成功问答保留 |
| 最近一轮长度为 23000，当前问题长 2000 | 历史整轮移除，只有当前问题 |
| 一轮 complete 问答 | 调用后原 messages 的内容与顺序不变 |

parseHistory 也要用本地值验证：空数组、首条 assistant、偶数条数组、非字符串 content、超长问题和总长度超过 24000 都应返回 null；合法的 user/assistant/user 应得到新的消息数组。

## 12. 范围、官方资料与后续

已核对 [OpenAI 官方会话状态文档](https://developers.openai.com/api/docs/guides/conversation-state)：可以在每次请求里显式传入过去的 user/assistant 消息来提供文本上下文。本课采用这一教学方式，保留 store: false，不使用 previous_response_id。

本课并非完整的 Responses 状态回放。官方同时建议推理模型的完整无状态续接保留全部 output 项，包括推理项及助手 phase；[phase 文档](https://developers.openai.com/api/docs/guides/reasoning#phase-parameter)说明 gpt-5.5 的中间说明与最终回答不应混淆。当前第五课只提取文本，故本课重新构造的是简化的文本对话，会丢失这些协议状态；不能直接用于工具循环或声称完整延续了推理。后续进入复杂流式或工具场景时，需要另建协议历史结构，不能只保存显示文字。

第三方网关是否接受这种多轮输入需要实际验收，官方文档不能证明第三方行为。本课不会读取本地密钥或代你请求网关。

文档创建时已对 buildContext、parseHistory 及对应类型做严格类型检查，并通过本地的轮数、长度、失败/pending 排除、原数组不变和非法参数验证。这不等于完整应用已经实现或网络交互已经验收。
