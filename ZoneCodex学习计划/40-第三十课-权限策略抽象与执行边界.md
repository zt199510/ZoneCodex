# 第三十课：权限策略抽象与执行边界

创建日期：2026-09-23。状态：已完成（用户反馈，2026-09-24）。

前一课：[第二十九课：真实 Agent 工具调用与权限闭环](39-第二十九课-真实Agent工具调用与权限闭环.md)。第29课已经完成真实 Agent 提案、用户确认和固定命令执行。本课把这条链从“只能执行一个固定命令”抽象成可复用的权限策略层。

## 1. 本课目标

理解并实现下面的分层调用链：

```text
模型提出工具调用
  → 解析为结构化提案
  → 权限策略判断风险、范围和是否需要确认
  → 沙箱/目录边界检查
  → 用户确认（如需要）
  → 执行器领取一次性许可
  → 结果回传 Agent
```

第29课的 `npm_typecheck` 仍作为第一个策略实例，但不再把它写死在界面、确认逻辑和执行器的每一层。

## 2. 与 Codex 权限模型的对应

本课学习两个不同概念：

- **批准策略**：决定操作是否需要暂停并等待用户确认。
- **沙箱边界**：决定操作可以访问哪些目录、文件和网络资源。

模型提出工具调用不等于获得权限。策略层必须独立于模型输出，执行器也必须独立重新核对授权。历史消息、模型理由和 UI 按钮都不能单独构成执行许可。

## 3. 建议的数据结构

新增或整理为纯共享类型，示例：

```ts
type PermissionRisk = 'read_only' | 'project_write' | 'command'
type ApprovalRequirement = 'none' | 'user'

type ToolProposal = {
  tool: 'propose_command'
  template: 'npm_typecheck'
  reason: string
  conversationId: string
  requestId: string
  assistantId: string
  callId: string
  snapshotId: string
}

type PermissionDecision = {
  risk: PermissionRisk
  approval: ApprovalRequirement
  allowed: boolean
  scope: { kind: 'project'; snapshotId: string }
}
```

类型只描述协议，不代表已授权。`preparedId`、`confirmationId` 和目录 grant 继续只存在于主进程短期记录中，不能写入聊天历史。

## 4. 实现步骤

### 第一步：提案与策略分离

把 `propose_command` 的参数解析、工具白名单、风险分类和用户确认判断分开。策略函数接收经过解析的提案及当前授权快照，返回允许、拒绝或需要确认的决定。

策略函数不能读取 React 状态，也不能相信模型传入的 cwd、程序、参数或环境变量。

### 第二步：把固定命令变成策略实例

保留 `npm_typecheck` 的固定程序和参数：

```text
程序：npm
参数：run typecheck
```

但把它放进策略/模板注册表。界面从模板元数据读取展示文本和影响说明，执行器从同一份受校验的模板生成启动参数，避免界面显示一条命令而实际运行另一条命令。

### 第三步：统一授权生命周期

确认以下记录边界：

- 提案记录：可随会话保存，用于展示。
- 目录授权：窗口和快照绑定的内存记录。
- 准备记录：短期、一次性领取。
- 确认 ID：只代表本次点击，不能重复使用。
- 执行记录：主进程维护，窗口销毁或授权撤销时清理。

关闭面板、切换会话、刷新页面、目录变化和授权撤销都不能留下可执行的旧许可。

### 第四步：统一结果协议

执行器只返回结构化终态：成功、非零退出、取消、超时、启动错误和输出截断。结果中区分 stdout 与 stderr，并注明退出码。Agent 可以根据结果继续回答，但不能把命令结果自动描述成文件已修改。

## 5. 验收场景

| 场景 | 必须观察 |
|---|---|
| 合法 `npm_typecheck` 提案 | 策略允许，但标记为需要用户确认 |
| 普通文本回答 | 没有权限提案和执行入口 |
| 提案带 cwd/command/env | 解析或策略拒绝，零进程 |
| 没有项目快照 | 策略拒绝，不能自行选择当前目录 |
| 用户未确认 | 不领取准备记录，不启动进程 |
| 重复 confirmationId | 主进程拒绝，不能多开进程 |
| 目录或脚本发生变化 | 旧准备记录失效，要求重新检查 |
| 刷新或切换会话 | 只恢复展示数据，不恢复执行许可 |
| 取消、超时、非零退出 | 终态清楚，不自动重试 |

入口拦截继续确认：没有 `node-pty` 输入、没有第二个 Agent 任务、没有任意命令分支，也没有写入测试目录之外的文件。

## 6. 本课不做的事情

- 不开放任意命令编辑器。
- 不建立永久批准规则。
- 不把模型的自然语言理由当作安全判断。
- 不实现完整的进程树隔离、容器沙箱或网络防火墙。
- 不加入 SSH、MCP、命令队列和自动重试。

这些主题应在策略抽象稳定后分别安排。

## 7. 自测题

1. 为什么批准策略和沙箱边界必须分开？
2. 为什么 `ToolProposal` 可以保存，而 `preparedId` 不能保存？
3. 为什么模板展示文本和执行参数应该来自同一份注册信息？
4. 为什么模型理由不能直接决定 `allowed`？
5. 为什么没有项目快照时不能把当前进程目录当作工作目录？
6. 为什么刷新后可以恢复提案卡片，却不能恢复执行按钮的有效许可？
7. 为什么执行结果需要区分退出码、stderr、取消和超时？
8. 什么时候应该把一个新工具安排成独立课程，而不是继续扩展本课？
