## 1. 本课目标与前置条件

本课完成一个可观察的功能：AI 命令通过真实 Windows 受限后端执行，允许在有效可写范围内工作，范围外写入和默认禁止的联网由系统阻止，子进程继承限制；停止或超时后能够核对整个受控进程树是否退出。

产品交互沿用当前输入框、三种权限菜单和输入框上方的授权浮窗。需要扩大本次执行权限时，继续显示原因、工作目录及可读命令，取消和确认位于右下角。技术验证在开发阶段完成，主聊天流程只呈现用户需要理解的执行结果和授权原因。

### 创建时的真实基线

| 能力             | 当前状态                                                                               |
| ---------------- | -------------------------------------------------------------------------------------- |
| 默认目录与工作区 | 未选工作区使用 `userData/chats/<conversationId>/workspace`；选择工作区后使用已授权目录 |
| 三种权限模式     | 请求批准、帮我批准、完全访问权限已启用；第44课完成独立评估和人工回退                   |
| 命令启动         | 通用命令与旧 npm 入口共用 `startCommandProcess`，底层仍是普通 Node `spawn`             |
| 沙箱策略         | 两处命令授权仍传入 `sandboxAvailable: false`，普通命令需要按模式批准                   |
| 停止能力         | `CommandProcess.stop()` 停止观察并请求杀主进程，尚不能确认进程树退出                   |
| 保存与重试       | 版本6、权限 revision、范围核对、副作用证据和消息级重试保护已存在                       |

前置练习：能沿“工具调用 → 授权 → 启动 → 结果”找到实际函数，并说明默认目录、可写范围、审批策略和执行后端分别解决什么问题。第44课与工程整理已有的测试只证明当时能力，不能作为本课沙箱已存在的证据。

本课的实施先通过原生方案验证，再修改执行链。若当前系统或后端不能提供要求的边界，应记录具体缺口，保留实际不可用状态；不能先启用自动放行，再补隔离。

## 2. 用 Vue 经验理解本课

在 Vue 应用中，隐藏一个按钮并不能阻止后端接口被调用。同样，页面显示“请求批准”、检查 `cwd` 或让模型判断安全，也不能限制已经启动的程序访问磁盘和网络。

| 概念         | 用已有经验理解             | 本课职责                                           |
| ------------ | -------------------------- | -------------------------------------------------- |
| 权限菜单     | 展示后端确认的表单选项     | 选择审批方式，界面不能制造沙箱能力                 |
| 权限策略     | 服务端业务条件判断         | 决定可以执行、需要评估、人工批准或拒绝             |
| 单次执行计划 | 服务端核验后的具体操作记录 | 绑定本条命令、边界、后端和批准，防止等待后发生漂移 |
| Windows 沙箱 | 操作系统实际执行的访问控制 | 程序即使主动越界，也会被限制                       |
| 进程生命周期 | 外部资源的启动、关闭与清理 | 停止请求和确认全部进程退出分别处理                 |

React 的 `state` 和 `ref` 继续负责展示与异步状态读取。沙箱句柄、命令计划和一次批准由主进程拥有，保存聊天不会恢复这些运行时能力。

## 3. Codex 官方依据与本课技术路线

本课创建时实际读取以下官方页面，核对日期为 2026-10-06：

- [Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)：原生 Windows 的 elevated / unelevated 两种实现及限制。
- [Permissions](https://learn.chatgpt.com/docs/permissions)：文件和网络边界，以及网络限制需要系统执行的原因。
- [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)：沙箱、批准、完全访问及独立沙箱探测命令。

### 原生 Windows 的两种方案

| 官方方案   | 关键机制                                                               | 本课判断                                       |
| ---------- | ---------------------------------------------------------------------- | ---------------------------------------------- |
| elevated   | 经管理员批准完成初始化，使用专用低权限用户、文件 ACL、防火墙和本地策略 | 优先核对这一路线，验证真实文件及网络边界       |
| unelevated | 从当前用户生成受限 token，配合 ACL；网络主要依靠环境层面的离线控制     | 网络隔离较弱，不能作为与优先方案等效的验收结果 |

这里的 elevated 指初始化需要提升权限；沙箱中的任务使用受限身份执行，不能将其解释为“AI 命令以管理员身份运行”。官方两种方案默认使用私有桌面，但私有桌面本身也不能替代文件、网络和进程控制。

Windows 11 是推荐环境，较新的 Windows 10 为尽力支持。企业策略、账户和防火墙配置可能限制原生方案。课程实施时先记录本机实际系统、用户权限和可用后端，再选择具体方案；创建文档没有初始化账户、修改 ACL 或防火墙。

### 怎样接入 ZoneCodex？

官方页面描述 Codex 的行为，没有提供可直接导入 Electron 的稳定 `sandbox.spawn()` API。优先验证官方独立沙箱执行能力能否作为本项目实际后端；官方提供的探测入口是：

```text
codex sandbox windows [--permissions-profile <name>] [COMMAND]...
```

这只是官方命令形式。实施时应先读取本机版本和帮助，核对 Windows 支持、参数、目录与权限传递、输出、退出码和取消能力，固定实际验证过的版本。不能仅凭文档就写死包装器或认为已安装该工具。

若这条路线满足独立执行与分发要求，可复用其真实沙箱能力；若接口或进程生命周期不满足要求，再决定是否采用经过核验的原生辅助程序。原生程序必须落实受限身份、文件访问、网络和进程树管理。仅有 Job Object 解决不了文件或网络隔离，仅有受限 token 也不能证明全部边界已建立。

选型结束只采用一个实际可运行的方案。辅助程序路径、来源、版本校验和打包定位都要有依据。不要用 `codex exec` 执行本项目命令，它会开启另一个 Agent 循环；修改 Codex 的 `config.toml` 也不会自动给 ZoneCodex 的 Node 子进程加上沙箱。

本课对齐命令隔离及按需升级的行为。现有第44课评估异常转人工批准，官方当前 auto-review 的失败处理为拒绝；这项既有差异另行记录，本课不将当前三模式称为全部行为已完全一致。

## 5. 按依赖顺序实施

### 步骤一：验证一种真实可用的原生后端

先做只读环境核对，记录系统版本、后端版本、实际可执行路径、初始化条件和开发/打包方式。官方独立沙箱入口先用最小固定命令探测；若需要系统初始化，应明确初始化动作与命令运行身份，实际执行按当时的授权范围处理。

**练习：**给选中的方案写一份简短结果：它怎样限制文件写入、怎样阻止直接联网、子进程怎样继承限制、怎样停止并确认进程树退出，以及哪些能力已实际验证。未验证项保持待验证。

**预期效果：**能够启动真实受限进程并获得结果；后端缺失或不可用时有明确原因。

**常见错误：**用环境变量代理、命令名称白名单、`cwd` 或 `shell: false` 冒充隔离；让普通 `spawn` 作为初始化失败后的静默备用方案。

### 步骤二：先证明文件、网络和后代进程的边界

在专用临时目录建立范围内文件、范围外标记文件和受保护子目录。标记文件使用合成短文本，保留原始哈希；验证完成只清理本次创建的 fixture。

实际边界至少包含：

1. 有效可写根与必要的临时目录。程序和系统运行所需的读访问按实际方案定义；当前策略对读取返回允许，不能写成“所有读取都只能在工作区”。
2. 范围外写入受限，包括绝对路径、`../`、不同盘符、junction、符号链接及后代进程的访问。路径解析帮助核对边界，系统控制才承担实际阻止。
3. `.git`、`.agents`、`.codex` 等受保护路径递归只读；`.git` 是指向外部 gitdir 的文件时，要核对实际目标。限制应防止通过改名、删除父目录、链接或修改 ACL 绕过，不能只匹配路径字符串。
4. 默认受限命令不能直接联网。用可控 listener 和系统规则验证 HTTP/TCP、IPv4/IPv6、回环及子进程路径；公网连接失败不是隔离成立的证据。将来若引入代理，也必须阻止绕过代理的连接。
5. 辅助程序与任务只得到必要环境；模型凭据不能因继承 `process.env` 进入子进程，检查只记录变量名和有无，不输出凭据值。

上述保护路径要求针对本课命令沙箱。现有文件工具的完整读取、冲突及小文本策略仍有独立执行边界，不能用命令测试代替文件工具验证。

**练习：**让 fixture 命令真正发起越界写入和连接，再核对拒绝结果、范围外文件哈希、listener 连接计数及子进程结果；不能在工具参数层提前拒绝后就宣称 OS 沙箱有效。

**预期效果：**范围内工作成功，越界动作在真实进程中被拒绝，子进程不能绕过限制。

**常见错误：**只测父进程，或只限制辅助程序却让它启动的任务获得普通用户权限。

### 步骤三：在主进程绑定本条命令的执行计划

当前 `WorkspaceApprove` 只返回 `Promise<boolean>`。一个 `true` 无法说明批准的是“保持沙箱执行”还是“允许本条命令脱离沙箱”。需要让授权和实际启动使用同一条主进程记录。

先列出计划必须绑定的信息，再决定最小类型：

| 信息                                             | 绑定目的                                                       |
| ------------------------------------------------ | -------------------------------------------------------------- |
| 窗口、会话、请求及具体 program/args/cwd          | 不能拿一条命令的批准启动另一条；解析出的程序与参数不得事后替换 |
| 可写根、受保护路径、必要临时访问、网络及环境政策 | 授权所见的边界就是实际后端执行的边界                           |
| 模式、revision、运行 scope、来源与目录身份       | 等待期间改变权限、工作区或配置后计划失效                       |
| 选定后端、版本及本次能力状态                     | 能力来自主进程实际核验，不能由 renderer 布尔值或模型声明决定   |
| 本次是否升级及对应的一次批准                     | 完全访问、沙箱内允许和批准升级都有明确来源                     |

计划采用不可变快照，嵌套参数和边界不能在批准后被修改。启动前重新核对当前能力、目录和权限；后端被移除、配置改变或版本变化时旧计划失效。需要升级时为精确操作形成新的待批准记录，旧沙箱计划不直接扩大范围。

主进程内部能力优先保留在内部。`ExecutionInfo` 当前严格只有 `cwd`、`scopeId`、`mode`、`revision`；若确需改变共享字段或范围指纹，必须同时说明解析、比较、协议历史、旧记录和重试来源如何处理，不能顺手新增字段或升级版本7。

**练习：**分别说明取消、权限切换、批准后的 argv 改变、后端失效会在哪一步被挡住，并核对两个命令入口都执行同一条计划。

**预期效果：**获批的具体执行方式与实际后端一致，过期批准零启动。

**常见错误：**把 `sandboxAvailable` 全局改成 `true`，仍让 `command-runner.ts` 普通启动；只证明 cwd 在根内就认为命令不会越界。

### 步骤四：让三种模式选择实际执行方式

下表是本课实施后的目标行为，前提是该命令的实际沙箱能够落实已核验的边界：

本步骤先明确决策，再与步骤五的真实后端路由同时接通；隔离未落实时，继续保持 `sandboxAvailable: false`，不能先发布权限放行。

| 场景                            | 请求批准 `default`                        | 帮我批准 `auto-approve`            | 完全访问权限 `full-access`     |
| ------------------------------- | ----------------------------------------- | ---------------------------------- | ------------------------------ |
| 范围内可由真实沙箱执行的命令    | 沙箱执行，权限层无需额外批准              | 沙箱执行，不调用风险评估器         | 按用户选择使用非沙箱后端       |
| 明确需要扩大文件/网络权限的命令 | 批准精确的本次升级后执行                  | 按第44课评估，必要时人工批准后执行 | 按完全访问方式执行             |
| 启动前发现沙箱不可用            | 明确请求批准本次非沙箱执行，或拒绝        | 按真实非沙箱操作评估/批准，或拒绝  | 非沙箱执行仍须通过其他前置检查 |
| 已启动后沙箱或执行失败          | 返回真实失败/未知结果；再次执行需要新请求 | 同左                               | 同左                           |

旧 npm 的提案、准备和明确执行确认继续保留。沙箱内允许意味着不再追加权限升级弹窗，并不取消旧入口原有的执行确认；需要升级且缺少可信用户任务时，仍按现有规定人工批准。

越界错误只表明本次运行被阻止，不能自动触发普通后端重跑。确有升级需要时，向用户说明本条命令为何需要扩大权限，按原授权流程批准新的精确执行。初始化提升权限和单条命令升级也不是同一份批准。

完全访问选择的是本机当前用户权限下的非沙箱运行，不代表自动获得管理员权限。参数、来源、取消、目录配置和重复提交检查继续生效。

**练习：**用同一条固定命令分别观察三种模式，记录实际后端和批准次数；拒绝、取消和迟到允许结果必须零启动。

**预期效果：**模式影响真实执行方式，范围内受限命令直接工作，升级沿用现有浮窗。

**常见错误：**把安全评估结论当作操作系统限制，或把一次升级变成后续所有命令的永久授权。

### 步骤五：接入共用底层，保留两个入口的差异

在 `startCommandProcess` 使用所选后端，保持具体授权和业务回执在各自调用者中。后端应能够返回输出、真实退出、启动失败和进程树收尾结果；辅助程序自身退出不一定代表任务及全部后代退出。

| 原有行为   | 通用工具命令                            | 旧 npm 入口                                          |
| ---------- | --------------------------------------- | ---------------------------------------------------- |
| 时间限制   | 30秒                                    | 60秒                                                 |
| 输出限制   | 合计1800字节，按原始字节捕获            | 合计256KiB，按当前文本块事件输出，截断后停止输出事件 |
| 当前环境   | 已有白名单                              | 当前继承主进程环境                                   |
| 启动前检查 | 路径/当前性、批准后二次核对、`onEffect` | 一次准备/确认、来源、目录及脚本配置复核              |
| 运行与结果 | 每250ms授权巡检，退出复核，返回工具结果 | 分段事件、执行回执及任务终态                         |

两套限额和输出方式分别保留。旧 npm 的环境继承是本课需要明确处理的缺口：实施时移除模型凭据等不应传入的变量，说明必要变量及兼容性，不为统一代码而将两个入口的环境策略整体互换。

命令继续采用程序与参数数组，不能为了 Windows `.cmd` 兼容而直接拼接不可信 shell 文本。真实 `npm.cmd` 与 `shell: false` 的运行方式需单独验证；若采用可信启动器，应核对空参数、空格、中文路径和转义，记录实际执行了什么。

`onEffect` 继续在真实启动尝试前记录。即使后来启动报错，也不能自动认定未产生效果并恢复安全重试；尤其在辅助程序已启动或失去联系后，结果可能未知。

**练习：**在两个入口分别验证正常退出、非零退出、启动失败、输出上限和 UTF-8 边界；一个入口的替身通过不能代替另一个入口的真实 Windows 验证。

**预期效果：**两条命令路径使用同一真实后端，业务限额、一次确认和副作用记录准确。

**常见错误：**只给通用工具加沙箱，旧 npm 仍普通启动；后端失败后在同一次调用中换普通 `spawn`。

### 步骤六：修正停止和结算时序

当前 `stop()` 先清理监听、再 `child.kill()`，随后 `close` 被忽略。实施进程树停止时必须同步调整底层与两个入口的结算顺序，不能只增加一个杀进程命令。

后端的生命周期应满足：

1. 任务执行第一条用户指令前，受限身份、访问控制和进程容器已经生效。若自建原生启动器，要保证创建与加入容器之间没有可运行的逃逸窗口。
2. 子进程和后代继承限制，不能通过脱离容器留在后台。主进程提前退出时，剩余后代仍受控，并按本次生命周期收尾。
3. 停止、超时、授权撤销、窗口刷新/关闭均到达执行拥有者。请求终止后继续等待可靠的收尾证据，在有界时间内确认或报告未确认。
4. stdout/stderr、退出、停止、计时和任务终态只结算一次；迟到事件不重新打开任务，运行句柄、监听器和计时器被释放。

`cancelled` 表示请求被取消，不能单凭这个状态声称进程树已退出。终止未确认时沿用现有错误/结果通道如实表达，并保留禁止自动重试的证据。

窗口关闭后 renderer 已销毁，收尾仍由主进程负责；必要结果与未确认的证据不能依赖页面还在显示，记录中只保留非敏感诊断。

**练习：**fixture 启动父、子、孙三个进程，让后代周期性写心跳。分别触发停止、短超时和授权撤销，核对相关 PID、容器终止信息和心跳停止；同时测试父进程先退出的情况。

**预期效果：**能够证明整个受控进程树结束，无法证明时返回准确结果。

**常见错误：**调用 `kill()` 或 `taskkill` 后立即宣称完成；只查看主 PID，忽略后代及终态后的持续写入。

### 步骤七：同步真实能力描述并验证打包

后端实际接通后，再更新 Agent 与评估器指令。主 Agent 应知道当前命令是在什么边界下执行，哪些需求可能需要批准；升级评估必须按升级后真实拥有的文件、网络及子进程访问范围判断。

当前两处提示都写“没有 OS 沙箱”。不要只改权限布尔值而保留错误描述，也不能对不可用后端宣称已经隔离。可信能力由主进程构造，文件中的文字、模型参数和 renderer 状态不能改变它。

授权原因使用用户能理解的表达，例如“此命令需要在当前受限环境之外运行”，并保留具体原因和可读命令。辅助程序名称、token、ACL、Job Object 等留在开发诊断中。

开发和打包产物分别验证辅助程序定位、版本、启动权限、带空格路径、进程清理与错误传播。应用向模型服务发送请求的网络，与沙箱命令的网络是两个边界；阻止命令联网不能误切断应用本身的 Responses SSE。

**练习：**从主进程构造的当前能力找到最终 Agent 说明，分别检查沙箱可用、不可用及本次升级的描述。

**预期效果：**界面、Agent 说明和实际执行方式一致，打包后具有同样的受限能力。

**常见错误：**开发版可用就记为打包通过，或把未公开的内部接口写成确定可用的依赖。
